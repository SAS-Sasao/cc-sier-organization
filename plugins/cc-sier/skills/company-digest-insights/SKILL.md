# 日次ダイジェスト知見抽出 Skill

蓄積済みの日次ダイジェストを入力に、**採用判断できる形**の知見を取り出してカタログへ追記します。

単なる要約ではなく、**自組織で実測して採用可否を判断する**ところまでが範囲です。

---

## 1. この Skill が守る原則

### 1.1 原本を読む（HTML ではなく MD）

配信ページ（GitHub Pages）ではなく `.companies/{org}/docs/daily-digest/*.md` を読みます。HTML は MD からの変換物であり、変換前を読む方が欠損がありません。

### 1.2 キーワード検索を主手段にしない

キーワードでは本質を拾えません。実績として、`Skill` で 4 件・`レビュー` で 4 件しかヒットせず、実際に最も効いた記事群（CLAUDE.md 削減系 6 件）を取りこぼしました。

**タイトルを全件目視でクラスタリング**してから絞り込みます。

### 1.3 原文は curl で取得する

@.claude/rules/web-content-fetch.md に従います。Zenn / Qiita / はてブは WebFetch の信頼ドメイン外で、要約経由になると一次情報リンク・数値の文脈・原文表記が落ちます。

### 1.4 主張を鵜呑みにせず自組織で実測する

記事の主張が本組織に当てはまるかは、**測らないと分かりません**。体感で判断すると取り違えます。

実測なしの採用判断は行わないこと。

### 1.5 採用しない判断も記録する

「不採用」とその理由を残します。理由がないと、後から同じ検討を繰り返します。

## 2. フェーズ構成

| Phase | 名称 | 主な出力 |
|---|---|---|
| 0 | 前処理（org / 期間 / ブランチ / task-log） | task-log |
| 1 | 母数の把握とクラスタリング | クラスタ表 |
| 2 | 上位記事の原文精読（curl） | 記事ごとの要点 |
| 3 | 自組織での実測 | 実測値 |
| 4 | 採用候補の判定 | 候補一覧（採用状況・コスト・未確認事項） |
| 5 | レポート作成 + カタログ追記 | 解析レポート / カタログ更新 |
| 6 | PR + 報告 | PR URL |

---

## 3. Phase 0: 前処理

```
1. .companies/.active から {org-slug} を取得
2. git config user.name → {operator}
3. 対象期間を決める（既定: 当月。「先月」「8月」等の指定があればそれに従う）
4. git fetch してリモート差分を確認（ローカルが古いと最新ダイジェストを取りこぼす）
5. git status --porcelain が空でなければ観測データをコミットして clean 化
6. ブランチ作成: {org-slug}/docs/{YYYY-MM-DD}-digest-insights
7. .task-log/{task-id}.md を作成
```

---

## 4. Phase 1: 母数の把握とクラスタリング

### 4.1 対象章

A1（AI駆動開発・エージェント）と A2（AI・ML・LLM）を既定とします。依頼に応じて A3〜A6 / B 章も対象にできます。

### 4.2 抽出

```bash
D=.companies/{org}/docs/daily-digest
awk '/^### A1\./{f=1;next} /^### A3\./{f=0} f&&/^\| [0-9]+ \|/{print}' $D/{YYYY-MM}-*.md \
  | sed -E 's/^\| *[0-9]+ *\| *\[([^]]*)\].*/\1/' | sort -u
```

### 4.3 クラスタリング

**全件のタイトルを読んで**、本リポジトリへの関連度でクラスタに分けます。クラスタごとに件数と関連度（直撃 / 高 / 中 / 低）を表にします。

「モデル/インフラ動向」（Bedrock の新機能、ローカル LLM 等）は件数が多くなりますが、**採用判断の対象外**として分離してよいです。

---

## 5. Phase 2: 原文精読

### 5.1 選定

関連度「直撃」のクラスタから **3〜5 件**に絞ります。全件精読は非現実的で、絞らないと解析が浅くなります。

選定理由をレポートに明記すること。

### 5.2 取得

URL はダイジェスト本文から抽出します。

```bash
grep -h "{記事タイトルの一部}" $D/{YYYY-MM}-*.md | head -1 | grep -oE 'https://[^)]+' | head -1
```

取得手順は @.claude/rules/web-content-fetch.md のとおり。

---

## 6. Phase 3: 自組織での実測（この Skill の中核）

記事の主張ごとに、**本組織の該当箇所を測ります**。

### 6.1 測定の例

| 記事の主張 | 測る対象 | 手段 |
|---|---|---|
| CLAUDE.md は短く保つべき | `CLAUDE.md` / `rules/` の文字数・指示数 | `wc` / `grep -c` |
| 強い言葉は過剰反応を招く | 「必須」「禁止」「MUST」等の出現数 | `grep -o \| wc -l` |
| Skill は弁別性で死ぬ | frontmatter のトリガー語重複 | Python で抽出して集合演算 |
| コメント量は不確実さの指標 | コメント比率・連続ブロック | `.claude/hooks/measure-comment-density.py` |

### 6.2 測定結果の扱い

- 記事の数値と**並べて比較**する（本組織が上回っているか下回っているか）
- 測定できなかったものは「未測定」と明記する
- **測定スクリプトは再現可能な形で残す**（再測定できないと、対策の効果が判定できない）

---

## 7. Phase 4: 採用候補の判定

### 7.1 記録する項目

候補ごとに次を記録します。

- 何を主張しているか（詳細は個別レポートへリンク）
- 採用状況（✅採用済 / 🔶部分 / ⬜未採用 / ❌不採用）
- 適用先（cc-sier 本体 / 派生アプリ / 両方）
- コストと、判断に必要な追加情報

### 7.2 優先度の付け方

**「理論上の欠落」より「実際に問題が起きている」を上に置きます。**

実績: 候補 B（`verification-pending` の追加）を優先度「高」としたのは、`retail-stats-tracker` で「動いたが使えるか未検証」が `completed` として記録される事態が実際に発生していたためです。

### 7.3 不採用の判定も書く

理由つきで残します。実績として、進行中タスク 1 件制限は「cc-sier の並列は 1 タスク内での Subagent 分担であり、Agent Teams の設計と衝突する」ため ❌ としました。

---

## 8. Phase 5: レポート + カタログ追記

### 8.1 レポート

`.companies/{org}/docs/research/digest-{YYYY-MM}-ai-insights.md` に作成します。

構成: 方法 → クラスタ分析 → 精読記事と実測 → 採用候補 → 未検証事項

**§0 に方法（母数・絞り込み手順・なぜその手順か）を必ず書くこと。** 後から再現・検証できなくなります。

### 8.2 カタログ追記

`.companies/{org}/docs/research/ai-driven-development-practices-catalog.md` に追記します。

- 新しい知見を節として追加（A〜Z の採番を継続）
- §7 の優先度まとめ表を更新
- §8 の未検証事項を更新

**カタログが採用判断の入口**です。個別レポートを積み上げるだけでは判断に使えません。

### 8.3 未検証事項を必ず書く

@CLAUDE.md の「不確実さを分量で埋めない」に従い、次を明記します。

- 精読しなかったクラスタは「タイトルからの推定に留まる」と書く
- 測定できなかった項目
- 新設したものが実際に効くかは「次回以降の観察待ち」

---

## 9. Phase 6: PR + 報告

@.claude/rules/git-workflow.md に従います。

PR 本文には次を含めます。

- 母数（記事数 / ユニークタイトル数）と絞り込みの手順
- 実測値（記事の数値と並べる）
- 採用候補と優先度
- 未検証事項

## 10. Skill / ルールを新設する場合

この Skill の解析結果として新しい Skill やルールを作る場合、**作成ゲート 4 問**を通します。

| # | ゲート | 判断基準 |
|---|---|---|
| 1 | 反復性 | その作業はもう繰り返し起きたか（**先回りの投機的作成が未使用の最大要因**） |
| 2 | アップリフト | 素の AI に頼むより明確に良くなるか |
| 3 | 区別可能性 | 隣の Skill とトリガー語が重ならないか |
| 4 | オーナーと寿命 | 誰が保守し、いつ見直すか |

**1 つでも No なら作りません。**

### 10.1 トリガー語の重複チェック（必須）

新設前に、既存 Skill の frontmatter からトリガー語を抽出し、**完全一致だけでなく部分一致も**確認します。

意味空間が重なると「票の取り合い」が起き、**エラーは出ずに静かに呼ばれなくなります**。

実績: 本 Skill の新設時、「ダイジェスト解析」は既存 4 語（`日次ダイジェスト対応` 等）と部分一致したため採用せず、「知見抽出」「ネタ探し」等に差し替えました。
