概要

Codex Review Gateway は、GitHub PR を OpenAI Codex に独立レビューさせる「セカンドオピニオン・レビューゲートウェイ」の AWS 参照構成。要件定義書 v0.1 の機能要件（FR-01〜18）・非機能要件（NFR-01〜13）を AWS サービスに写像した。Codex の app-server プロトコル（JSON-RPC 2.0 over stdio）を Web サービスのバックエンドに組み込む際の最大の論点 — ① マルチテナントのプロセス管理、② エージェント実行のサンドボックス隔離 — を、spawn-per-review（レビュー 1 件 = app-server 1 プロセスの使い捨て）+ 承認リクエスト全拒否の設計で回避している。

同期系（Webhook 受信・ダッシュボード API）と非同期系（レビュー実行、中規模 diff で〜5 分）を SQS で分離し、レビューワーカーは Private Subnet 内の read-only コンテナとして NAT Gateway 経由で OpenAI モデル API にのみ egress する。採点結果（6 軸 + composite の JSON）は RDS PostgreSQL に、生レスポンスログは 90 日ライフサイクル付きの S3 に保存する。

ジョブライフサイクル: Webhook 受信で queued のレビュージョブが起票され、ワーカーが SQS から取得して running に遷移。VisibilityTimeout（15 分）をレビュータイムアウトの上限とし、2 回失敗したジョブは DLQ に隔離して CloudWatch アラームで通知する。ワーカーは diff を一時ワークスペースに展開して codex app-server にレビューさせ、完了後はプロセスとワークスペースを即時破棄する（コードはレビュー実行中のみ保持、NFR-05）。

設計のポイント

1. spawn-per-review でプロセス管理問題を消す — app-server はスレッド（会話）をプロセス内に保持するステートフルな作りだが、レビューは 1 件完結の処理なので「レビューごとに spawn → 採点 JSON 回収 → 破棄」の使い捨てモデルを採用。プロセスプール・スレッド常駐管理・メモリリーク監視が不要になり、ワーカーのスケールアウトは SQS のジョブ数に対する ECS Service の水平スケールに帰着する。

2. 同期 / 非同期の境界を SQS に固定 — レビューは中規模 diff で〜5 分（NFR-01）かかるため、Webhook 応答（GitHub は 10 秒でタイムアウト）と分離が必須。VisibilityTimeout 15 分をレビュータイムアウトの物理上限とし、maxReceiveCount=2 + DLQ で「自動リトライ 1 回、以後は人間へ」（NFR-04）をキュー設定だけで実現している。

3. エージェント実行の多層サンドボックス — ワーカーコンテナは read-only rootfs（一時ワークスペースのみ書き込み可）、Security Group は ingress ゼロ、egress は NAT Gateway 経由のモデル API のみ。さらに app-server の承認リクエスト（コマンド実行許可）はアプリレイヤーで全拒否ポリシーに固定し、コンテナ・ネットワーク・プロトコルの 3 層で暴走を封じる。

4. シークレットの用途別分離と最小権限 — Codex API キー / GitHub App 秘密鍵 / Webhook シークレット / DB 認証情報を別シークレットに分け、API タスクロールは Webhook + GitHub 鍵のみ、ワーカータスクロールは Codex キーのみ取得可能にした。API サーバーが乗っ取られても Codex キーは漏れない（逆も同様）。

5. プロトコル変化をアダプタ層とバージョンピンで局所化 — app-server プロトコルは公式クライアント優先で進化し破壊的変更があり得るため、Codex CLI をコンテナイメージにバージョンピン留めして同梱し、JSON-RPC の呼び出しはワーカー内のアダプタ層に閉じ込める。CLI 更新はイメージビルド + プロトコル疎通スモークテストを通してからロールアウトする。

コスト最適化のポイント

最大の固定費はワーカーの常駐分。レビュー頻度が低いうちは Prod でもワーカーを 1 タスクに絞り、SQS キュー深度をトリガーに ECS Service をスケールさせると $150 前後まで圧縮できる。夜間・休日にワーカーとDev 環境全体をスケジュール停止すれば Fargate 分はさらに半減する。NAT Gateway はモデル API への egress 専用なので、転送量が伸びたら VPC エンドポイント化できる AWS 内通信（S3 / Secrets Manager / SQS）を Gateway/Interface エンドポイントに逃がして NAT 転送課金を削る。

学習ポイント

  • ローカル CLI エージェントの Web サービス組み込みは「子プロセス + stdio」が基本形 — Codex app-server のように stdio で JSON-RPC を話すツールは、デスクトップ専用に見えてもバックエンドで spawn すれば Web サービスに組み込める。「プロトコルのトランスポート（stdio / WebSocket）」と「ホスト環境（ローカル / サーバー）」を分けて考えると、ツールの適用範囲を正しく見積もれる。
  • 使い捨て実行モデルはステートフル問題の万能な逃げ道 — 常駐プロセスの状態管理が難しいコンポーネントは、「リクエストごとに生成して破棄する」設計にできないかをまず検討する。スケール・隔離・リーク対策が一挙に単純化する代わりに起動オーバーヘッドを払うトレードオフで、実行時間が秒〜分オーダーの処理なら通常ペイする。
  • 同期 API と長時間処理の境界はキューで物理的に固定する — Webhook 応答期限（秒）と処理時間（分）のオーダーが違う時点で非同期化は必須。SQS の VisibilityTimeout・maxReceiveCount・DLQ をタイムアウト / リトライ / 隔離のポリシーとして使うと、リトライ制御をアプリコードからインフラ設定に外出しできる。
  • 信頼できないコード実行は「層で重ねて」封じる — AI エージェントによるコード解析・実行系は、単一のサンドボックス機構に頼らず、コンテナ（read-only rootfs）・ネットワーク（egress 限定 SG）・プロトコル（承認全拒否）の独立した層で防御する。1 層が破られても被害が波及しない defense-in-depth は、プラグイン実行基盤や CI ランナー設計にも共通する原則。
  • 外部プロトコル依存はアダプタ層 + バージョンピンで隔離する — 自分が管理できない進化速度を持つ依存（今回は app-server プロトコル）は、呼び出しコードを 1 モジュールに閉じ込め、依存バージョンを固定し、更新時はスモークテストを通す。「壊れる前提で、壊れる場所を 1 箇所にする」ことがサードパーティ統合の保守性を決める。
