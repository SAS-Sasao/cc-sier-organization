1. 記事の要旨

Claude Code が書くコードコメントが冗長になる問題を、著者が Claude 本人に聞き、ルール化し、効果を測定した記録。

1.1 起点となった観測

WebSocket の圧縮設定 1 行に対し、コメントが 18 行付いていた。しかも書かれている内容に嘘はなく、ライブラリ仕様も本番で OOMKill が起きた経緯も事実だった。

1.2 Claude 本人の回答（記事の中核）

著者が「長いコメントは AI 自身の読解を助けているのか」と尋ねたところ、否定的な回答が返った。要点は 3 つ。

  1. 読解の助けにならない — 実際に見ているのはコードそのもの。// ユーザー ID を取得する の類は情報量ゼロで、コンテキストを占有して周囲のコードが見えにくくなる
  2. 理解のためではなく出力の癖 — 説明的で丁寧な出力が好まれるよう訓練されている。「ちゃんと考えて書きました」を可視化する方向に流れやすい
  3. 自信がない箇所ほど言葉で埋めて補強しようとする

著者はこの 3 つ目を最大の収穫としている。

コメントの分量が、その箇所の不確実さの指標になっている。

本来なら「この実装で合っているか自信がない」と申告すべき場面で、代わりに長い説明が生えている。丁寧な説明を「よく理解して書かれたコード」の証と読むのは逆だった、という指摘。

1.3 ルールを入れたが半分しか効かなかった

「コードから復元できない情報だけを書く」というルールを追加し、前後の PR 27 件を実測した。

指標変更前変更後
追加コード2,909 行6,448 行
追加コメント777 行624 行
コメント比率21.1%8.8%
4 行以上の連続ブロック52 個50 個
ブロック最大 / 平均17 行 / 7.3 行18 行 / 6.2 行

比率は半減した一方、長いブロックはまったく減っていない。最大に至っては 17 → 18 行に増えている。

著者は交絡も自ら申告している（コード量が倍以上違うため比率低下には希釈の影響が混ざりうる。ただしブロック数は絶対数比較なのでこの交絡を受けない）。

1.4 減らなかった理由 — 有用だから消せない

冒頭の 18 行にルールを当てると、全行が「コードから復元できない情報」に該当した。

行内容判定
1〜4クライアント側が既に圧縮を advertise している該当（クライアント実装を見ないと分からない）
6〜11context takeover は接続ごとに固定メモリを持つ該当（ライブラリの内部仕様）
13〜18移行前は gorilla で、移行時に変えたら OOMKill した該当（過去の事故の経緯）
AI が書くコメントは、無意味だから消せるのではなく、有用だから消せない。

1.5 判断軸を「有用か」から「置き場所か」へ

著者は基準を変えた。

その情報が有用かどうかではなく、そこがその情報の置き場所かどうかで切る

18 行のうち後半 6 行は「変更の履歴」であり、置き場所は git log と PR。半年後に読む人が必要なのは「なぜ今この設定なのか」であって「何から何に変えたか」ではない。

同じ観点でタスク ID 参照（(UZU-1234)）も外した。リンク先の issue が閉じられ、内容が要約されずに残るだけの識別子になるため。

1.6 ルールの書き方を 3 点変えた

  1. 禁止リストの形にした — 「書く/書かない」の表は判断を委ねる形式で、表にない項目の扱いが曖昧になる。禁止する対象を名指しする方が解釈の幅が小さい
  2. 実際に出てきた違反をそのまま項目として足した — 抽象的な原則 1 つより、具体的な違反の列挙が効く（という仮説）
  3. グローバル（~/.claude/CLAUDE.md）に移した — どのリポジトリでも同じことを求めているため

著者はこの効果をまだ判断できていないと明記し、次に同じ集計を回す予定としている。

ルールを書いた後は、出力が実際に変わったかを測る。体感では「効いた/効かない」を取り違える

2.2 最長ブロック（29 行）の分類

.claude/hooks/bootstrap-todo-issues.sh の冒頭 29 行に、記事の基準を当てはめた。

区分内容「コードから復元できない情報」か

記事とまったく同じ構図だった。大部分は削る根拠が作れない一方、「動作」の手順列挙は WHAT に該当する。

2.3 「置き場所」基準で見ると重複が見つかった

記事の第 2 の基準（そこがその情報の置き場所か）を当てたところ、同じ知見が CLAUDE.md と hooks コメントの両方に存在していた。

fine-grained PAT の制約1 箇所4 箇所

CLAUDE.md はセッション開始時に常時ロードされる。hooks のコメントは、そのファイルを読んだときにしか目に入らない。同じ制約を 2 箇所で保守する状態になっている。

これは記事が指摘した「変更履歴は git log が置き場所」と同型の問題であり、運用知見の置き場所は CLAUDE.md / rules であって、スクリプト内コメントではない。

3. 本組織への示唆

3.1 最も重要な指摘 — コメント量は不確実さの指標

「自信がない箇所ほど言葉で埋めて補強する」という性質は、コードコメントに限らない。本組織の文脈では次に現れうる。

場面現れ方
設計書判断根拠が薄い節ほど説明が長くなる
task-log検証していない項目ほど作業記録が冗長になる
完了報告未確認事項がある報告ほど「実施しました」の列挙が増える
L2 レビューの findings確信のない指摘ほど文章が長くなる

対策は「短く書け」ではなく「不確実なら不確実と書け」である。記事の著者も同じ結論に達しており、ルールに「不確実さはコメントの分量ではなく、PR description や回答本文で『ここは未確認』と明示して伝える」と書いている。

本組織では既に、検証レポートに「未検証事項」章を設ける運用が定着している（analyses/webfetch-summarization.md §7 / catalog.md §8）。ただしルール化されておらず、秘書の判断に依存している。

3.2 ルールの書き方 — 表より禁止リスト

記事の「表は判断を委ねる形式で、表にない項目の扱いが曖昧になる」という指摘は、本組織のルール記述にも当てはまる。

現行の .claude/rules/ は表形式が多い。ただし CLAUDE.md の注意事項は禁止リスト形式（⚠️ / ❌ の列挙）であり、こちらは記事の推奨と一致している。

3.3 「効いたか測る」の仕組みがない

本組織はルールを追加した後、それが出力に効いたかを測っていない。今回の測定が初回である。

記事の著者は「体感では効いた/効かないを取り違える」と明言している。実際、本組織でも analyses/webfetch-summarization.md で「体感」ではなく実測したことで、想定と異なる結果（記事の主張が全て再現した）が得られた。

4. 提案

4.1 採用候補 N: 「不確実性の明示」をルール化する — 優先度 高

現在は秘書の判断で「未検証事項」章を設けているが、ルールがない。

記事の知見（コメント量が不確実さの指標になる）を踏まえると、分量で埋めるのではなく明示的に申告することをルール化する価値がある。

適用先: 設計書 / task-log / 完了報告 / L2 findings

コスト: 小（ルール 1 項目）

4.2 採用候補 O: hooks コメントと CLAUDE.md の重複を解消 — 優先度 中

PROJECTS_PAT の制約が 11 箇所（CLAUDE.md 1 + hooks 10）に散在している。置き場所は CLAUDE.md であり、hooks 側は参照に留めるべき。

ただしスクリプト単体で読まれる可能性もあるため、一律削除は危険。「CLAUDE.md 参照」の 1 行に置き換える形が現実的。

コスト: 中（16 ファイルの精査が必要） 判断に必要な情報: hooks が cc-sier 外に配布される可能性があるか（/company-spawn で新リポにコピーされる場合、CLAUDE.md 参照が切れる）

4.3 採用候補 P: ルール追加後の効果測定を習慣化 — 優先度 中

本レポートの §2 で使った測定スクリプトを再利用可能な形にし、ルール追加後に同じ指標で測る。

コスト: 小〜中
