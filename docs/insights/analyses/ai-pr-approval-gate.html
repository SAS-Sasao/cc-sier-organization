0. 結論（先に書く）

記事は「人間レビューを減らす」話ですが、本組織にとっては 逆向きに効きます。

実測の結果、本組織の直近 60 件の PR はすべてレビュー 0 件でした。approve 率でいえば既に 100% です。記事が 1 割から 58% へ引き上げた対象を、本組織は最初から全部通しています。

したがって採るべきは「AI に承認させる仕組み」ではなく、記事の裏側にある「人間が見るべき変更の定義」です。本組織にはこれが存在しません。

さらに深刻な数字が出ました。

統制系の変更（hooks / rules / CLAUDE.md / skills）を含む PR は 60 件中 10 件（16.7%）。そのすべてが task-log を持たず、L0/L1/L2 の 3 層レビューを一度も通っていません。

本組織は成果物（図・ダイジェスト・シート）には 3 層の審査を敷き、審査の仕組みそのものを変える PR は素通しにしています。 記事が人間レビュー必須の第 1 項目に挙げる control_plane_change が、最も無防備な場所になっています。

1. 記事の解説

1.1 出発点は「測ったこと」

著者はまず 直近 3 週間に人間レビューへ回った PR 75 件を全数分析しました。

実測値
無言の approve か LGTM のみ60%
実質的な指摘が付いた約 1 割
その指摘の大半の出所人間ではなく、以前から稼働している AI レビュアー

著者はこの分析の限界（チャットや口頭での指摘は観測できない）を自分で書き添えたうえで、「人間レビューのプロセスは、リードタイムを長くしているほどの効果は生んでいない」と結論しています。

主張の前に数字がある構成です。本レポートが実測を重視するのも同じ理由です。

1.2 方針 — 全部やめるのではなく、線を引く

数字だけを見て AI に置き換えるのは性急、と著者自身が留保しています。そのうえで、

「本当に品質担保すべき・オーナーシップを持つべき」場所を定義し、それらを含む変更は必ず人間レビューに回すが、そうでないものは AI レビューで OK にする

という方針を採ります。

補足として、PR レビューには「誰かのコードを自分たちのコードにする」という中長期の意味がある、という反論を自分で挙げ、それに同意しつつ「AI コーディングの普及で、一行一行までみんながオーナーシップを持つのは現実的に難しくなった」と応じています。

1.3 ワークフロー（4 段階）

PR 作成
  ↓
① 決定的ゲート判定（特定ファイルの変更 → 人間レビュー必須）
  ↓
② AI（LLM）レビュー + 審査 → 判定
  ↓
③ ラベルと sticky コメントへの反映
  ↓
④ 承認なら bot が GitHub 上で Approve

マージボタンを押すのは人間のままです。自動マージまではしていません。

1.4 中核 — 「AI の意見」と「人間が見るべきか」を独立させる

この記事で最も応用が効くのがここです。

軸値
AI の意見approve / pending / need fix（3 値）
人間レビューの要否required / optional（2 値）

ai-review:approved かつ human-review:optional のときだけ PR が approved になります。

2 軸を独立させると「AI はコードに問題がないと言っている。ただし人間も見てほしい」という状態が表現できます。1 軸だとこれが潰れます。

sticky コメントの実例:

AIの意見   : ✅ Approve — must-fix の指摘はありません
人間レビュー : 🙋 必要（理由: 不可逆操作）

1.5 決定的ゲートに LLM を使わない理由

決済・売上に関わるコードは、監査法人との取り決めで人間レビュー必須。この判定は ファイルパスのマッチングとモデル参照検知で行い、LLM を使いません。

理由が明快です。

監査では「なぜこの PR が人間レビューに回ったのか」を後から説明し、同じ入力で同じ結果を再現できるほうがよく、実行のたびに判断が揺れうる LLM はこの要件を満たさない

再現性が要るところに LLM を置かない、という線引きです。本組織の L0（機械レビュー）と同じ思想で、既に持っている考え方でもあります。

なお、このゲートに該当した PR も AI コードレビュー自体は実行されます（人間レビューが必須になるだけ）。

1.6 LLM が判定する 8 項目

トリガー説明
統制系変更（control_plane_change）レビュー・審査・CI など統制の仕組みそのものに触れる変更
不可逆操作（irreversible_operation）データ削除や外部送信など、実行後に取り消せない操作
セキュリティ境界（security_boundary_change）認証・認可・権限チェックなど守りの境界の変更
個人情報フロー（personal_data_flow_change）個人情報の取得・保存・出力経路の変更
外部契約（external_contract_change）外部 API やスキーマなど外部との取り決めの変更
新規パターン導入（architectural_precedent）コードベースに前例のない実装パターンの持ち込み
高リスク値計算（high_stakes_calculation）金額など誤りの影響が大きい値の計算の変更
実行時ハザード（runtime_hazard）重いクエリやジョブなど実行時に事故を起こしうる変更

著者はこの項目群を Claude Fable 5 に提案させ、ほぼそのまま採用したと明記しています。

1.7 最も重要な教訓 — あいまいにすると AI は安全側に倒す

この項目を定義する前は「ロジックの変更があれば人間レビューに回す」でした。結果、ほとんどの PR が引っかかり、人間レビュー必須に回っていました。

基本的に、あいまいにしておくと AI は安全側に倒しがちなので、きちんと条件を決めて、それに当てはまらなければ OK（人間レビュー不要）にする、という形式にしています。

さらに、これを運用に落とすための一文があります。

こういう安全側に倒さない判断は、責任者が良いと言わないとなかなかそうなりづらいので、そういう判断・意思決定は開発責任者として意識的にするようにしています。

「緩める判断は権限を持つ人が明示的に下す」という指摘です。これは仕組みの話ではなく運用の話で、本組織にそのまま当てはまります。

1.8 pending — 承認も却下もしない第三の状態

PR の diff の外の事実に、正しさが依存している場合があります。例として、後方互換性のない変更に対して「古い仕様に依存しているクライアントがないか」の確認が挙げられています。

人間のレビュアーはこの場面で、承認も却下もせず質問します。単に承認したのでは品質担保にならず、diff の外の事実次第では、そのままでよいかもしれないからです。

この振る舞いを AI にも持たせたのが pending です。審査エージェントが承認を保留して作者に質問し、回答をもとに再審査して承認まで進めます。

実装上の細かい知見が 2 つ、どちらも実運用でしか出てこない類のものです。

  • GitHub は既存コメントの編集では通知が飛ばない。そのため sticky コメントの更新とは別に、@メンション付きの新規コメントを 1 件投稿している
  • すべてのコメントでフルレビューを起動するとコストが跳ねるため、軽量モデル（claude-haiku-4-5）で「このコメントは質問への回答か」をプリフィルタしている

1.9 成果と、著者自身の留保

指標値
AI が approve した PR の割合58%（導入前は約 1 割）
運用期間約 2 週間（速報値）

著者は「体感としても適正値」「もう少し（70% くらい）高くてもよい」としつつ、むやみに高くすべきものでもないと書いています。

そして重要な留保を残しています。

本当に approve されるべきものに approve されているか（偽陽性/偽陰性の率）は引き続き見ていくべき

数字が出た後も判定精度の検証を続けるという姿勢です。本組織の L2 にこの検証材料が残っていないことが、後述の実測で分かりました。

2.5 L2 の判定精度は検証できるか（記事 §6 の留保に対応）

記事は「偽陽性/偽陰性の率は引き続き見ていくべき」と書いています。本組織で同じ検証ができるか測りました。

指標実測

平均0.963
最小値0.88
閾値 0.85 を下回るもの0 件
retry 発生率L0 4.4% / L1 5.0% / L2 2.8%（4 件）

L2 の retry が 4 件発生しているのに、記録された composite は 1 件も 0.85 を下回っていません。 つまり task-log には修正後の最終スコアだけが残り、初回 fail の値が保存されていません。

結果として、L2 が正しく落としたのか、落とすべきものを通したのかを後から検証する材料がありません。

なお、この数字だけでは「L2 が甘い」とは断定できません。retry で実際に直っている可能性の方が高いです。言えるのは「検証できない」ことだけです。

2.6 「あいまいだと AI は安全側に倒す」は本組織で起きているか

記事の最重要教訓ですが、本組織の L2 では起きていません。

L2 は 6 軸 + 致命軸 + 必須セクションで条件が具体的に決まっており、retry 率は 2.8% と低い水準です。記事の「ロジック変更があれば人間レビュー」のような広すぎる条件にはなっていません。

本組織の問題は逆で、条件が具体的すぎて条件外のリスクを見逃すことです。実例が Issue #724 / #728 / #729（L2 pass 後に設計不整合が発覚）で、これは既に候補 S として記録済みです。

候補 X: 「人間が見るべき変更」の定義を作る — 優先度 高

実装は 2 段構えにします。記事の設計をそのまま踏襲します。

  1. 決定的ゲート（LLM を使わない） — ファイルパスのマッチだけで判定する。.claude/hooks/ .claude/rules/ CLAUDE.md .github/workflows/ を触る PR は無条件で人間レビュー必須。再現性が要るので LLM を置かない（記事 §1.5）
  2. LLM レイヤー — 上記に当てはまらない PR について、残り 4〜5 項目を判定する

まず 1 だけでも意味があります。 パスのマッチは hook かワークフローで書け、判定が揺れません。

コスト: 小〜中（決定的ゲートのみなら小）

判断に必要な追加情報: 現状 auto-merge は gh pr merge --squash を Skill が直接叩いています。ゲートをどこに置くか（PR 作成時の hook か、GitHub Actions か）は未検討です。

候補 Y: 判定を 2 軸に分ける（成果物の品質 / 人間レビューの要否）— 優先度 中

本組織は現在 1 軸です。l2_composite ≥ 0.85 で pass → auto-merge。

この設計では「L2 は通ったが人間も見るべき」を表現できません。実際に、Issue #724 / #728 / #729 は L2 を通過した後に設計不整合が発覚しています。

記事の 2 軸をそのまま持ち込むと:

軸値本組織での意味
L2 の判定pass / pending / fail成果物そのものの品質
人間レビューの要否required / optional候補 X のゲートが決める

両方が揃ったときだけ auto-merge します。

候補 S（「緑 ≠ 実用可」の明文化）と候補 B（verification-pending の追加）は、この 2 軸化の一部として実装できます。 3 つを別々に扱うより整合します。

コスト: 中（task-log スキーマと Skill の Phase 7 に手を入れる）

候補 Z: pending（承認も却下もしない状態）— 優先度 中

記事の pending は「diff の外の事実に正しさが依存する」場合の状態です。

本組織の L2 は pass / fail の 2 値で、この状態がありません。結果として、未確認事項があっても pass か fail のどちらかに丸められます。

本組織で pending が要る典型:

  • 設計書が他の設計書と整合しているか（その文書の外の事実）— #724/#728/#729 がまさにこれ
  • 生成した数値が実データで再現するか — NFR-05 の実測
  • 参照先のファイルが実在するか

候補 B / S / Y と同じ問題を指しています。 別々の候補として持つより、「未確認を未確認のまま扱える状態を作る」として統合すべきです。

コスト: 中
