## 0. 結論（先に書く）

記事は「**人間レビューを減らす**」話ですが、本組織にとっては **逆向きに効きます**。

実測の結果、**本組織の直近 60 件の PR はすべてレビュー 0 件**でした。approve 率でいえば既に 100% です。記事が 1 割から 58% へ引き上げた対象を、本組織は最初から全部通しています。

したがって採るべきは「AI に承認させる仕組み」ではなく、記事の裏側にある「**人間が見るべき変更の定義**」です。本組織にはこれが存在しません。

さらに深刻な数字が出ました。

> **統制系の変更（hooks / rules / CLAUDE.md / skills）を含む PR は 60 件中 10 件（16.7%）。そのすべてが task-log を持たず、L0/L1/L2 の 3 層レビューを一度も通っていません。**

本組織は**成果物（図・ダイジェスト・シート）には 3 層の審査を敷き、審査の仕組みそのものを変える PR は素通しにしています。** 記事が人間レビュー必須の第 1 項目に挙げる `control_plane_change` が、最も無防備な場所になっています。

## 1. 記事の解説

### 1.1 出発点は「測ったこと」

著者はまず **直近 3 週間に人間レビューへ回った PR 75 件を全数分析**しました。

| 実測 | 値 |
|---|---|
| 無言の approve か LGTM のみ | **60%** |
| 実質的な指摘が付いた | **約 1 割** |
| その指摘の大半の出所 | **人間ではなく、以前から稼働している AI レビュアー** |

著者はこの分析の限界（チャットや口頭での指摘は観測できない）を自分で書き添えたうえで、「人間レビューのプロセスは、リードタイムを長くしているほどの効果は生んでいない」と結論しています。

**主張の前に数字がある**構成です。本レポートが実測を重視するのも同じ理由です。

### 1.2 方針 — 全部やめるのではなく、線を引く

数字だけを見て AI に置き換えるのは性急、と著者自身が留保しています。そのうえで、

> 「本当に品質担保すべき・オーナーシップを持つべき」場所を定義し、それらを含む変更は必ず人間レビューに回すが、そうでないものは AI レビューで OK にする

という方針を採ります。

補足として、PR レビューには「誰かのコードを自分たちのコードにする」という中長期の意味がある、という反論を自分で挙げ、それに同意しつつ「AI コーディングの普及で、一行一行までみんながオーナーシップを持つのは現実的に難しくなった」と応じています。

### 1.3 ワークフロー（4 段階）

```
PR 作成
  ↓
① 決定的ゲート判定（特定ファイルの変更 → 人間レビュー必須）
  ↓
② AI（LLM）レビュー + 審査 → 判定
  ↓
③ ラベルと sticky コメントへの反映
  ↓
④ 承認なら bot が GitHub 上で Approve
```

**マージボタンを押すのは人間のまま**です。自動マージまではしていません。

### 1.4 中核 — 「AI の意見」と「人間が見るべきか」を独立させる

この記事で最も応用が効くのがここです。

| 軸 | 値 |
|---|---|
| **AI の意見** | approve / pending / need fix（**3 値**） |
| **人間レビューの要否** | required / optional（**2 値**） |

`ai-review:approved` **かつ** `human-review:optional` のときだけ PR が approved になります。

2 軸を独立させると「**AI はコードに問題がないと言っている。ただし人間も見てほしい**」という状態が表現できます。1 軸だとこれが潰れます。

sticky コメントの実例:

```
AIの意見   : ✅ Approve — must-fix の指摘はありません
人間レビュー : 🙋 必要（理由: 不可逆操作）
```

### 1.5 決定的ゲートに LLM を使わない理由

決済・売上に関わるコードは、監査法人との取り決めで人間レビュー必須。この判定は **ファイルパスのマッチングとモデル参照検知**で行い、LLM を使いません。

理由が明快です。

> 監査では「なぜこの PR が人間レビューに回ったのか」を後から説明し、**同じ入力で同じ結果を再現できる**ほうがよく、実行のたびに判断が揺れうる LLM はこの要件を満たさない

**再現性が要るところに LLM を置かない**、という線引きです。本組織の L0（機械レビュー）と同じ思想で、既に持っている考え方でもあります。

なお、このゲートに該当した PR も **AI コードレビュー自体は実行されます**（人間レビューが必須になるだけ）。

### 1.6 LLM が判定する 8 項目

| トリガー | 説明 |
|---|---|
| 統制系変更（control_plane_change） | レビュー・審査・CI など**統制の仕組みそのもの**に触れる変更 |
| 不可逆操作（irreversible_operation） | データ削除や外部送信など、実行後に取り消せない操作 |
| セキュリティ境界（security_boundary_change） | 認証・認可・権限チェックなど守りの境界の変更 |
| 個人情報フロー（personal_data_flow_change） | 個人情報の取得・保存・出力経路の変更 |
| 外部契約（external_contract_change） | 外部 API やスキーマなど外部との取り決めの変更 |
| 新規パターン導入（architectural_precedent） | コードベースに前例のない実装パターンの持ち込み |
| 高リスク値計算（high_stakes_calculation） | 金額など誤りの影響が大きい値の計算の変更 |
| 実行時ハザード（runtime_hazard） | 重いクエリやジョブなど実行時に事故を起こしうる変更 |

著者はこの項目群を Claude Fable 5 に提案させ、ほぼそのまま採用したと明記しています。

### 1.7 最も重要な教訓 — あいまいにすると AI は安全側に倒す

この項目を定義する前は「**ロジックの変更があれば人間レビューに回す**」でした。結果、**ほとんどの PR が引っかかり**、人間レビュー必須に回っていました。

> 基本的に、**あいまいにしておくと AI は安全側に倒しがち**なので、きちんと条件を決めて、それに当てはまらなければ OK（人間レビュー不要）にする、という形式にしています。

さらに、これを運用に落とすための一文があります。

> こういう**安全側に倒さない判断は、責任者が良いと言わないとなかなかそうなりづらい**ので、そういう判断・意思決定は開発責任者として意識的にするようにしています。

**「緩める判断は権限を持つ人が明示的に下す」**という指摘です。これは仕組みの話ではなく運用の話で、本組織にそのまま当てはまります。

### 1.8 pending — 承認も却下もしない第三の状態

**PR の diff の外の事実に、正しさが依存している**場合があります。例として、後方互換性のない変更に対して「古い仕様に依存しているクライアントがないか」の確認が挙げられています。

人間のレビュアーはこの場面で、承認も却下もせず**質問**します。単に承認したのでは品質担保にならず、diff の外の事実次第では、そのままでよいかもしれないからです。

この振る舞いを AI にも持たせたのが `pending` です。審査エージェントが承認を保留して作者に質問し、回答をもとに再審査して承認まで進めます。

実装上の細かい知見が 2 つ、どちらも実運用でしか出てこない類のものです。

- **GitHub は既存コメントの編集では通知が飛ばない**。そのため sticky コメントの更新とは別に、**@メンション付きの新規コメントを 1 件投稿**している
- すべてのコメントでフルレビューを起動するとコストが跳ねるため、**軽量モデル（claude-haiku-4-5）で「このコメントは質問への回答か」をプリフィルタ**している

### 1.9 成果と、著者自身の留保

| 指標 | 値 |
|---|---|
| AI が approve した PR の割合 | **58%**（導入前は約 1 割） |
| 運用期間 | 約 2 週間（**速報値**） |

著者は「体感としても適正値」「もう少し（70% くらい）高くてもよい」としつつ、**むやみに高くすべきものでもない**と書いています。

そして重要な留保を残しています。

> 本当に approve されるべきものに approve されているか（**偽陽性/偽陰性の率**）は引き続き見ていくべき

**数字が出た後も判定精度の検証を続ける**という姿勢です。本組織の L2 にこの検証材料が残っていないことが、後述の実測で分かりました。

## 2. 自組織での実測

記事の主張ごとに本組織を測りました。測定日は 2026-08-09、母数は直近 60 件の merged PR です。

### 2.1 人間レビューの実態（記事 §1 に対応）

記事は 75 件を全数分析して「60% が無言 approve」でした。本組織を同じ方法で測ります。

```bash
gh pr list --state merged --limit 60 --json number,reviews \
  --jq '.[] | "\(.number)\t\(.reviews|length)"'
```

| 指標 | SHE 社（記事） | **本組織** |
|---|---|---|
| 母数 | 75 件 | **60 件** |
| レビューが 1 件でも付いた PR | 100%（人間レビューに回った PR が母数） | **0 件（0%）** |
| 実質的な指摘 | 約 1 割 | **0 件** |
| approve 率 | 1 割 → 58% | **実質 100%** |

**直近 60 件すべてがレビュー 0 件でマージされています。** author の内訳は SAS-Sasao 35 件 / github-actions 25 件。

記事の課題（approve 率が低くボトルネック）は本組織に存在しません。**逆に、止まる場所が一つもありません。**

### 2.4 AI が自分のルールを書き換えている量

nightly workflow が `CLAUDE.md` と `.claude/rules/` を自動更新した PR は **全期間で 12 件**（仕組み構築の PR 3 件を除く）。その差分を集計しました。

| | 行数 |
|---|---|
| 追加 | **+49** |
| 削除 | **-5** |
| 純増 | **+44** |

**追記が削除の約 10 倍**です。12 回とも人間のレビューなしでマージされています。

現在の規模:

| 対象 | 実測 |
|---|---|
| `CLAUDE.md` | 9,403 字 |
| `CLAUDE.md` + `.claude/rules/*.md` | 1,195 行 |
| 注意事項（⚠️ / ❌）の項目数 | **28 項目** |

**AI が自分を縛るルールを、一方向に増やし続けています。** 候補 Q（CLAUDE.md / rules の削減）が長く未着手なのは、**増やす仕組みだけがあって減らす判断をする場所がない**からだと、この数字は示しています。

これは記事 §1.7 の裏返しです。nightly は「気づいたことを追記する」方向にしか動かず、削る判断をしません。**安全側に倒し続けています。**

### 2.5 L2 の判定精度は検証できるか（記事 §6 の留保に対応）

記事は「偽陽性/偽陰性の率は引き続き見ていくべき」と書いています。本組織で同じ検証ができるか測りました。

| 指標 | 実測 |
|---|---|
| `l2_composite` が記録された task-log | 109 件 |
| 平均 | 0.963 |
| **最小値** | **0.88** |
| **閾値 0.85 を下回るもの** | **0 件** |
| retry 発生率 | L0 4.4% / L1 5.0% / **L2 2.8%（4 件）** |

**L2 の retry が 4 件発生しているのに、記録された composite は 1 件も 0.85 を下回っていません。** つまり task-log には**修正後の最終スコアだけが残り、初回 fail の値が保存されていません**。

結果として、**L2 が正しく落としたのか、落とすべきものを通したのかを後から検証する材料がありません。**

なお、この数字だけでは「L2 が甘い」とは断定できません。retry で実際に直っている可能性の方が高いです。**言えるのは「検証できない」ことだけ**です。

### 2.6 「あいまいだと AI は安全側に倒す」は本組織で起きているか

記事の最重要教訓ですが、**本組織の L2 では起きていません**。

L2 は 6 軸 + 致命軸 + 必須セクションで条件が具体的に決まっており、retry 率は 2.8% と低い水準です。記事の「ロジック変更があれば人間レビュー」のような広すぎる条件にはなっていません。

本組織の問題は逆で、**条件が具体的すぎて条件外のリスクを見逃す**ことです。実例が Issue #724 / #728 / #729（L2 pass 後に設計不整合が発覚）で、これは既に候補 S として記録済みです。

### 2.7 個人情報フロー（記事の 8 項目のうち 1 つ）

記事の `personal_data_flow_change` に該当するものが本組織に実在するか確認しました。

| 指標 | 実測 |
|---|---|
| リポジトリの公開状態 | **PUBLIC** |
| `.conversation-log/` のファイル数 | 15 |
| サイズ | 4.3 MB |
| **記録されている人間の発言数** | **3,163 件** |
| マスキング処理 | **`.claude/hooks/capture-conversation.sh` に実装あり**（顧客名 → `[CLIENT-NN]` / 人名 → `[PERSON-NN]`） |

**マスキングは実装されていました。** frontmatter に `masked: true` が付与されます。

ただし、この仕組みは**マスタから構築した辞書に載っている固有名詞だけを置換**します。辞書にない名前は素通りします。`masked: true` は「マスキング処理を通した」という意味であって、「機密が残っていない」保証ではありません。

**辞書の網羅性は測っていません**（マスタの顧客名・担当者名の登録件数と、実際にログに現れる固有名詞の照合は未実施）。ここは本レポートの範囲外とします。

## 3. 採用候補

### 候補 X: 「人間が見るべき変更」の定義を作る — 優先度 **高**

**根拠は理論ではなく実測です。** 統制系変更を含む PR が 10/60（16.7%）あり、そのすべてが 3 層レビューも人間レビューも通っていません。うち #723 は品質ゲート、#714 は Case Bank という、**審査と学習の仕組みそのもの**でした。

記事の 8 項目を本組織にマッピングすると次のようになります。

| 記事の項目 | 本組織での該当 | 実在するか |
|---|---|---|
| 統制系変更 | `.claude/hooks/` `.claude/rules/` `CLAUDE.md` `**/skills/` `.github/workflows/` | **✅ 10/60 件** |
| 不可逆操作 | `git reset --hard` / main 直コミット / ファイル削除 | ✅ 実例あり（2026-08-08 に無承認実行、記録済み） |
| セキュリティ境界 | workflow の `permissions:` / PAT / secrets | 未測定 |
| 個人情報フロー | `.conversation-log/`（public リポジトリに 3,163 発言） | ✅ 実在。マスキングあり、辞書の網羅性は未測定 |
| 外部契約 | `.mcp.json` のバージョンピン / GitHub API | ✅ 実例あり（#569/#570 で PyPI yank） |
| 新規パターン導入 | 新規 Skill / 新規 hook の追加 | ✅ #757 が該当 |
| 高リスク値計算 | `retail-stats-tracker` の数値抽出（NFR-05） | ✅ 実例あり（正規表現の 30 倍誤差） |
| 実行時ハザード | cron workflow / 巡回処理 | 未測定 |

**8 項目中 6 項目が本組織に実在します。** 記事の項目群は流用可能です。

実装は 2 段構えにします。記事の設計をそのまま踏襲します。

1. **決定的ゲート（LLM を使わない）** — ファイルパスのマッチだけで判定する。`.claude/hooks/` `.claude/rules/` `CLAUDE.md` `.github/workflows/` を触る PR は無条件で人間レビュー必須。**再現性が要るので LLM を置かない**（記事 §1.5）
2. **LLM レイヤー** — 上記に当てはまらない PR について、残り 4〜5 項目を判定する

**まず 1 だけでも意味があります。** パスのマッチは hook かワークフローで書け、判定が揺れません。

**コスト**: 小〜中（決定的ゲートのみなら小）

**判断に必要な追加情報**: 現状 auto-merge は `gh pr merge --squash` を Skill が直接叩いています。ゲートをどこに置くか（PR 作成時の hook か、GitHub Actions か）は**未検討**です。

### 候補 Y: 判定を 2 軸に分ける（成果物の品質 / 人間レビューの要否）— 優先度 **中**

本組織は現在 **1 軸**です。`l2_composite ≥ 0.85` で pass → auto-merge。

この設計では「**L2 は通ったが人間も見るべき**」を表現できません。実際に、Issue #724 / #728 / #729 は L2 を通過した後に設計不整合が発覚しています。

記事の 2 軸をそのまま持ち込むと:

| 軸 | 値 | 本組織での意味 |
|---|---|---|
| L2 の判定 | pass / **pending** / fail | 成果物そのものの品質 |
| 人間レビューの要否 | required / optional | 候補 X のゲートが決める |

両方が揃ったときだけ auto-merge します。

**候補 S（「緑 ≠ 実用可」の明文化）と候補 B（`verification-pending` の追加）は、この 2 軸化の一部として実装できます。** 3 つを別々に扱うより整合します。

**コスト**: 中（task-log スキーマと Skill の Phase 7 に手を入れる）

### 候補 Z: `pending`（承認も却下もしない状態）— 優先度 **中**

記事の `pending` は「**diff の外の事実に正しさが依存する**」場合の状態です。

本組織の L2 は pass / fail の 2 値で、この状態がありません。結果として、**未確認事項があっても pass か fail のどちらかに丸められます**。

本組織で `pending` が要る典型:

- 設計書が他の設計書と整合しているか（**その文書の外の事実**）— #724/#728/#729 がまさにこれ
- 生成した数値が実データで再現するか — NFR-05 の実測
- 参照先のファイルが実在するか

**候補 B / S / Y と同じ問題を指しています。** 別々の候補として持つより、**「未確認を未確認のまま扱える状態を作る」**として統合すべきです。

**コスト**: 中

**注意**: 記事の pending は「作者に質問して回答を待つ」対話ループを含みます。本組織は作者も AI なので、そのままは持ち込めません。**保留の状態を持つところまで**が現実的です。

### 候補 AA: nightly の CLAUDE.md 自動更新に人間の承認を入れる — 優先度 **高**

**追記 +49 行 / 削除 -5 行**。12 回とも人間のレビューなしでマージされています。

これは候補 X の一部ですが、**単独で切り出す価値があります**。理由は 2 つ。

1. **AI が自分を縛るルールを自分で書き換えている**。記事の `control_plane_change` の最たるもの
2. **候補 Q（CLAUDE.md 削減）が進まない原因が、この非対称性で説明できる**。増やす仕組みは自動で回り、減らす判断をする場所がない

対処は 2 つ考えられます。

| 案 | 内容 | 評価 |
|---|---|---|
| (a) nightly PR を auto-merge させず、人間の approve を必須にする | ゲートを 1 箇所入れるだけ | **低コスト。ただし溜まると形骸化する** |
| (b) nightly に「削除の提案」も行わせる | 追記と同時に、陳腐化した項目の削除候補を出させる | 効果は大きいが、**判断が AI に寄る**ので (a) とセットが要る |

**(a) を先に、(b) は候補 Q の判断材料が揃ってから**が順当です。

**コスト**: 小（(a) のみ）

### 候補 AB: L2 の初回スコアを保存する — 優先度 **中**

記事は「偽陽性/偽陰性の率は引き続き見ていくべき」と明記しています。本組織にはその材料がありません。

`l2_composite` の記録 109 件すべてが 0.88 以上で、**fail が 1 件も残っていません**。L2 retry は 4 件発生しているので、**修正後の最終値だけが上書き保存されている**と考えられます。

対処は task-log スキーマに 1 フィールド足すだけです。

```yaml
l2_composite: 0.98        # 最終
l2_composite_initial: 0.72  # ← 初回（retry 前）
l2_retries: 1
```

これがあれば「L2 が何を落としたか」の分布が取れ、**閾値 0.85 が適正かを後から検証できます**。

**コスト**: 小

**注意**: これは**過去分には遡れません**。今から記録を始めても、判断材料が溜まるのは先です。

### 候補 AC: AI による PR auto-approve の導入 — ❌ **不採用**

記事の主題そのものですが、**本組織には導入する対象がありません**。

approve 率は既に実質 100%（直近 60 件すべてレビュー 0 件でマージ）。記事が解決した「approve 率が低くてボトルネックになる」という課題が存在しません。

**同じ記事から、本組織は逆向きの示唆を採るべきです**（候補 X / Y / Z / AA）。仕組みを持ち込むのではなく、記事が前提として持っていた「**人間が見るべき線**」を、本組織はまだ引いていないという点を採ります。
