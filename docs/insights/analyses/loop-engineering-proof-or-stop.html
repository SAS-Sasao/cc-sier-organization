0. 方法

オーナーから URL を直接指定された解析であり、日次ダイジェストからの抽出ではない。したがって本 Skill の通常フロー（Phase 1 クラスタリング）は適用せず、指定 3 ページを全件精読した。

取得は curl（User-Agent 付き）。sbbit.jp は信頼ドメイン外のため WebFetch は使っていない（@.claude/rules/web-content-fetch.md）。ページ間で共通のナビゲーション部分は「前へ 1 2 3 次へ」を境界に機械除去し、本文のみを抽出した。

1. 記事の主張

1.1 ループエンジニアリングとは

きっかけは 2026-06-07、OpenClaw 作者 Peter Steinberger 氏の X 投稿。

もうコーディングエージェントにプロンプトを書くべきではない。エージェントをプロンプトするループを設計するべきだ。

Claude Code を率いる Boris Cherny 氏の「私の仕事はループを書くことだ」も拡散し、2026 年 6 月末に Anthropic が公式ブログで「ループエンジニアリング」として定義した。

停止条件が満たされるまでエージェントが作業サイクルを繰り返すこと

従来のバイブコーディングでは、「次に何をやるか」を決める一番外側の輪を人間が手動で回していた。ループエンジニアリングはその外側の輪ごと機械に任せる。

AI との関わり方は、段階を追って外側へ移動してきた、というのが記事の整理である。

段階問い
プロンプトエンジニアリング何と頼むか
コンテキストエンジニアリング何を知らせるか
ハーネスエンジニアリングどんな道具を使わせるか
ループエンジニアリングいつ動かし、どう検証し、いつ止めるか
誤解しないでほしいが、プロンプトが不要になるわけではない。ループの内部では今もプロンプトが働いている。変わるのは、エンジニアが最も時間をかける場所だ。

1.2 著者の環境と「人間の仕事 3 つ」

著者は約 1 年運用した結果、自分の仕事が 3 つに絞られたと書く。

  1. 設計書を斜め読みして、問題に気がついたら指摘する
  2. 長い開発をどこで区切るか決める
  3. 本番反映のタイミングを判断する
人間は開発の流れに常時付き添う操作員ではなく、ゴールを決めて例外だけに対応する監督になった。コードを書かなくなったことよりも、うまく回っている限り人間が工程から抜けていることこそが大事だと考えている。

構成要素は 4 つ。

要素中身
CLAUDE.md「最小の実装から始める」「仕様を推測せず、必ず検証する」等、AI が迷ったときの判断基準
開発文書要件定義書・設計書・実装計画書を必ず作らせ参照させる。これが AI の外部記憶。状況が変われば AI 自身が書き換える
サブエージェント設計 / 実装 / レビューを分ける。レビューは開発元の違う GPT 系モデルに任せ、作った本人に採点させない
/issue-to-merge課題ファイル → 実装計画 → 複数 AI で実装 → GPT レビュー → テスト → 本番反映 → 本体組み込みまで自動。このスキル自体も Claude Code に書かせた

重要な但し書き: 最初からループエンジニアリングを目指したわけではなく、毎回の面倒な作業を 1 つずつ自動化した結果、振り返るとこの形になっていたという。

1.3 5 ステップ（順番が逆だと事故る）

多くの人は最初に「全自動で回るコマンド」を作りたがる。順番は逆だ。 判断の原則と検証の仕組みがない状態で自動化すると、間違った方向へ高速で突き進むシステムができあがる。
Step内容
1判断の原則を書く — CLAUDE.md に「迷ったときのルール」を 10〜20 個。自動化の第一歩は AI を動かすことではなく、AI の判断基準を固定すること
2文書を AI の外部記憶にする — 要件定義書・設計書・実装計画書の 3 点を毎回作る決まりにする
3作る係と評価する係を分ける — 自分の宿題を自分で採点させない。AI は自分の作ったものを甘く評価しがちなので、ここが品質を守る生命線
4合格を機械が判定できるようにする — テスト・文法チェックをコマンド一発に。TDD ならそのテストが客観的な停止条件になる
5繰り返す作業を標準手順書にする — 頻出作業を Skill として登録
—最後に外側のループをつなぐ。部品がそろっていれば、自動コマンドは AI 自身に書かせられる

1.4 「終わり」の定義がすべて

記事で最も実務的な部分である。

良し悪しゴールの書き方
❌ 悪い「ログイン機能を完成させろ」 — 抽象的。AI が「できました」と言えば終わってしまう
✅ 良い「テスト 42 件がすべて通り、文法チェックのエラーが 0 件になるまで修正する。5 回試して駄目なら、状況を報告して止まる」

ただし著者は「そんな指示は人間には面倒すぎる」とも書く。そこでコンテキストエンジニアリングが効いてくる。目的や背景が共有されていれば、必要十分なゴール条件も AI 自身に設定させ、完了したか自分でチェックさせられる。

このゴール判定の精度こそがループエンジニアリングの肝なのだ。

もう 1 つが 「人間の関与」の設計。

完全無人化は目標ではない。筆者も本番反映の直前だけは自分で判断すると決めている。（中略）人間をどの工程から外し、どこに残すか。それを決めること自体がループエンジニアリングなのだ。

コストについては、Anthropic が「定型作業には安価なモデル、重要な判断には高性能なモデル」を推奨していると触れている。

1.5 冷静な数字 — 成功率 25%

2026 年 7 月末に Microsoft らが公開したベンチマーク LoopsBench（112 件の長時間開発タスク）。

条件完全解決率
Claude Opus 4.7 + Claude Code（当時最強）25%
実際の GitHub 上の複雑な連続タスクに限ると3% 台
優秀なモデルを無限に回せばソフトウェアが勝手に完成する、という期待は現時点では幻想だ。

したがってループエンジニアリングの本当の姿は、著者いわくこうなる。

失敗する AI を前提に、失敗を検出し、修正させ、再試行させ、それでも駄目なら安全に止める。そのための制御の仕組みを作る技術だ。

1.6 Proof-or-Stop — 本記事の核心

7 月公開の査読前論文「Proof-or-Stop」が示した思想として、次が引かれている。

AI の「終わりました」は事実ではなく、ただの主張である。テスト結果という証拠がそろうまで、完了として扱ってはならない。

1.7 残る人間の仕事

コンテキストを整え、ゴール条件を定義し、どこで人間が引き取るか。AI を安全に自動運転させるための高度な判断と設計が、人間の仕事になる。 これには経験による勘だけでは対応しきれない。ソフトウェア工学や組織マネジメント、もしくは人間側の認知心理学といった基礎知識が必要になってくる。

2.2 Step3 の弱さ — 「別ベンダー」ではない

記事の要求は 「レビューは開発元の違う GPT 系モデルに任せ、作った本人に採点させない」 である。

本組織の L2 は「fresh な general-purpose agent」で執筆者バイアスは避けているが、モデルは同じ Claude である。GPT 系を使う Skill は 1 件（company-diagram-v2 が Codex を言及）にとどまる。

参考: 2026-08-16 の解析（2026-08-w2-claude-code-codex-agent.md §8.3.1）で読んだ claudex 記事の委譲マトリクスは、高リスクレビューを cc と Codex の独立並列にし、互いの結果を見せない設計だった。方向性は同じである。

2.3 Proof-or-Stop の当てはまり — 本組織にも、この解析自体にも

(a) task-log の実測

項目値
status: completed の task-log237 件
うち「未検証事項」「確認していないこと」を自認しているもの18 件（7.6%）

つまり 92.4% の task-log は「完了」と主張するだけで、何を検証していないかを書いていない。記事の言う「主張」と「証拠」の区別が、記録上ついていない。

既存カタログの候補 B（verification-pending の追加）・C（未検証事項欄）・S（緑 ≠ 実用可）・AL（L2 を判定から証拠の構造化へ）は、いずれもこの問題を別角度から指している。Proof-or-Stop は、それらに共通の名前を与えたと読める。

(b) このセッション自身が実例

2026-08-16 のセッションで、「修正した」と報告して実は直っていなかった事例が 2 回連続で起きた。

PR報告内容実態
#786「reward が付かない問題を是正した」❌ 原因を記述しただけで、テンプレートに ## reward 見出しが残っており次回も再発する状態だった
#787「テンプレートを直したので次回から正常値が取れる」❌ 通常タスクには効いたが、/company-cycle の経路では直らなかった（Phase 順序の問題）
#788「Phase 3 に再評価手順を追加した」⏳ 次サイクルまで未検証（本レポート時点でも未確認）

さらに 2026-08-22 の本セッション冒頭でも、git fetch 前のローカルを見て「8/17 以降のコミットは 0 件 / 日次ダイジェストは 8/16 が最新」と報告し、直後に訂正している（実際は 17 コミット / ダイジェストは 8/22 まで存在）。

いずれも「テスト結果という証拠」を取る前に完了を主張した結果である。 記事の指摘がそのまま当てはまる。

2.4 「人間の仕事 3 つ」との対比

記事の 3 つと、本組織でオーナーが実際にやっていることを並べる。

記事の 3 つ本組織での対応
設計書を斜め読みして問題を指摘✅ 実施（配置先の判断、対象期間の解釈の訂正など）
長い開発をどこで区切るか決める✅ 実施（「案 A で」「いったんそれでいい」等）
本番反映のタイミングを判断✅ PR のマージは全件オーナーが手動（auto-merge していない）

3 つとも既に人間側に残っている。 記事の到達点と同じ形になっている。

3. 採用候補

(BC) 停止条件を「主張」から「証拠」へ — Proof-or-Stop の明文化 — ⬜ 優先度 高

根拠: §2.3。completed 237 件のうち 92.4% が未検証事項を書いていない。加えて、直近セッションで「修正した」報告が 2 回連続で誤りだった実例がある。

やること（既存候補 B / C / S / AL を 1 本に束ねる）:

@.claude/rules/task-log.md に次を追加する。

完了を報告する前に、「何をもって完了としたか」の証拠を 1 行書く。 証拠が実行結果でない場合（読んだだけ・書いただけ）は、status: completed にしてよいが「未検証事項」に必ず記載する。

記事の良いゴールの例（「テスト 42 件が通り、エラー 0 件。5 回試して駄目なら止まる」）を、そのまま雛形として載せる。

コスト: 小（rules に 1 節） 判断に必要な情報: 既存 237 件に遡って書かせるかは未決定（遡及は候補 AV / AW と同じ問題を含む）

(BD) L2 レビューを別ベンダーにする — ⬜ 優先度 中

根拠: §2.2。記事は「開発元の違う GPT 系に任せる」を品質を守る生命線と位置づけている。本組織は fresh agent で執筆者バイアスは避けているが、モデルは同じ Claude である。

Codex CLI は既にインストール済み（2026-08-16 実測: codex-cli 0.144.5、認証済み・現用中）なので、環境は揃っている。

留保: 8/16 の解析で読んだ claudex 記事は、高リスクレビューのみを独立並列にする設計だった。全 Skill の L2 を差し替えるのは過剰で、致命軸を持つ Skill に限るのが現実的。

未検証: Codex 側から本リポジトリの成果物を読ませるコストと、レビュー品質の差を測っていない。

(BE) 停止条件を持たない 13 Skill の扱いを決める — ⬜ 優先度 中

根拠: §2.1 Step4。L0（機械判定）を持つのは 5 / 18 Skill のみ。残り 13 は「AI が完了と言えば完了」である。

ただし全部に L0 が要るわけではない。/company（対話）や /company-admin（マスタ CRUD）は性質が違う。どの Skill に機械的な停止条件が必要かを選別するのが先。

未検証: 13 Skill の内訳を性質別に分類していない。

(BF) 「1 つずつ自動化する」順序の記録 — ❌ 不採用（既に達成済み）

記事の 5 ステップは「これから始める人」向けであり、本組織は既に外側のループ 2 本まで到達している。改めて順序をなぞる意味はない。

ただし記事の警告——「判断の原則と検証の仕組みがない状態で自動化すると、間違った方向へ高速で突き進むシステムができあがる」——は、新しい Skill を作るときのゲートとして既存の候補 R（Skill 作成ゲート 4 問）に含まれている。
