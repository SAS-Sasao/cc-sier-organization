## 0. 3 行で

- 記事の主張は **「ドメインモデル図は、コードの外に置くから古くなる。コードの世界の内側に持ってくれば、構造的に古くならない」**。
- 実装の型を参照してモデリングを書くので、**型が変わればモデリングのコードがコンパイルエラーになる**。図を直し忘れることが仕組み上できなくなる。
- 副産物として **AI にオブジェクト図のパターンを量産させられる**。これが記事の隠れた本題。

## 1. DDD とは何か（前提知識ゼロから）

記事は DDD を知っている前提で書かれているので、まずそこを埋める。

### 1.1 出発点 — 「何を主語にして設計するか」

システムを設計するとき、何から考え始めるでしょうか。

よくあるのは **データベースのテーブルから**考える方法です。「注文テーブルには id と会員 ID と金額があって……」と組み立てていく。動くものは作れますが、**業務の言葉とコードの言葉がずれていきます**。

現場の人は「**キャンセルした注文は再開できない**」と言っているのに、コードには `status` という文字列カラムがあるだけ。ルールがどこにも書かれていないので、開発者ごとに違う場所でチェックが書かれ、抜ける。

**DDD（Domain-Driven Design / ドメイン駆動設計）** は、ここを逆転させます。

> **業務（ドメイン）の構造を主語にして、コードをそれに合わせる。**

「ドメイン」とは、そのシステムが扱う**業務領域**のことです。小売なら「発注」「在庫」「棚割」、会計なら「仕訳」「締め」。**その領域の専門家が使っている言葉と概念**が設計の出発点になります。

### 1.2 なぜ SIer にとって重要か

SIer の仕事は「顧客の業務をシステムにする」ことです。**業務の言葉と、出来上がったシステムの言葉がずれると、後の変更が全部つらくなります。**

- 顧客が「掛け率を変えたい」と言う → コードのどこを直せばいいか誰も分からない
- 業務ルールが仕様書・コード・運用手順に散らばり、**どれが正なのか分からない**

DDD はこれを「業務の言葉でコードを書く」ことで防ごうとします。

### 1.3 最低限の用語（6 つ）

記事を読むのに必要な語だけに絞ります。**小売の「注文」を例**にします。

| 用語 | ひとことで | 例 |
|---|---|---|
| **ユビキタス言語** | 業務側と開発側で**同じ言葉を使う**こと | 現場が「注文者」と呼ぶなら、コードも `orderer` にする。`user` にしない |
| **境界づけられたコンテキスト** | 同じ言葉でも**部署が違えば意味が違う**ので、区切りを引く | 「商品」は販売部門では売価つきの商品、物流部門では箱のサイズが主。**同じ名前の別物**として分ける |
| **エンティティ** | **ID で識別され、状態が変わっていく**もの | 注文（`o-1001`）。中身が変わっても同じ注文 |
| **値オブジェクト** | **値そのものが同一性**で、変わらないもの | 金額 1,000 円、日付。「1,000 円」に ID はない |
| **集約（アグリゲート）** | **まとめて守るべき塊**。整合性の単位 | 注文と注文明細は一体。「明細だけ勝手に増やす」を禁じる |
| **ドメインイベント** | 業務上「**起きた事実**」。あとから変わらない | 「注文が確定した（OrderPlaced）」 |

**集約が一番わかりにくい**ので補足します。

> 注文には明細が複数ぶら下がります。ここで「注文の合計金額は明細の合計と一致していなければならない」というルールがあるとします。
> このとき、**明細だけを外から勝手に触れると壊れます**。だから「注文を通してしか明細を触れない」という壁を作る。この壁の内側が **集約** です。
>
> そして**集約をまたぐときは ID で参照するだけにする**。注文から会員を直接いじらない。会員は別の集約だからです。

記事のサンプルコードにこれがそのまま現れます。

```ts
ds.aggregate(Order, {
  members: [
    externalAggregate(Member),   // 会員は別集約 → 参照だけ（点線）
    entity(OrderItem),           // 注文明細は注文集約の中
    valueObject(OrderPlaced),    // 確定イベントは不変の事実
  ],
})
```

## 2. SUDO モデリングとは

記事が使っているモデリング手法です。ログラスの松岡氏が提唱したもので、**DDD のモデリングを実装に落とすための最小限の 4 枚**という位置づけです。

| 記号 | 図 | 何を描くか |
|---|---|---|
| **S** | システム関連図 | 開発するシステムと、利用者・外部システムの関係 |
| **U** | ユースケース図 | 利用者の要求に対して、システムがどう振る舞うか |
| **D** | **ドメインモデル図** | 簡易クラス図。**属性・関連・多重度・集約の範囲・ルール/制約** |
| **O** | **オブジェクト図** | ドメインモデルの**具体例**（実際の値を入れたもの） |

記事が扱うのは **D と O** です。

**なぜ D と O がセットなのか**が肝心です。

- **D（抽象）** だけだと、机上では正しく見えるモデルの穴に気づけない
- **O（具体）** に実際の値を入れると、「あれ、キャンセル済みの注文にこの状態あり得るの？」と**矛盾が見える**

つまり **抽象と具体を往復してモデルを磨く**のが SUDO の D・O の使い方です。

## 3. 記事が挙げる 3 つの課題

著者は 5 年ほど SUDO モデリングを使ってきて、D と O の**「書いたあとの運用」**にモヤモヤしていた、と書いています。

### 課題 1: 図が古くなる

実装が進めば属性は増え、集約の切り方も概念の名前も変わります。しかし図は**別の場所に置かれた静的な成果物**なので、

> 誰かが意識して直さない限り古くなり続けます。

そして著者が指摘する怖い点はこちらです。

> **一度「この図、最新じゃないかも」と思われた瞬間に、図は参照されなくなります。**

### 課題 2: オブジェクト図のパターンが足りない

O の価値は「具体例でモデルの矛盾に気づけること」なので、**パターン数が勝負**です。ところが draw.io で 1 パターン描くのは面倒。

> 結果、代表的な1〜2パターンだけ描いて満足してしまい、**エッジケース（本当は一番議論したいやつ）が図にならない**

### 課題 3: AI 駆動の開発フローに組み込めない

> draw.io のような GUI で描いた図は **AI からの読み書きと相性が悪く**、フローの外側に置かれたままになりがちでした。

## 4. 解決案 — Storybook の発想を持ち込む

著者の着想はこうです。

> UI コンポーネントは、Storybook で「コードで書いたコンポーネント」を「複数パターンの Story と一緒に」WebUI で見られる。**ドメインモデルも同じことができるのでは？**

| Storybook | ドメインモデリング |
|---|---|
| コンポーネント本体 | **ドメインモデル図**（型定義から導出される抽象） |
| Story（値を流し込んだパターン） | **オブジェクト図**（具体例） |

作られたのが [`domain.storybook`](https://github.com/shinoda-yosuke/domain.storybook) で、TypeScript の型定義から図を生成し、静的ページとして publish できます。

### 効いた理由 — 「構造的に古くならない」

ここが本質です。

> モデリングのコードは実装の型を参照しているので、**ドメインモデル側の型が変わればモデリングのコードもコンパイルエラーになります**。「図を直し忘れる」ことが仕組み上できず、図は常に実装と同期した最新の状態に保たれます。

**「気をつけて更新する」ではなく「更新しないと壊れる」に変えた。** 課題 1 はこれで消えます。

### 副産物 — AI にパターンを量産させられる

こちらが実務的には大きい効果です。

> 型定義と既存のパターンを渡して「解約済み契約に紐づくデバイスのパターンを追加して」と指示すれば、draw.io で図形を並べる作業なしにパターンが増えていきます。

課題 2（エッジケースが図にならない）は、**パターン追加のコストが劇的に下がったこと**でほぼ解消したとのこと。課題 3 もモデリングがただのコードなので自動的に解決します。

## 5. 自組織（cc-sier）での実測

### 5.1 図の古さ

| 対象 | 件数 | 最終更新 |
|---|---|---|
| `docs/drawio/` | **16 図** / HTML 17 | **2026-06-13**（約 2 ヶ月前） |
| `docs/diagrams/` | **28 図** / HTML 57 | **2026-07-25**（約 3 週間前） |

**記事が課題 1 で指摘した状態そのものである。** 本組織の図は `/company-drawio` や `/company-diagram-v2` で生成した**静的成果物**で、生成した時点で更新が止まっている。

### 5.2 ただし、記事の解法はそのままは効かない

**重要な限界がある。** 記事の仕組みは「**モデリングのコードが実装の型を参照している**」から成立する。型が変わればコンパイルエラーになる、という因果があって初めて「構造的に古くならない」。

本組織の図の大半は **AWS アーキテクチャ図**であり、**その実装コードは本リポジトリに存在しない**（顧客システムの提案・設計であって、動くコードを持たない）。参照すべき型がないので、この仕組みは適用できない。

| 図の種類 | 件数の目安 | 記事の手法が効くか |
|---|---|---|
| AWS 構成図（`docs/diagrams/`） | 28 | ❌ 参照する型が無い |
| 業務フロー・C4・ER 図（`docs/drawio/`） | 16 | 🔶 **ER 図とドメインモデル図のみ可能性あり**。ただし実装が別リポジトリ |
| 派生アプリの設計（`retail-stats-tracker` 等） | — | 🔶 `/company-spawn` で切り出した先にコードがあるなら適用余地あり。**未調査** |

### 5.3 それでも効く部分 — 「AI にパターンを量産させる」

記事の**副産物のほうは、型がなくても採れる**。

本組織は既に「モデリングの成果物をコードの世界（Markdown + Git）に置く」ことは実現している（`docs/drawio/*.md` に図の説明を置き、PR 運用している）。足りていないのは **具体例（オブジェクト図）のパターンを増やす習慣**である。

`docs/drawio/storcon-instore-system.md` や `btob-sales-c4.md` は**抽象の図だけ**で、「この値のときどうなるか」という具体例が無い。記事の課題 2 がそのまま当てはまる。

### 5.4 関連する既存アセット

- Subagent: `system-architect` / `data-architect`（DDD 的な設計を担当しうる）
- Skill: `/company-drawio`（ER 図・C4・業務フロー生成）
- DDD 用語を含む既存成果物: 8 ファイル（うち設計文書は `decisions/2026-06-13-diagram-aws-skill-migration-design.md` 等）

## 6. 採用候補

### (AZ) 図に「具体例（オブジェクト図）」の節を足す — ⬜ 優先度 **中**

**記事の課題 2 への対処。型がなくても今日からできる。**

`/company-drawio` が生成する詳細ページ（`docs/drawio/*.md`）に、**「具体例」セクション**を必須化する。抽象の図だけでは、モデルの穴が議論の俎上に乗らない。

- 代表パターンだけでなく、**エッジケースを最低 1 つ**書かせる（キャンセル済み・上限超過・権限なし など）
- AI が生成するのだから、draw.io で図形を並べるコストは元々ゼロに近い。**やっていないだけ**

**コスト**: 小（SKILL.md と `review-prompt.md` に 1 セクション追加）
**判断に必要な情報**: 既存 16 図のうち、具体例を書く価値があるのはどれか（**未選別**）

### (BA) `/company-drawio` に DDD 語彙のガイドを持たせる — ⬜ 優先度 **低**

ER 図や C4 を描くとき、**集約の境界**と**ユビキタス言語（日本語の業務名）**を明示させる。記事のサンプルが `addUbiquitousTerm(Order, { ja: '注文' }, ...)` で日本語名を持たせているのと同じ発想。

SIer の成果物は顧客に読ませるものなので、**業務の言葉が図に出ていること**の価値が高い。

**未検証**: 現行の図に業務語彙がどれだけ載っているかを**測っていない**。

### (BB) `domain.storybook` の導入 — ❌ **現時点では不採用**

理由は §5.2。**本リポジトリの図は参照すべき実装の型を持たない**ため、この仕組みの核（型変更でコンパイルエラー）が成立しない。TypeScript 前提であることも、本組織（Bash / Python 中心）と噛み合わない。

**ただし条件付きで再評価する**: `/company-spawn` で切り出した派生アプリが TypeScript で、かつドメインモデルを持つ場合は適用余地がある。`retail-stats-tracker` の実装言語は**未確認**。
