## 0. 方法

### 0.1 対象期間の確定

依頼の「8/9週」を **2026-08-03（月）〜 08-09（日）** と解釈した。根拠は次の 2 点。

1. 2026-08-09 は日曜日であり、月曜起点の週は 08-03 から始まる
2. **日次ダイジェストは 2026-08-09 が最新で、08-10 以降は未生成**（`docs/daily-digest/` を実査）

「8/9 から始まる週（08-09〜08-15）」と解釈した場合でも、データが存在するのは 08-09 の 1 日分だけである。08-03 起点で取ることは、どちらの解釈に対しても取りこぼしがない。

### 0.2 取得方法

精読対象の外部記事 12 件はすべて `curl`（User-Agent 付き）で原文 HTML を取得し、`script` / `style` を除去してテキスト化した。**WebFetch は使っていない**（`@.claude/rules/web-content-fetch.md` に従う。Zenn / Qiita / はてブ / 企業技術ブログはいずれも信頼ドメイン外）。

## 2. レンズ① Claude Code 実運用

### 2.1 サブエージェントは「1 件ずつ」より「まとめて並列」が速く、かつ安い

**出典**: [検証！Claude Code のサブエージェント並列はお得なのか](https://qiita.com/tamashiro_nobuyuki/items/ff9004b66b7761c4d34c)（tamashiro_nobuyuki / 株式会社NEXT TECHNOLOGY、2026-07-31、curl 3,621 字）

同一の独立 3 タスクを 3 通りの方法で実行し、所要時間・トークン・メイン文脈の増加量を計測した記事。

| 群 | 所要時間 | 全体トークン | メイン文脈の増加 |
|---|---|---|---|
| ① 直列・サブエージェント無し | 約 9.5 秒 | 40,770 | 5,876 |
| ② 直列・サブエージェント経由 | 約 30.0 秒 | 119,194 | 6,183 |
| ③ **並列**・サブエージェント経由 | 約 14.3 秒 | **66,884** | **3,473** |

意外なのは **②→③ でトークンが 44% 減っている**点。著者の分析では、同時に似た内容のサブエージェントを起動したことで**定義部分のキャッシュを共有でき**、③ では新規キャッシュ書き込みがほぼ発生せず、コストが約 1/10 のキャッシュ読み込みが大半を占めたため。

一方、著者が期待していた「メイン文脈の保護」効果は**確認できなかった**と正直に書いている。理由は、依頼したタスクが `tool_uses: 0` の一発回答で、そもそもサブエージェント側に隠すべき試行錯誤が無かったから。

**この記事の限界**（著者自身が明記）: 測定は 3 タスク・1 セットのみ。査読も反復もない。「重いタスクでの文脈保護効果は未検証」と結んでいる。

### 2.2 `isolation: worktree` — 「決定論的な処理を LLM の外へ」だけでは足りない

**出典**: [【並列開発】isolation: worktree やめました 〜決定論と認知を分けて AI と仕事する〜](https://zenn.dev/rakko_inc/articles/2da36c0abe4dbe)（marimo / ラッコ株式会社、2026-08-06、curl 6,973 字）

Claude Code の `isolation: worktree`（サブエージェントを専用 git worktree で動かす設定）を並列開発に使っていたが、やめた記録。

著者は「起動のたびに壊れ方が変わる」現象を追い、**原因が呼び出し方にあった**ことを突き止めている。

> Claude Code のサブエージェントには起動のしかたが 2 通りあり、`isolation: worktree` はそのうち片方でしか効きません。
> - **名前を付けずに起動する** … 設定通り専用の worktree が用意される
> - **名前を付けて起動する** … メインの作業ディレクトリをそのまま使う。`isolation: worktree` の指定は**無視される**

さらに、本体はエージェントを起動時のパスに固定するため、そのパスを自分で `git worktree move` すると足場が消える。

注目すべきは、**原因が分かった上で「直さずにやめた」**点。worktree の用意は入力が決まれば出力が決まる決定論的な処理であり、そもそも Claude Code の機能に載せる必要がなかった、という判断である。シェルスクリプト 1 本（`setup-worktree.sh`）に置き換えた結果、`isolation` 指定・Hooks・改名工程・「名前付きで起動してはいけない」という運用上の注意が、まとめて消えた。

教訓として提示されているのが、次の物差し。

> 見分ける物差しとして使えるのが、**単体で叩いて確かめられるか**です。

そして、この不安定さは「AI の気まぐれ」に見えるが実際には配線の問題であり、**プロンプトを直そうとしてしまう**のが厄介だ、と書いている。

> LLM の判断から外しても、呼び出し方しだいで挙動が変わる仕組みに載せていれば同じことです。

なお本記事は 2026 年 7 月時点の挙動であり、著者もバージョンによって変わりうる点を注記している。

### 2.3 プロンプトキャッシュ — 「再開一発目」のコストは順番で決まる

**出典**: [プロンプトキャッシュを意識して claude code のトークンを節約しよう](https://zenn.dev/ceres_tech_blog/articles/7163ae482e124e)（tamapon / 株式会社セレス、2026-08-04、curl 5,931 字）

「前日のやり取りを複数再開したら、まだ一言も打っていないのに 5 時間制限が 2 割持っていかれた」という実体験から書かれた記事。公式ドキュメントの参照が多く、記事内で**どこが公式記載でどこが自分の推論か**を明示している点が信頼できる。

**キャッシュが飛ぶ条件**（記事の列挙）:

| 条件 | 補足 |
|---|---|
| 1 時間触らない | 日跨ぎは確定でこれ |
| `/model` によるモデル切り替え | キャッシュはモデル単位。opusplan の plan mode 出入りも該当 |
| `/effort` による effort 変更 | キャッシュキーはモデルと effort の組 |
| 自動モデルフォールバック | safety classifier に引っかかった場合 |
| MCP サーバの接続/切断 | ただし tool search 対応モデルでは遅延ロードのため壊れない |
| ツールまるごと deny | `Bash` は飛ぶ。`Bash(rm *)` のようなスコープ付きは飛ばない |
| Claude Code のアップグレード | 次回起動でシステムプロンプトが変わる |

**対策の中核は「順番」**である。

> `/compact` は会話履歴を短い要約に置き換える。この要約を作る処理はキャッシュがまだ生きてるうちに走るから安く済む。（中略）逆に「再開してから /compact」だと、キャッシュが切れた履歴を全部読んでから要約することになるので、再処理ぶんは丸々払う。**順番が全て。**

すでに切れてしまった場合は、`/model` で Sonnet 等に落としてから `/compact` し、元に戻す。全履歴の再処理 1 回は避けられないが、**どのモデルに払わせるかは選べる**、という理屈。

著者が「公式ドキュメントに明記がなく、記述からの帰結として書いた」と断っているのは 2 点（要約が選択中のモデルで走ること / 5 時間・週次ウィンドウ側の節約分）。**この 2 点は本レポートでも未検証扱いとする。**

### 2.4 cclens — 設定の棚卸しを「計測」に置き換える

**出典**: [Claude Code の「無駄」を可視化するツール cclens を作った](https://zenn.dev/lambdalisue/articles/introduce-cclens)（Alisue、2026-08-05、curl 8,824 字）

問題設定が、本組織の状況とそのまま重なる。

> ある目的のためにルールやスキルを書いたとして、それが本当に効いてるのか？（中略）気付いたら使われない設定だけが静かに積もっていく
> じゃあ棚卸しするか、となっても、今度はその非決定性が逆に効いてきます。「もしかしたら自分の知らないところで効いてるのかも」と思うと、途端に消せなくなる。

cclens は**計測用に何かを走らせるのではなく、普段使いのログ（`~/.claude/projects/**/*.jsonl`）をそのまま解析する**。Rust 製・全ローカル完結・データ送信なし。

| コマンド | 見えるもの |
|---|---|
| `cclens doctor` | 1 画面の健康診断（global / project 別） |
| `cclens waste` | 最適化余地のランキング（削除 / スリム化 / トリムの推奨付き） |
| `cclens inventory` | 全設定サーフェス × 実際の使用状況 |
| `cclens overhead` | **毎セッション必ず払う常時オンのコンテキスト量**（自分の設定由来 / 削れない下駄 に分解） |
| `cclens usage` | スキルごとの使用回数ランキング |
| `cclens failures` | ツール失敗のカテゴリ別集計 |
| `cclens stuck` | Claude が短時間に何度も編集し直したファイル |
| `cclens optimize` | findings を Claude 自身に渡して修正案を出させる |

本組織にとって効くのは `overhead` と `usage` と `inventory` の 3 つ。理由は §5 の実測を参照。

### 2.5 plan モードは要らなくなった（という主張）

**出典**: [【Claude Code】plan モードはもう使っていない](https://zenn.dev/haru067/articles/0c28638945aa32)（haru067 / NOT A HOTEL、2026-07-29、curl 1,974 字）

短い記事だが論旨は明快。plan モードの役割は「判断を求める停止点」と「Edit 禁止のガードレール」の 2 つで、どちらも**「案をください」と一言言うだけで解決する**、という主張。

plan モードより優れている点として挙げているのが Human-in-the-Loop。

> plan モードの典型的な敗北は、人間が知らない調査のコンテキストを使った結論を列挙し、人間の認知負荷を超えた読むに堪えない実装案の羅列を吐き出してしまうことだ。そして人間は読むに耐えないので脳死で許可し、あとで検証すればいいか、となる。

「案をください」なら一問一答ではなく何往復もできる、というのが利点だという。

**この主張の扱いには注意が要る。** 記事は Anthropic のブログ（context engineering）を根拠に「今のモデルは十分に賢いので雑な命令でよい」としているが、**cc-sier は Skill が固定フェーズを持つ設計**であり、「雑な命令で全部良い感じに」とは前提が異なる。§6 では優先度を低く置いた。

## 3. レンズ② Codex 併用

### 3.1 CLAUDE.md / AGENTS.md / Skills の二重管理をどう畳むか

**出典**: [【決着】Claude Code と Codex の設定ファイルを同期させる（みんな仲良く）](https://zenn.dev/kanta_tkd/articles/20f7f41cff8428)（Kanta / 株式会社エクスプラザ、2026-07-28、curl 3,413 字）

課題の記述が、そのまま本組織に当てはまる。

> 同じプロジェクトで Codex と Claude Code の両方を使っているとき、AGENTS.md や SKILLS などの変更が片方にしか適用されない
> 何も意識せずに両方を使っていると、片方でのみ更新が入ってそのまま・・・ という状況が起きますし、なんならそれぞれ独自に分岐していく未来が容易に想像できますよね。

著者の解法は **「形式が同じものはコピーを作らず symlink」**。

| 対象 | 手段 |
|---|---|
| AGENTS.md / CLAUDE.md | **CLAUDE.md に `@AGENTS.md` と記載**して AGENTS.md を読ませる |
| Skills | `.claude/skills/` を `.agents/skills/` へ symlink（git は symlink をリンク先パス文字列として記録するのでそのまま版管理できる） |
| MCP（`.mcp.json` JSON ↔ `.codex/config.toml` TOML） | 書式が違うため変換ロジック。中立形に正規化して比較し、差があれば相手側の書式へ変換 |

> 最終的に、編集されるのは常に Claude 側の 1 か所だけになり、生成・コピーを忘れるという事故が構造的に起きなくなります。

重要なのは **「すべてを一律で同期しない」** という設計判断。

- **Prompting Guide の違い**: Anthropic と OpenAI で推奨される指示の書き方が異なる。Claude 向けに調整した Skill の文面が Codex でも最適とは限らない
- **片方に仕組み自体が無い**: Codex には Claude Code の `rules`（パス条件つきで読み込まれる指示ファイル）に当たる機能が無い。`~/.codex/rules/` は存在するがコマンド承認ポリシーであり別物

そのため著者は、rules については**ファイル一覧と読むべきタイミングだけを AGENTS.md に書き出し**、実際に読むかは読み手のツールに委ねている。

成果物は `agents-sync` CLI + スキル + fswatch/launchd 常駐スクリプト（MIT）。なお著者は「Claude Code CLI から Codex を操作する手法（`claudex` 等）もあり、CLI しか使わない人はそちらが良い」と冒頭で断っている。

### 3.2 Codex の利用量と Budget を Gateway 層で止める

**出典**: [Amazon Bedrock AgentCore Gateway で Codex の利用量と Budget を制御する](https://zenn.dev/kashiwabaray/articles/796539362435eb)（Yutaka Kashiwabara / NTT DATA、2026-08-07、curl 12,971 字）

AWS Samples の `sample-agentcore-gateway-usage-interceptor` を EC2 に構築し、Codex CLI から実際に叩いた検証記録。手順とコマンドが全部載っており、再現性が高い。

構成は、AgentCore Gateway の **Interceptor** をコストガバナンスのポイントとして使うもの。

- **REQUEST Interceptor**: JWT からユーザーを特定 → DynamoDB から現在利用額を取得 → Daily / Monthly Budget を確認 → 超過なら **モデル呼び出し前に HTTP 403**
- **RESPONSE Interceptor**: レスポンスの `usage` からトークン数を取得 → コスト算出 → CloudWatch EMF 出力 → DynamoDB へ加算

検証結果（記事の表）:

| 検証内容 | 結果 |
|---|---|
| Codex → AgentCore Gateway → GPT-5.4 | 成功 |
| DynamoDB へのユーザー別 spend 記録 | 成功 |
| Daily Budget 超過 | HTTP 403 |
| **Block 後の spend 増加** | **なし** |
| Monthly Budget 超過 | HTTP 403 |

著者は**確認できていないことを明示している**点が誠実で、そのまま引用に値する。

> 今回確認したのは **すでに現在利用額が cap を超えているユーザーの次のリクエストを止められること** です。
> （中略）「Budget を超えたユーザーの次の呼び出しを止める」ことと、「設定した Budget を絶対に超過しない」ことは同じなのか という点は、もう少し検証する余地があります。

並列実行時に複数の REQUEST Interceptor が同じ現在利用額を参照して同時通過しうる、という懸念も自分で挙げている。

**本組織への適用**: 現状 1 人運用のため、ユーザー単位のコスト帰属は過剰。**チーム展開（要件定義書 §1.3 Phase 2）に入る段階で効いてくる**設計として記録する。

## 4. レンズ③ AI エージェント設計

### 4.1 エージェントハーネスの解剖 — ループ本体は最後まで変わらない

**出典**: [Claude Code のようなエージェントをゼロから作る](https://zenn.dev/sun_asterisk/articles/f5514175aa0a0a)（グエン・タイ・ゴック / Sun*、2026-08-06、curl 18,827 字）

GitHub 70k スターの教材 `shareAI-lab/learn-claude-code`（MIT）全 20 章を読んだ記録。各章が前章のコードに仕組みを 1 つだけ足す構成で、**Claude Code の各機能が「なぜ必要か」を問題起点で説明している**。

第 1 章のエージェントループがすべての土台で、`stop_reason == "tool_use"` なら実行して結果を返し、そうでなければ抜ける、というだけ。

結論が最も価値がある。

> 20 章ぶんの仕組みは、どれもこのループのまわりに「モデルに何を見せて、何をさせるか」を足しているだけで、**ループ本体は最後まで変わりません**。
> エージェントの賢さはモデルが持っていて、ハーネスの仕事はモデルにコンテキストと道具を渡すことだ

cc-sier の理解に直接効く章を抜き出す。

| 章 | 仕組み | cc-sier での対応物 |
|---|---|---|
| 3 | Permission | `settings.local.json` の allow リスト |
| 4 | Hooks（PreToolUse / PostToolUse / Stop） | `.claude/hooks/` 15 本 |
| 6 | Subagent（**親と別の messages[] / システムプロンプト / ツール一覧**。最後のテキストしか親に返らない） | `.claude/agents/` 20 種 |
| 7 | Skills（起動時はカタログのみ、本文は `load_skill` で `tool_result` として渡す **2 段階ロード**） | `.claude/skills/` 17 種 |
| 8 | Context Compact（**安い順に 4 段階**。budget / micro は取り戻せるが snip は取り戻せない） | — |

### 4.2 エージェント向けツールは MCP より CLI（設計 3 原則）

**出典**: [AI エージェント向けのツールを、MCP ではなく CLI として作った — 設計の 3 原則](https://zenn.dev/codatum/articles/80b99faba75704)（g0e / Codatum、2026-08-04、curl 13,163 字）

MCP を試していた過程で CLI に行き着いた経緯と、その設計原則。**MCP を否定する記事ではない**と著者自身が断っている。

転換点は、MCP 経由でファイル検証を試したときの違和感。

> エージェントは、ローカルのファイルを読み込み、その内容を MCP ツールに渡すためのリクエストボディを組み立て、ツールを呼ぶ、という一連の処理を **すべて自分の「頭の中」＝コンテキスト上でこなそうとします**。

MCP のツールはファイルを**値渡し**でしか受け取れないため、1MB のノートブックを検証させたいだけでも 1MB がエージェントのコンテキストを通過する。CLI ならファイルそのものを引数にできる。

さらに、CLI は**人間・CI・エージェントが同じインターフェースに乗れる**。`cdm notebook validate` を CI で回すために MCP サーバーを立てて……とはならない。

**3 原則**:

| 原則 | 中身 |
|---|---|
| **1. コンテキストを浪費させない** | ファイル形式は**モデルの事前学習を活かせるもの**を選ぶ（JSON/YAML は括弧・インデント・キー反復にトークンを食う → Markdown 拡張を採用）。コマンド名も `validate` / `format` という既存概念に乗せる。独自構文を発明しない。ドキュメントは全部積まず `cdm doc index` / `doc show` で**取りに行かせる** |
| **2. 間違えさせない努力より、気づいて直せる設計に投資する** | プロンプトに禁止事項を積み上げるのをやめる。構造の誤りは `validate` で（**行番号 + 該当行の抜粋 + 具体的な指摘 + 直し方が載った URL** の 3 点セット）、見た目の誤りは PNG 出力させて**エージェント自身に目視確認**させる。機械的に直せるものはツールが直す（**LLM はランダム文字列の生成が苦手**なので ID は `format` が自動付与する） |
| **3. ワークフロー全体をシンプルな一本道に設計する** | 多段手順は 1 コマンドに畳み込む（ポーリングのループをエージェントの判断に委ねない）。検証は対象ごとに分けず `validate` 一発（**どれを叩くべきかという判断＝分岐を持ち込まない**）。流れは人間と共用のドキュメントで伝える |

原則 2 の前提として著者が強調しているのが、ドキュメントの位置づけ。

> エージェントに使わせるツールでは、ドキュメントは単なる付属物ではなく、**コマンドと並ぶインターフェースの一部**です。

原則 3 の「分岐を持ち込まない」は、cc-sier の Skill 設計に直接効く（§6 候補 C）。

### 4.3 「純粋リファクタリング」を証明させて自動マージする

**出典**: [「純粋リファクタリング」を AI に証明させて自動マージする](https://engineering.nature.global/entry/2026/07/prove-pure-refactoring-with-ai-and-auto-merge)（大塚 / Nature CTO、2026-07-31、curl 5,756 字）

3 層レビュー + auto-merge を持つ cc-sier にとって、**最も参考になる 1 本**。

出発点は、レビュー対象を**目的で分ける**という発想。リファクタリング PR で見るのは 2 軸しかない。

1. 設計が良くなっているか（命名・責任分割・依存の方向・結合度）→ **人間の判断が要る**
2. 挙動の等価性 → **機械的**

そこで前者は事前に GitHub issue や夕会で合意しておき、**後者だけを AI に判断させる**。AI に任せる範囲を限定することで信頼性を担保している。

実装は `review-refactoring` Skill + GitHub Actions。

1. PR に `/review_refactoring` とコメント
2. Actions 内で Skill 本体をそのままプロンプトとして Claude に渡し、ベースブランチとの差分をレビューさせる
3. **出力を JSON スキーマ（`pass` と `report_file`）で縛る**
4. `pass: true` → approve + squash auto-merge + `refactoring-only` ラベル
5. `pass: false` → auto-merge せず、人間レビューが必要とコメント

Skill の中身で挙げられているポイント 3 つ。

- **マインドセット**: 「あなたは懐疑的な第三者レビュアーである」「『たぶん大丈夫』ではなく『証明できる』レベルで検証せよ」——AI が人間に同意しがちなことへの対策
- **実行手順**: 動作変更が紛れ込みやすいパターンを列挙。**テストセットを少しずつ足して育てた**
- **原則**: テストコードの変化は挙動変化の兆候として扱う。**「他多数」「以下同様」といった省略を禁じ**、変更ファイル・関数・参照箇所をすべて列挙して 1 つずつ等価性をチェックさせる

さらにプロンプト自体も mizchi 氏の `empirical-prompt-tuning`（対象プロンプトを毎回まっさらな別エージェントに実行させ、どこが曖昧だったか・何手かかったかで評価して改善する Skill）で複数回チューニングしている。**CI で回すには flaky を避けるため曖昧さの除去が重要だった**という。

**実績（3 ヶ月半）**:

| 指標 | 値 |
|---|---|
| 自動マージしたリファクタリング PR | 247 件 |
| チーム全 PR に占める割合 | 約 3 割 |
| 2026 年 6 月の API 利用料 | $74.48 |
| 6 月の自動マージ件数 | 55 件 |
| **1 件あたり** | **約 $1.35** |

著者は前提条件も明記している。「積み上げてきた E2E テストの資産があるからこそ、安心して自動マージできる」。

### 4.4 コーディングエージェント安全運用ガイド v0.2

**出典**: [コーディングエージェントを安全に使うための実務ガイド v0.2](https://zenn.dev/kanaria007/articles/ee3dfd438af4df)（かなりあ、2026-08-07、curl 9,713 字）

15 節構成の実務ガイド。中心となる一文が置かれている。

> AI に証拠を構造化させ、機械で検出できるものは自動化し、人間は判断に集中する。

重要なのは**変更を「複雑さ」と「リスク」の別軸で扱う**設計。「単純でも高リスクな変更はあり、複雑でも影響を限定しやすい変更はある」。

本組織にとって効く節を 4 つ抜き出す。

**§5「PR を小さく分ければ安全になるわけではない」**

> 個別 PR がすべて正しいことと、統合された機能全体が正しいことは同じではない。
> merge conflict が発生しなかったことは、**意味上の競合が存在しないことを保証しない**。

**§9「プロンプトだけで安全を守ろうとしない」**

CLAUDE.md / rules / skills に「この操作は禁止してください」と書くのは有効だが、それは安全装置の最終層ではない、という指摘。

| 層 | 例 |
|---|---|
| リポジトリ | CODEOWNERS、branch protection、required checks |
| 実行環境 | sandbox、権限制限、network 制限 |
| CI | lint、typecheck、test、SAST、dependency scan、secret scan |
| レビュー | human review、security review、domain owner review |
| リリース | feature flag、canary、rollback 手順 |

> プロンプト → 望ましい振る舞いを伝える
> CI / 権限 / repository policy → 望ましくない変更を通さない

**§10「『問題ありませんか』より『証拠を出してください』」**

> `このPRはマージして大丈夫ですか？` という問いだけを投げると、最終判定まで AI へ委譲しやすい。

代わりに、各指摘へ「根拠となるファイルや処理 / 確認できた事実 / **未確認事項**」を添えさせ、AI の役割を**判定者ではなく証拠を収集・構造化する補助者**に寄せる。

**§12「統合後レビュー」** では、確認状態を 4 値で出させる形式が提示されている。

| 状態 | 意味 |
|---|---|
| CONFIRMED | 根拠と対応する証拠を確認できた |
| PARTIAL | 一部だけ確認できた |
| UNCONFIRMED | 十分な証拠が見つからない |
| CONTRADICTED | 計画や不変条件と矛盾している |

> 根拠のない推測で CONFIRMED にしないでください。

そして §13 のポイント。**AI に「人間が確認した」と書かせない。AI が作った証拠と、人間が行った判断を分ける。**

### 4.5 承認プロンプトの見逃し率は、脅威の種類で 3 倍違う

**出典**: [40 万件の AI 承認を分析したら、見逃し率が 3 倍違った — 危ないものほど、ちゃんと止められている](https://qiita.com/jqit_suwa/items/ac7d1201bd14e9a4e1ac)（jqit_suwa / 株式会社JQIT、2026-08-06、curl 4,422 字）

公開された 409,000 件の承認/拒否判断の集計。平均正答率 66.3%。

| 脅威の種類 | 見逃し率 |
|---|---|
| 明白な破壊的操作 | 11.7% |
| 永続的な変更 | 23.8% |
| 持ち出し・コード実行 | 33.4% |
| **スコープ違反** | **35.0%** |

**いかにも危なそうなコマンドは止められている**。止められていないのは、コマンド自体は正常なのに触ってはいけない範囲に手を出しているもの。

> 承認プロンプトに出てくるのは **コマンドそのもの** です。でも危険かどうかを決めるのは、**そのコマンドが何に対して実行されるか** のほう。
> `rm -rf ./build` → 危なそうに見える が、ビルド成果物なら問題ない
> `cp config.json /tmp/` → 普通に見える が、中身が API キーなら持ち出しになる

Anthropic のテレメトリでは**ユーザーは約 93% の許可プロンプトを承認**しており、「承認を目にする回数が増えるほど、ひとつあたりに払う注意は減っていく」という指摘も引かれている。

結論は「気をつけて読む」では解決しない、というもの。

> **スコープ違反は、人間に見せる前に潰す** しかありません。
> - 触ってよいディレクトリを設定で制限する
> - 本番環境の認証情報を、そもそも実行環境に置かない
> - 到達できないホストは、ネットワークレベルで遮断する

**著者はデータの限界を自分で 3 点挙げている**（査読された研究ではない / ゲームなので脅威の割合が現実より高い（約 34%）/ 被験者が自己選択）。それでも「種類によって 3 倍違う」傾向と Anthropic の実データが同じ方向を向く点は無視しにくい、と結んでいる。

## 6. 採用候補

優先度は「本組織で実害が出ているか」と「対処コスト」で決めた。

### 候補 A: AGENTS.md を CLAUDE.md へ畳む — 優先度 **高**

**根拠**: §5.2 (a)。Codex 現用中に 2 ヶ月分の分岐が発生している。

**やること**（§3.1 の手法をそのまま適用）:

1. CLAUDE.md に `@AGENTS.md` 記載を入れるか、逆に **AGENTS.md を削除して CLAUDE.md に一本化**する
2. Skills を Codex へ渡すなら `.claude/skills/` → `.agents/skills/` の symlink（git は symlink をパス文字列として記録するため版管理できる）
3. **ただし記事の警告に従い、一律同期はしない**。Anthropic と OpenAI で推奨される指示の書き方が異なるため、rules については「ファイル一覧と読むべきタイミングだけを AGENTS.md に書き出す」方式を採る

**コスト**: 小（1 セッション）。**判断が要る点**: 一本化するか symlink 併存にするかは、笹尾さんが Codex をどの程度使い続けるかで変わる。

### 候補 B: Skill 台帳の棚卸し — 優先度 **高**

**根拠**: §5.2 (b)。CLAUDE.md の記述（12 種）と実体（17 種）の乖離、`plugins/` 未同期 3 種。

**やること**:

1. `company-evolve` / `company-quality-setup` / `company-report` を `plugins/cc-sier/skills/` へ移送（VCS 真ソース原則の回復）
2. CLAUDE.md の開発コマンド表に 4 種を追加し、「12 種類」の記述を修正
3. `diff -rq plugins/cc-sier/skills/ .claude/skills/` を定期実行できる形にする

**コスト**: 小。**これは記事由来ではなく、記事を読んだことで探しに行って見つかった問題**である。

### 候補 C: `/company-*` Skill に「分岐を持ち込まない」原則を適用 — 優先度 **中**

**根拠**: §4.2 原則 3。「どれを叩くべきかの判断こそが分岐で、抜けや取り違えの温床になる」。

cc-sier の Skill は 9 フェーズ構成で、L0 の検証手段が Skill ごとに異なる（`review-drawio.js` / `validate_drawio.py` / grep）。§4.2 の主張に照らすと、**検証コマンドを 1 本に寄せ、何を編集したかにかかわらず同じものを叩く**形が望ましい。

**未確認**: 現行 9 フェーズで実際に「どの検証を叩くべきか」の取り違えが起きているかは**測定していない**。まず task-log の `l0_retries` を集計して発生実績を確認すべきで、実績がなければ着手しない。

### 候補 D: 独立タスクは 1 メッセージで並列起動する運用の明文化 — 優先度 **中**

**根拠**: §2.1。直列サブエージェント経由（119,194 トークン）に対し並列（66,884）で 44% 減。

**やること**: `@.claude/rules/` または該当 Skill に「独立した委譲が複数あるときは 1 メッセージにまとめて起動する」を明記。

**留保**: 元データは 3 タスク・1 セットの測定で、査読も反復もない。本組織の Agent Teams は日次ダイジェストのように**重く独立性の高い**タスクで使っており、記事の測定条件（`tool_uses: 0` の一発回答）とは異なる。**同じ比率で効くとは限らない。**

### 候補 E: `deny` とディレクトリ制限の追加 — 優先度 **中**

**根拠**: §4.5。スコープ違反の見逃し率 35.0%、承認率 93%。

**やること**: `settings.local.json` に `deny` を追加し、`.companies/{他組織}/` への書き込みや `~/.ssh` 等の読み取りを構造的に止める。

**留保**: 単一開発者・本番認証情報なしの環境では、記事が想定する被害の一部は成立しない。ただし**組織横断の誤書き込み**（`@.claude/rules/multi-org.md` の「組織 A の作業で組織 B に書き込まない」）は現状プロンプトでしか守られておらず、これは §4.4 §9 の「プロンプトだけで安全を守ろうとしない」に該当する。

### 候補 F: cclens の導入 — 優先度 **中**

**根拠**: §2.4。Skill 17 種 / rules 9 本 / Subagent 20 種の効果検証が未実施。

**やること**: `brew install lambdalisue/cclens/cclens` → `cclens doctor` → `cclens overhead` で常時オンのコンテキスト量を、`cclens usage` で Skill 別使用回数を確認。

**留保**: **Windows 非対応**と記事に明記されている。本環境は WSL2（Linux）なので動く見込みだが、**未検証**。また候補 B の問題は cclens なしで見つかったので、**ツール導入を棚卸しの前提条件にしない**。

### 候補 G: 純粋リファクタリング判定ゲート — 優先度 **低**

**根拠**: §4.3。3 ヶ月半で 247 件自動マージ、1 件あたり約 $1.35。

**不採用寄りの理由**: Nature の前提は「積み上げてきた E2E テスト資産」であり、cc-sier は**主にドキュメント・図・HTML を生成するリポジトリでコードの自動テストがほとんどない**。挙動の等価性という概念自体が成立しにくい。

**ただし転用できる部分がある**:

- 出力を **JSON スキーマで縛る**（cc-sier の L2 はすでに JSON 出力だが、スキーマによる強制はしていない）
- **「他多数」「以下同様」の省略を禁じ、全件列挙させる**（L2 review-prompt に追加可能）
- `empirical-prompt-tuning` で review-prompt 自体を育てる

### 候補 H: L2 レビューを「判定」から「証拠の構造化」へ寄せる — 優先度 **中**

**根拠**: §4.4 §10 §12 §13。

現行の L2 は `verdict: pass|fail` と `composite` を返す**判定者**である。§4.4 の主張に従えば、AI には CONFIRMED / PARTIAL / UNCONFIRMED / CONTRADICTED の 4 値で確認状態を出させ、最終判定は人間と機械（L0）に残すのが筋。

**ただしこれは cc-sier の auto-merge 設計の根幹に触れる**。無人で回す前提を崩すことになるため、**変更するかは方針判断であって、記事が正しいから直す類の話ではない**。まず「L2 の findings に未確認事項の欄を追加する」という部分適用から試すのが現実的。

### 候補 I: plan モードをやめて「案をください」 — 優先度 **低**

**根拠**: §2.5。

**留保が大きい**。記事の前提は「賢いモデルに任せる雑な命令」だが、cc-sier は Skill が固定フェーズと必須セクションを持つ設計であり、方向性が逆。**個人の対話作業には効く可能性があるが、Skill 経由の作業には適用しない**のが妥当。

### 候補 J: AgentCore Gateway による Codex の Budget 制御 — 優先度 **低（時期尚早）**

**根拠**: §3.2。1 人運用ではユーザー単位のコスト帰属は過剰。要件定義書 §1.3 の Phase 2（チーム展開）に入る段階で再評価する。
