0. この記事は何か（解説）

0.1 PKB とは

PKB（Personal Knowledge Base＝個人の知識ベース） は、Obsidian の Vault（＝ Markdown ファイルを置くフォルダ）を 人間と AI の共有メモリに据える構想です。

従来「AI に文脈を渡す」といえば、その都度プロンプトに貼り付けるものでした。PKB はそれをファイルシステムに永続化し、人間も AI も同じ場所を読み書きします。

著者は前提として、AI が読むのは Obsidian そのものではなくファイルだと述べています。つまり Obsidian は人間側の窓であって、本質は「構造化された Markdown 群」です。

0.2 中核となる 3 段導線

記事の骨格はこの 3 段です。

外部ソース ──▶ Inbox/ ──▶ Daily/ ──▶ Wiki/ など Main DB
              Capture     Daily      Distill
             （自動寄り）（人間の監査盤面）（承認必須）
段役割自動化の度合い
CaptureSlack / Gmail / Calendar 等の生データを Inbox/ に取り込む自動寄り
Dailyその日 1 枚のノートに集約する人間の監査盤面
Distill永続的な知識だけを Wiki/ へ蒸留する承認必須

設計の要点は「人間は Daily 1 枚を見るだけで全体を差配できる」ことです。取り込みは自動でよいが、永続化には人間の承認を挟む。ここに線を引いています。

0.3 「0.5 から始める」の意味

著者はゼロから作って「山ほど作って山ほど壊した」経験から、土台部分をテンプレート化して公開しました。

テンプレが持ってくる（＝0.5）自分で埋める（＝残りの 0.5）
エージェント契約（AGENTS.md）モデル選択・自律度の線引きの微調整
運用ルール（frontmatter スキーマ・タグ・Inbox routing）自分の語彙・ドメイン固有の規約
skill 群（daily-briefing / inbox 集約 / eod-distill 等）要らない skill の間引き・自作
ディレクトリ雛形中身（自分の案件・ノート）
認証の雛形と接続ウィザード各サービスのトークン（自分のもの）

自動化しきれない部分を正直に切り分けているのが特徴です。認証と「毎日回して運用に定着させる」ところは、テンプレートが肩代わりできないと明言しています。

0.4 構成要素

要素役割
ObsidianPKB の人間側の窓
Codex CLIVault の整理・蒸留を担うコアエージェント
Hermes Agent外部接続の認証を一手に持つ capture 専任
Google Drive 等複数 PC での Vault 同期

Hermes に認証を集約する設計が効いています。Slack / Gmail / Calendar のトークンが 1 箇所（.hermes/.env）に集まり、コアエージェントは認証を持ちません。責務が分離されています。

0.5 セキュリティ面の設計判断

記事には慎重な判断が複数あります。

  • Gmail は件名・差出人・スニペットのみ取り込み、本文や添付は取り込まない（機密性の高いメールでも比較的安心して繋げる）
  • Slack は bot トークンではなく User Token を使う（bot をチャンネルに招待して回る手間が消える）。ただし「権限が自分のアカウントと同じ強さになる」ため取り扱いは bot 以上に慎重に、と警告
  • Codex のオプトアウトを確実に行う（認証情報に触らせるため）

0.6 日次ループ

朝  daily-briefing  → 今日・明日の予定・タスク・前日からの持ち越しを並べる
日中 aggregate 系    → Slack・メール・議事録を Daily に集約
夜  eod-distill     → 未 capture 分を取得し、Wiki へ蒸留（人間が承認）

実行は定時 cron ではなく on-demand。Daily ノートに ## 🤖 ジョブリスト があり、チェックリストを見て「これやって」と指示する形です。

記事は §7 で 4 つの詰まりどころを挙げています。本組織で起きているかを測りました。

1.3 詰まりどころ①の詳細

daily-digest: 2026-03-21 〜 2026-08-08 の 115 日分
A1+A2 の記事: 3,192 件
解析済み:     8 日分（8月のみ）= 7.0%
未解析:       107 日分

記事の表現を借りれば「capture が強力なぶん、処理が追いつかないと Inbox が生データで溢れる」状態です。

しかも本組織は日次ダイジェストが毎日自動生成され続けるため、対策しなければ差は開く一方になります。

記事が挙げる予防策は「§5 の『1 つずつ』を守る」ことだけです。つまり取り込みを増やす前に、処理できる量に合わせるという考え方で、根本的な解決策は示されていません。

2. 採用候補

候補 U: ダイジェストの未解析分をどう扱うか決める — 優先度 中

問題は「解析していないこと」ではなく、「解析していないことが可視化されていない」ことです。

現状、115 日分のうち 107 日分が未解析であることは、今回測って初めて分かりました。カタログにも insights/README.md にも「どこまで解析したか」の記録がありません。

考えられる対処は 3 つ。

案内容評価
(a) 全件を遡って解析する107 日分 × 約 28 件 = 約 3,000 件非現実的。かつ古い記事は陳腐化している
(b) 解析済み範囲を記録し、未解析であることを明示するinsights/README.md に「解析済み: 2026-08 のみ」と書く低コストで効く
(c) 定期的に直近 N 日を解析する運用にする月次で前月分を /company-digest-insights にかける継続性はあるが、運用の定着が前提

(b) を推奨します。記事の教訓は「取り込み過多は起きる」であって「全部処理しろ」ではありません。処理していない範囲を正直に示す方が、後から「これは見ていない」と判断できます。

(c) は (b) の後に検討すべきです。運用を増やす前に、まず現状を可視化する。

コスト: 小（README への追記）

候補 V: 認証を 1 箇所に集約する設計 — ❌ 不採用

記事の Hermes（認証を一手に持つ capture 専任エージェント）は優れた設計ですが、本組織には該当する課題がありません。

本組織の外部接続は GitHub（gh CLI）と MCP サーバー数種のみで、いずれも Claude Code 側で認証が完結しています。Slack / Gmail / Calendar のような多数のトークンを扱っていません。

課題がないものに構造を導入すると保守対象が増えるだけなので採りません。

候補 W: on-demand 実行（ジョブリスト方式） — 🔶 部分採用済み

記事は「定時 cron ではなく on-demand」で、Daily ノートの ## 🤖 ジョブリスト を見て指示する方式を採っています。

本組織は両方を併用しています。

本組織
定時日次ダイジェスト（cron 07:30）/ TodoInsights（05:00）/ 補完サマリー（19:00）
on-demand/company-cycle / /company-digest-insights 等の Skill

記事の「ジョブリストをチェックリストとして並べる」に相当するものは board.md にありますが、cycle 実行時に board を見る運用にはなっていません。ここは改善余地がありますが、現状で困っていないため優先度は低いです。

3. この記事から本組織が学べる点（解説）

3.1 「自動化しきれない部分を正直に切り分ける」姿勢

テンプレートが持ってくる範囲（0.5）と自分で埋める範囲（0.5）を表で明示し、認証と運用の定着はテンプレートが肩代わりできないと明言しています。

本組織の /company-spawn も同じ構造を持っています（設計書と Subagent はコピーするが、実装は自分でやる）。origin.md に未決事項を独立した節として残す運用は、この思想と一致します。

3.2 「毎日回して運用に定着させる」が最も難しい

記事の結びは「PKB は作った瞬間に完成するものではなく、毎日回しながら少しずつ自分の形に寄せていくもの」です。

本組織で /company-cycle を継続実行しているのは、まさにこの「回す」部分にあたります。ただしダイジェストの解析だけは追いついていないことが今回の実測で分かりました。

3.3 承認の線引きを保守的に始める

記事は「テンプレートの既定は保守的（削除や配分は承認前提）にしてあるので、慣れてきたら自分で緩める、くらいがちょうどよい」としています。

本組織も同じ方向です（破壊的操作は事前承認必須、auto-merge は 3 層レビュー通過が条件）。緩める方向への変更は、実績が溜まってからという順序が共通しています。
