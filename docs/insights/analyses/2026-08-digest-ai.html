2. 精読した記事と、自組織での実測

2.1 CLAUDE.md は「短く保つ」が公式の立場

出典: CLAUDE.md は21セクションか、8行か — 公式ドキュメントで決着をつけた（jqit_suwa / 株式会社JQIT）

記事の要点

「20 項目以上のテンプレートを用意すべき」（立場 A）と「8 行で十分」（立場 B）が対立していたが、公式は明確に立場 B だった。理由は 2 つ。

理由内容
毎リクエストのコンテキストに載るセッション開始時に 1 回読まれて終わりではない。API はステートレスなので毎回送り直される。100 回やり取りすれば 100 回分のトークンコスト
指示が増えると 1 つあたりの重みが下がる指示 5 個ならそれぞれに注意が払われるが、50 個あると相対的な重みが下がる。「日本語で」が「デプロイは CI/CD で自動化」と同じ重みで並ぶ

さらに現行モデルでは書くと逆効果になる指示がある。

  • 「検証しろ」は削除が正解 — Opus 5 は言われなくても自己検証する。指示が残ると二重に検証してトークンを消費する。Anthropic の移行ガイドが「書き換えるのではなく削除」と明示
  • CRITICAL: / MUST は過剰反応（overtrigger）を招く — Opus 4.5 以降は指示に忠実になったため、強い言葉が過剰に効く。公式が明言

評価

一方、強い言葉 78 箇所は多い。ただし本リポジトリの ⚠️ は「注意事項リストの見出し記号」であり、記事が指す CRITICAL: プレフィックス（個々の指示を強調する接頭辞）とは性質が異なる。同列に扱うべきかは未検証。

2.2 Skill は「弁別性」で死ぬ（トークンではない）

出典: スキルは増やしすぎると使われなくなるのか？実測したら原因はトークンではなかった（KeitoInoue / 株式会社カンリー）

記事の要点

スキルが 50 個になったとき、一度も使われないスキルが出はじめた。当初は「トークンを食うから間引くべき」と考えたが、実測で否定された。

実測値
50 スキル分のメタデータ5.2k tokens
コンテキスト全体に対する比率0.5%（上限は 1%）

真の問題は「薄いスキルの弁別性不足」だった。

トリガー例が乏しく、description が when_to_use より長いスキル——つまり「何をするか」は書いてあるが「いつ使うか」が薄いスキルは、静かに呼ばれなくなります。エラーは出ません。ただ選ばれないだけです。

さらに意味空間が重なる隣接スキル間で「票の取り合い」が起きることを実測で確認している（誤ルーティングは「起こりうる」ではなく「起きた」）。

構造の整理も有用:

層内容発火判定への影響
常時ロードfrontmatter（name / description / when_to_use）これだけが効く
オンデマンド本体（指示書 + references）一切効かない。使うまでコストゼロ

記事が提示する作成ゲート 4 問

  1. 反復性 — その作業はもう繰り返し起きたか？（先回りの投機的作成が未使用スキルの最大要因）
  2. アップリフト — 素の AI に頼むより明確に良くなるか？
  3. 区別可能性 — 隣のスキルの発火と重ならないか？
  4. オーナーと寿命 — 誰が保守し、いつ見直すか？

2.3 「緑になっていること」が一番危ない

出典: DESIGN.md を置くと、どこまで「いい感じ」になるのか — 74件を測って確かめた（aito）

記事の要点

Google Labs の DESIGN.md（デザイン意図を 1 ファイルに書いて AI に読ませる形式）を 74 件測定した記録。効くところと効かないところを分けている。

最も重要な指摘:

DESIGN.md を置いても、実装がそれに従っているかは誰も確認していません。lint は通ります。CI も緑になります。でもそれは「DESIGN.md というファイルの書式が正しい」という意味であって、画面が意図どおりかとは無関係です。

節タイトルが「一番危ないのは緑になっていること」。

この警告は本組織で既に実証されている。

L0/L1/L2 は「成果物の書式・構造・内容が基準を満たすか」を測るが、実装がそれに従うか、実用に耐えるかは測っていない。DESIGN.md と同じ構造の限界を持つ。

3. 採用候補

候補 Q: CLAUDE.md / rules の削減を検討 — 優先度 中

現状 37,309 文字。記事の立場（短く保つ）と乖離している可能性がある。

ただし即座の削減は推奨しない。 理由:

  1. @参照 された rules が常時ロードか遅延ロードかが未確定。遅延なら CLAUDE.md 本体 9,403 文字のみが毎回載ることになり、問題の規模が変わる
  2. 注意事項 28 件は実際に踏んだ事故の記録であり、削ると同じ事故が再発しうる
  3. 記事自身が別記事（コメント分量）で示したとおり、削減ルールは「有用だから消せない」で止まる

先にやるべきは測定。@参照 の挙動を公式ドキュメントで確認し、実際のトークン消費を測ってから判断する。

候補 R: Skill 作成ゲート 4 問の導入 — 優先度 中

現状 16 種で弁別性は良好だが、増やすときの歯止めがない。記事の 4 問（反復性 / アップリフト / 区別可能性 / オーナーと寿命）を skill-development.md に追加する価値がある。

とくに「先回りの投機的作成が未使用スキルの最大要因」は、本リポジトリでも将来起きうる。

候補 S: 「緑 ≠ 実用可」を明文化 — 優先度 高

L2 pass が実用可を意味しないことは、既に 2 度実証されている（設計不整合 3 件 / 「動いたが未検証」が completed）。

これは既存の候補 B（verification-pending の追加）と同じ問題を別角度から指しており、統合して扱うべき。

候補 T: when_to_use フィールドの採用 — 優先度 低

記事は when_to_use を前提に議論しているが、本リポジトリは description 内トリガー語方式で弁別性を確保できている（重複 0）。変える利益が確認できないため見送る。
