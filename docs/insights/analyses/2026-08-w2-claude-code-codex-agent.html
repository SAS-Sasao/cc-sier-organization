2.3 プロンプトキャッシュ — 「再開一発目」のコストは順番で決まる

出典: プロンプトキャッシュを意識して claude code のトークンを節約しよう（tamapon / 株式会社セレス、2026-08-04、curl 5,931 字）

「前日のやり取りを複数再開したら、まだ一言も打っていないのに 5 時間制限が 2 割持っていかれた」という実体験から書かれた記事。公式ドキュメントの参照が多く、記事内でどこが公式記載でどこが自分の推論かを明示している点が信頼できる。

キャッシュが飛ぶ条件（記事の列挙）:

条件補足

対策の中核は「順番」である。

/compact は会話履歴を短い要約に置き換える。この要約を作る処理はキャッシュがまだ生きてるうちに走るから安く済む。（中略）逆に「再開してから /compact」だと、キャッシュが切れた履歴を全部読んでから要約することになるので、再処理ぶんは丸々払う。順番が全て。

すでに切れてしまった場合は、/model で Sonnet 等に落としてから /compact し、元に戻す。全履歴の再処理 1 回は避けられないが、どのモデルに払わせるかは選べる、という理屈。

著者が「公式ドキュメントに明記がなく、記述からの帰結として書いた」と断っているのは 2 点（要約が選択中のモデルで走ること / 5 時間・週次ウィンドウ側の節約分）。この 2 点は本レポートでも未検証扱いとする。

2.5 plan モードは要らなくなった（という主張）

出典: 【Claude Code】plan モードはもう使っていない（haru067 / NOT A HOTEL、2026-07-29、curl 1,974 字）

短い記事だが論旨は明快。plan モードの役割は「判断を求める停止点」と「Edit 禁止のガードレール」の 2 つで、どちらも「案をください」と一言言うだけで解決する、という主張。

plan モードより優れている点として挙げているのが Human-in-the-Loop。

plan モードの典型的な敗北は、人間が知らない調査のコンテキストを使った結論を列挙し、人間の認知負荷を超えた読むに堪えない実装案の羅列を吐き出してしまうことだ。そして人間は読むに耐えないので脳死で許可し、あとで検証すればいいか、となる。

「案をください」なら一問一答ではなく何往復もできる、というのが利点だという。

この主張の扱いには注意が要る。 記事は Anthropic のブログ（context engineering）を根拠に「今のモデルは十分に賢いので雑な命令でよい」としているが、cc-sier は Skill が固定フェーズを持つ設計であり、「雑な命令で全部良い感じに」とは前提が異なる。§6 では優先度を低く置いた。

3.1 CLAUDE.md / AGENTS.md / Skills の二重管理をどう畳むか

出典: 【決着】Claude Code と Codex の設定ファイルを同期させる（みんな仲良く）（Kanta / 株式会社エクスプラザ、2026-07-28、curl 3,413 字）

課題の記述が、そのまま本組織に当てはまる。

同じプロジェクトで Codex と Claude Code の両方を使っているとき、AGENTS.md や SKILLS などの変更が片方にしか適用されない 何も意識せずに両方を使っていると、片方でのみ更新が入ってそのまま・・・ という状況が起きますし、なんならそれぞれ独自に分岐していく未来が容易に想像できますよね。

3.2 Codex の利用量と Budget を Gateway 層で止める

出典: Amazon Bedrock AgentCore Gateway で Codex の利用量と Budget を制御する（Yutaka Kashiwabara / NTT DATA、2026-08-07、curl 12,971 字）

AWS Samples の sample-agentcore-gateway-usage-interceptor を EC2 に構築し、Codex CLI から実際に叩いた検証記録。手順とコマンドが全部載っており、再現性が高い。

構成は、AgentCore Gateway の Interceptor をコストガバナンスのポイントとして使うもの。

  • REQUEST Interceptor: JWT からユーザーを特定 → DynamoDB から現在利用額を取得 → Daily / Monthly Budget を確認 → 超過なら モデル呼び出し前に HTTP 403
  • RESPONSE Interceptor: レスポンスの usage からトークン数を取得 → コスト算出 → CloudWatch EMF 出力 → DynamoDB へ加算

検証結果（記事の表）:

検証内容結果
Codex → AgentCore Gateway → GPT-5.4成功
DynamoDB へのユーザー別 spend 記録成功
Daily Budget 超過HTTP 403
Block 後の spend 増加なし
Monthly Budget 超過HTTP 403

著者は確認できていないことを明示している点が誠実で、そのまま引用に値する。

今回確認したのは すでに現在利用額が cap を超えているユーザーの次のリクエストを止められること です。 （中略）「Budget を超えたユーザーの次の呼び出しを止める」ことと、「設定した Budget を絶対に超過しない」ことは同じなのか という点は、もう少し検証する余地があります。

並列実行時に複数の REQUEST Interceptor が同じ現在利用額を参照して同時通過しうる、という懸念も自分で挙げている。

本組織への適用: 現状 1 人運用のため、ユーザー単位のコスト帰属は過剰。チーム展開（要件定義書 §1.3 Phase 2）に入る段階で効いてくる設計として記録する。

4.2 エージェント向けツールは MCP より CLI（設計 3 原則）

出典: AI エージェント向けのツールを、MCP ではなく CLI として作った — 設計の 3 原則（g0e / Codatum、2026-08-04、curl 13,163 字）

MCP を試していた過程で CLI に行き着いた経緯と、その設計原則。MCP を否定する記事ではないと著者自身が断っている。

転換点は、MCP 経由でファイル検証を試したときの違和感。

エージェントは、ローカルのファイルを読み込み、その内容を MCP ツールに渡すためのリクエストボディを組み立て、ツールを呼ぶ、という一連の処理を すべて自分の「頭の中」＝コンテキスト上でこなそうとします。

MCP のツールはファイルを値渡しでしか受け取れないため、1MB のノートブックを検証させたいだけでも 1MB がエージェントのコンテキストを通過する。CLI ならファイルそのものを引数にできる。

さらに、CLI は人間・CI・エージェントが同じインターフェースに乗れる。cdm notebook validate を CI で回すために MCP サーバーを立てて……とはならない。

3 原則:

原則中身
1. コンテキストを浪費させないファイル形式はモデルの事前学習を活かせるものを選ぶ（JSON/YAML は括弧・インデント・キー反復にトークンを食う → Markdown 拡張を採用）。コマンド名も validate / format という既存概念に乗せる。独自構文を発明しない。ドキュメントは全部積まず cdm doc index / doc show で取りに行かせる
2. 間違えさせない努力より、気づいて直せる設計に投資するプロンプトに禁止事項を積み上げるのをやめる。構造の誤りは validate で（行番号 + 該当行の抜粋 + 具体的な指摘 + 直し方が載った URL の 3 点セット）、見た目の誤りは PNG 出力させてエージェント自身に目視確認させる。機械的に直せるものはツールが直す（LLM はランダム文字列の生成が苦手なので ID は format が自動付与する）
3. ワークフロー全体をシンプルな一本道に設計する多段手順は 1 コマンドに畳み込む（ポーリングのループをエージェントの判断に委ねない）。検証は対象ごとに分けず validate 一発（どれを叩くべきかという判断＝分岐を持ち込まない）。流れは人間と共用のドキュメントで伝える

原則 2 の前提として著者が強調しているのが、ドキュメントの位置づけ。

エージェントに使わせるツールでは、ドキュメントは単なる付属物ではなく、コマンドと並ぶインターフェースの一部です。

原則 3 の「分岐を持ち込まない」は、cc-sier の Skill 設計に直接効く（§6 候補 C）。

4.3 「純粋リファクタリング」を証明させて自動マージする

出典: 「純粋リファクタリング」を AI に証明させて自動マージする（大塚 / Nature CTO、2026-07-31、curl 5,756 字）

3 層レビュー + auto-merge を持つ cc-sier にとって、最も参考になる 1 本。

出発点は、レビュー対象を目的で分けるという発想。リファクタリング PR で見るのは 2 軸しかない。

  1. 設計が良くなっているか（命名・責任分割・依存の方向・結合度）→ 人間の判断が要る
  2. 挙動の等価性 → 機械的

そこで前者は事前に GitHub issue や夕会で合意しておき、後者だけを AI に判断させる。AI に任せる範囲を限定することで信頼性を担保している。

実装は review-refactoring Skill + GitHub Actions。

  1. PR に /review_refactoring とコメント
  2. Actions 内で Skill 本体をそのままプロンプトとして Claude に渡し、ベースブランチとの差分をレビューさせる
  3. 出力を JSON スキーマ（pass と report_file）で縛る
  4. pass: true → approve + squash auto-merge + refactoring-only ラベル
  5. pass: false → auto-merge せず、人間レビューが必要とコメント

Skill の中身で挙げられているポイント 3 つ。

  • マインドセット: 「あなたは懐疑的な第三者レビュアーである」「『たぶん大丈夫』ではなく『証明できる』レベルで検証せよ」——AI が人間に同意しがちなことへの対策
  • 実行手順: 動作変更が紛れ込みやすいパターンを列挙。テストセットを少しずつ足して育てた
  • 原則: テストコードの変化は挙動変化の兆候として扱う。「他多数」「以下同様」といった省略を禁じ、変更ファイル・関数・参照箇所をすべて列挙して 1 つずつ等価性をチェックさせる

さらにプロンプト自体も mizchi 氏の empirical-prompt-tuning（対象プロンプトを毎回まっさらな別エージェントに実行させ、どこが曖昧だったか・何手かかったかで評価して改善する Skill）で複数回チューニングしている。CI で回すには flaky を避けるため曖昧さの除去が重要だったという。

実績（3 ヶ月半）:

指標値
自動マージしたリファクタリング PR247 件
チーム全 PR に占める割合約 3 割
2026 年 6 月の API 利用料$74.48
6 月の自動マージ件数55 件
1 件あたり約 $1.35

著者は前提条件も明記している。「積み上げてきた E2E テストの資産があるからこそ、安心して自動マージできる」。

4.4 コーディングエージェント安全運用ガイド v0.2

出典: コーディングエージェントを安全に使うための実務ガイド v0.2（かなりあ、2026-08-07、curl 9,713 字）

15 節構成の実務ガイド。中心となる一文が置かれている。

AI に証拠を構造化させ、機械で検出できるものは自動化し、人間は判断に集中する。

重要なのは変更を「複雑さ」と「リスク」の別軸で扱う設計。「単純でも高リスクな変更はあり、複雑でも影響を限定しやすい変更はある」。

本組織にとって効く節を 4 つ抜き出す。

§5「PR を小さく分ければ安全になるわけではない」

個別 PR がすべて正しいことと、統合された機能全体が正しいことは同じではない。 merge conflict が発生しなかったことは、意味上の競合が存在しないことを保証しない。

§9「プロンプトだけで安全を守ろうとしない」

CLAUDE.md / rules / skills に「この操作は禁止してください」と書くのは有効だが、それは安全装置の最終層ではない、という指摘。

層例
リポジトリCODEOWNERS、branch protection、required checks
実行環境sandbox、権限制限、network 制限
CIlint、typecheck、test、SAST、dependency scan、secret scan
レビューhuman review、security review、domain owner review
リリースfeature flag、canary、rollback 手順
プロンプト → 望ましい振る舞いを伝える CI / 権限 / repository policy → 望ましくない変更を通さない

§10「『問題ありませんか』より『証拠を出してください』」

このPRはマージして大丈夫ですか？ という問いだけを投げると、最終判定まで AI へ委譲しやすい。

代わりに、各指摘へ「根拠となるファイルや処理 / 確認できた事実 / 未確認事項」を添えさせ、AI の役割を判定者ではなく証拠を収集・構造化する補助者に寄せる。

§12「統合後レビュー」 では、確認状態を 4 値で出させる形式が提示されている。

状態意味
CONFIRMED根拠と対応する証拠を確認できた
PARTIAL一部だけ確認できた
UNCONFIRMED十分な証拠が見つからない
CONTRADICTED計画や不変条件と矛盾している
根拠のない推測で CONFIRMED にしないでください。

そして §13 のポイント。AI に「人間が確認した」と書かせない。AI が作った証拠と、人間が行った判断を分ける。

4.5 承認プロンプトの見逃し率は、脅威の種類で 3 倍違う

出典: 40 万件の AI 承認を分析したら、見逃し率が 3 倍違った — 危ないものほど、ちゃんと止められている（jqit_suwa / 株式会社JQIT、2026-08-06、curl 4,422 字）

公開された 409,000 件の承認/拒否判断の集計。平均正答率 66.3%。

脅威の種類見逃し率
明白な破壊的操作11.7%
永続的な変更23.8%
持ち出し・コード実行33.4%
スコープ違反35.0%

いかにも危なそうなコマンドは止められている。止められていないのは、コマンド自体は正常なのに触ってはいけない範囲に手を出しているもの。

承認プロンプトに出てくるのは コマンドそのもの です。でも危険かどうかを決めるのは、そのコマンドが何に対して実行されるか のほう。 rm -rf ./build → 危なそうに見える が、ビルド成果物なら問題ない cp config.json /tmp/ → 普通に見える が、中身が API キーなら持ち出しになる

Anthropic のテレメトリではユーザーは約 93% の許可プロンプトを承認しており、「承認を目にする回数が増えるほど、ひとつあたりに払う注意は減っていく」という指摘も引かれている。

結論は「気をつけて読む」では解決しない、というもの。

スコープ違反は、人間に見せる前に潰す しかありません。 - 触ってよいディレクトリを設定で制限する - 本番環境の認証情報を、そもそも実行環境に置かない - 到達できないホストは、ネットワークレベルで遮断する

著者はデータの限界を自分で 3 点挙げている（査読された研究ではない / ゲームなので脅威の割合が現実より高い（約 34%）/ 被験者が自己選択）。それでも「種類によって 3 倍違う」傾向と Anthropic の実データが同じ方向を向く点は無視しにくい、と結んでいる。

選定理由: 本編 §2.2 は「isolation: worktree をやめてシェルスクリプトにした」話だった。本記事はやめずに、フックで組む逆の結論に至っており、性質の異なる 3 プロジェクトで運用した記録がある。

結論は §2.2 と同じ方向を向いている。

実処理は決定論 CLI に集約し、スキルは「翻訳係」に徹する。 環境の作成・採番・起動・破棄というオーケストレーションを、LLM に手順として実行させない。

フック役割

8.4.1 「違反できないコード」を書かせる — ガイドとセンサーの設計

CLAUDE.md は読まれますが、従われるとは限りません。（中略）「守ってほしい」と書くことと「守られている」ことは別物という構造の問題です。 口頭で直すたびに、あなたが規約の一部を肩代わりしていることになります。

ハーネスを 2 つに分ける。

分類実行するもの性質
ガイド（フィードフォワード）設定・文書書ける範囲そのものを狭める
計算的センサーCPU 上のプログラム速い。同じ入力なら必ず同じ結果
推論的センサーLLM遅い。結果がぶれる。意味の判断ができる

cc-sier の L0（機械）/ L2（LLM）とほぼ同じ二分だが、本記事は「先に計算的センサーを作り、その限界を自分の目で確かめてから推論的センサーを作る」順序を強く推している。

実装で持ち帰れるものが 3 つある。

(a) deny の具体設計 — defaultMode: "dontAsk" + allow 列挙 + deny。deny の対象が示唆的である。

node -e や sh -c は引数の文字列を実行するため、rm を禁止しても迂回経路になる git -c キー=値 はそのコマンド 1 回だけ設定を渡す書き方で、設定ファイルは変更しないが同じ効果を持つ。片方だけ禁止しても意味がない

また Write(path) を書いたルールは受理されるが参照されない（ファイル権限の照合は Edit(path) と Read(path) のみ）という実装上の注意も書かれている。

(b) エラーメッセージは修正手順である

人間向けの lint 設定なら「禁止です」で足ります。AI に自己修正させるなら、「どこに何を定義して、どう注入するか」まで書きます。メッセージの質が、そのまま自己修正の成功率になります。

(c) 「通った」は「検査された」を意味しない — ファイルが 1 つも無い状態でも成功する検査が 5 つ中 3 つあった、という実測を示している。これは既存カタログの候補 S（緑 ≠ 実用可）と同じ主張の、より原始的な形である。

さらに手順 9 で「わざと違反コードを 3 種類書かせ、検出されるか試す」工程を置いている点が重要で、センサー自体をテストしている。

8.4.2 同じ指摘を二度させない — count で強制力を段階的に上げる

出典: Claude Code に「同じ指摘を二度させない」仕組みを hook で作った（nonchan7720、2026-08-11、curl 9,506 字）

選定理由: cc-sier の Case Bank / feedback memory と同じ問題を、強制力の側から解いている。

1 指摘 = 1 ファイル（~/.claude/feedback/{topic}.md）に永続化し、frontmatter の count（指摘された回数）から severity を自動決定する。

countpre_bash / pre_editstop_check
≥ 5deny（ツール実行を禁止）deny
3〜4ask（ユーザーに確認）block
1〜2warn（stderr に出すだけ）warn
1〜2 回目は「記録するが縛らない」暫定ルール。3 回目で確定ルールになり、5 回目で問答無用の禁止になります。指摘の重みは、指摘した回数という一番正直な指標で決まるわけです。

設計上の判断が 3 つ効いている。

  • count は自動インクリメントしない。 hook が検知した違反は「Claude が破ろうとした」だけで「人間がもう一度指摘した」わけではないため。ルールの重みを上げる権限は人間側に残す
  • 本文に「言い訳」を書かせる。 ルールを破りたくなる場面で先に立つ理屈を、あらかじめ潰した文章を同じファイルに置く
  • hook 自身は絶対に事故らせない。 3 つの hook すべてで例外を握り潰して exit 0。「検知できないことより止まらないことを優先」

コンテキスト圧迫対策として、注入は 3,000 文字の予算を設け、超えたら count の低いものから本文を落として description だけにする（重いルールほど詳しく残る優先度付き切り捨て）。

著者が挙げた限界: 47 ルール中 enforce を書けたのは 14 個だけ。「実装を先に書いてから呼び出し元を書く」のような順序のルールは、ファイル単体を見ても違反判定ができない。

8.4.3 Agent Plugins 1.0.0 — 何を標準化し、何を標準化しなかったのか

出典: Agent Plugins 1.0.0 は何を標準化し、何を標準化しなかったのか（いなりく / AWS Japan、2026-08-10、curl 17,364 字）

選定理由: 本編のクラスタ F（エージェント向けツール設計 8 件）で精読を見送った領域。cc-sier 自身がプラグイン形式であるため、標準への準拠が論点になる。

まず前提の整理が有用である。Agent Skills（Anthropic 発、中身の標準）と Agent Plugins（OpenAI 主導、箱の標準）はレイヤーが違う。

v1 が定義するのは「plugin.json + skills/ + mcp.json を入れた、検査可能なディレクトリ」だけ。hooks・subagents・rules・スラッシュコマンド・LSP 設定はすべて意図的にスコープ外である（Design Decisions いわく「クライアント固有性が強すぎて、安定したポータブル契約にはまだ早い」）。

設計として学べる点:

  • closed schema + extensions 名前空間 — トップレベルに書けるのは 10 フィールドだけ。ベンダー独自設定は逆ドメイン名前空間へ隔離する
  • 階層化された非致死エラー — サーバー 1 つの障害で「全部入りプラグイン」が全損しない。知らないフィールドは警告して無視（前方互換）、必須欠落は拒否
  • PLUGIN_ROOT / PLUGIN_DATA の分離 — 更新で差し替わるパッケージと、更新をまたいで保持される状態を最初から分ける
  • command はシェル文字列ではなく単一の実行可能トークン — 引数は args 配列に分離。コマンドインジェクションの余地を構造的に減らす
  • 「配布物の中に秘密を入れる標準的な方法は存在しない」と仕様レベルで断言

そして本組織に直接効くのが次の事実である。

TSC に参加していない Claude Code は公式の対応クライアント一覧に載っていない Claude Code のプラグインは独自形式のまま。マニフェストは .claude-plugin/plugin.json（標準はルート直下の plugin.json）

将来検討リスト（FUTURE_CONSIDERATIONS.md）を占めるのは、権限・署名・シークレット・組織統制・監査——つまり信頼とガバナンスであって、新コンポーネントの追加ではない。

著者の結論は「いま投資すべきレイヤーは Agent Skills。スキルとして書いた知見は、標準の勝敗がどう転んでもポータブル」。
