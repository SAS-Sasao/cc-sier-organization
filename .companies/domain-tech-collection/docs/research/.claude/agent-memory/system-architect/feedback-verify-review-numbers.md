L2 レビュー findings に書かれた「正しい値」をそのまま転記しない。必ず自分で再集計・再実行して確定させる。

**Why:** retail-stats-tracker 実装設計の修正で、L2 レビュアーは §4.3.2 の「旧版 11/16 合格」を「9/16 が正しい（NG 7 件）」と断定し、秘書もその前提で指示を出した。実際に旧版（整数限定 `_JPY_NUM` + カンマ除去バグ `(?=[0-9]{3}\b)`）を実装して 16 ケースを走らせると **8/16・NG 8 件**だった。レビュアーは表が太字にしていた 7 件だけを数え、表自体が誤っていた 1 件（`12,345,678万円` は旧版で 0.0678 を返すのに OK と記載）を見落としていた。findings をそのまま適用していたら誤った数値に「訂正」していた。

**2 例目（同じ文書・同じ類型）:** §9.4 U9 の「左窓の節境界を跨ぐ後方探索 → 69/84 = 82.1%」も `実測` と明記されていたが再現せず、実測は 66/84 = 78.6%。左窓の距離制限を完全撤廃した上限も 66 で、69 はそもそも到達不能だった。この値は「目標値 80% の引き下げを提案しない」根拠として使われ、要件書と CI/CD 設計にも波及していた。**将来値・到達可能性の数値ほど検算されずに既定事実化する。**

**How to apply:** 数値・件数・スコアの指摘を受けたら、(1) 比較対象の定義を本文から特定し（今回は「旧版」がどのガードを持たないかで結果が変わる。`(?<![0-9.])` を外して初めて本文の主張値 50000.0 等が再現する）、(2) 実行して確定値を得る、(3) 表・本文・テストコード・トレーサビリティ表の**全箇所**を同じ値で揃える。grep で残存を機械確認するまで完了としない。関連: [[project-retail-stats-tracker]]
