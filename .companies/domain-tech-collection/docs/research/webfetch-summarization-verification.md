## 1. 検証の目的

参照記事は「Claude Code の WebFetch は、信頼ドメイン外のページについて **Haiku による数百文字の要約**をメインモデルに渡しており、その事実が可視化されていない」と主張している。

本組織の中核ワークフロー `wf-daily-digest` は **WebFetch を第一選択**として 8 ソースを巡回している（`daily-digest-automation.yml` L225「**WebFetch ツールを第一選択**で使用」）。主張が事実なら、毎朝のダイジェストは「要約の要約」になる。

そこで **curl による原文取得と WebFetch の出力を突き合わせ**、主張を実証・反証する。

- 比較手段: `curl -sL -H "User-Agent: Mozilla/5.0"` で HTML を取得し、`script`/`style` 除去 → タグ除去 → 空白圧縮でテキスト化

## 3. 検証結果

### 3.1 【実証】全文要求が中間層に拒否される

記事 A（8,167 字）に対し「省略や要約を一切せず全文出力」を指示したところ、**記事本文ではなく一人称の断り文**が返った。

返答の要旨（原文は英語）:

- 「全文をそのまま出力せよ」という要求と、「引用は **125 文字以内**」「著作権保護された内容を再現しない」という制約が両立しないため応じられない
- 代わりに要点の要約を提供する

**これは中間に別の LLM が介在していることの直接的な証拠**である。WebFetch が単なる HTTP 取得 + Markdown 変換であれば、このような「判断」は発生しない。参照記事が指摘した **125 文字の引用制限**が実在することも裏づけられた。

### 3.2 【実証】信頼ドメインでは生 Markdown が全文通る

対照実験として D（`docs.aws.amazon.com`）に「**H2 と H3 の見出しのみ**を列挙、本文の要約は不要」と指示した。

返ってきたのは見出し一覧ではなく、**生の Markdown 全文**だった。具体的には以下が含まれていた。

- `<a name="what-is-bedrock"></a>` などの HTML アンカー
- Python コードブロック 5 種（Messages API / Responses API / Chat Completions API / Converse API / Invoke API）
- 画像の alt テキスト（`![Amazon logo with curved arrow from A to Z forming a smile.]`）
- Markdown テーブル記法（`| --- |--- |`）

**要約経路であればこれらは残らない。** 信頼ドメインではバイパスが機能し、原文がそのまま渡ることが実証された。

**副次的な発見**: バイパス経路では **prompt による絞り込みが効かない**。「見出しのみ」と明示したのに全文が返った。要約経路とバイパス経路で、prompt の扱いが非対称になっている。

### 3.3 【実証】ボイラープレートを記事内容と誤認する

記事 B（1,795 字）に「登場する固有名詞・ツール名・数値をすべて列挙」と指示したところ、固有名詞として以下が返った。

```
Claude Code / Anthropic / NOT A HOTEL / haru067 / Zenn / GitHub / Hatena / X (Twitter) / Publication
```

curl 原文と突き合わせた結果、**`Zenn` / `GitHub` / `X (Twitter)` / `Publication` は記事本文ではなくページフッターの要素**だった。原文末尾には次のフッターが含まれる。

> エンジニアのための 情報共有コミュニティ About Zennについて 運営会社 お知らせ・リリース Guides 使い方 法人向けメニュー … X(Twitter) connpass GitHub … 利用規約 プライバシーポリシー 特商法表記

参照記事が挙げた GitHub Issue **#53297「ページテンプレートが事実と誤認される問題」の実例を再現**したことになる。

「この記事は GitHub と X (Twitter) に言及している」と受け取れば、事実誤認がそのまま下流に流れる。

### 3.4 【実証】根拠リンクと具体的主張の欠落

記事 B の原文には、著者の主張を支える**一次情報へのリンク**が含まれている。

```
https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models
```

原文はこのリンクとあわせて「Anthropic のブログでも言及されていて、現に opus5 ではシステムプロンプトを削るような調整が入っている」と述べているが、**WebFetch の出力にはリンクも当該主張も含まれなかった**。

日次ダイジェストは「出典 URL 付きで一次情報に到達できること」を要件としている（`/company-diagram` 系の FR-17 と同じ思想）。記事内リンクが落ちると、**記事から先の一次情報に到達する経路が失われる**。

### 3.5 【確認】表記の正規化

WebFetch はツール名を `Opus 5` として返したが、原文の表記は `opus5`（小文字・空白なし）だった。

軽微だが、**原文検索で照合できない形に変形されている**。`grep "Opus 5"` では原文にヒットしない。ダイジェストの記述を後から検証する際に、原文との突き合わせが失敗する要因になる。

### 3.6 短い記事では情報量が保たれる

記事 B（1,795 字）では見出し 3 件・固有名詞・数値が具体的に返り、**見出しはすべて原文に実在**した（`planモードがなぜ必要だったのか` / `2026/7にやるなら、もっと適当でいい` / `「案をください」メソッドの利点`）。

一方、記事 A（8,167 字）は全文要求が拒否された。**記事の長さによって挙動が変わる**という参照記事の主張と整合する。

## 5. 本組織への影響

### 5.1 日次ダイジェストの全ソースが信頼ドメイン外

`wf-daily-digest` が巡回する 8 ソースを、参照記事が挙げた信頼ドメイン群（`docs.python.org` / `developer.mozilla.org` / `react.dev` / `kubernetes.io` / `docs.aws.amazon.com` など）と照合した。

| ソース | 信頼ドメイン |
|---|---|
| Zenn | ✗ |
| Qiita | ✗ |
| はてなブックマーク | ✗ |
| DevelopersIO | ✗ |
| AWS What's New / AWS Blog | ✗（`aws.amazon.com` であって `docs.aws.amazon.com` ではない） |
| 流通ニュース | ✗ |
| ダイヤモンド・チェーンストア | ✗ |
| ネットショップ担当者フォーラム | ✗ |

**8/8 が要約経路**にあたる。ダイジェストは次の二重要約になっている。

```
記事原文 → [中間 LLM] 数百字に要約 → [Opus] 章立て・1文要約 → MD
```

### 5.2 L2 レビューはこの欠落を検出できない

`/company-daily-digest` の L2 は 6 軸で採点するが、**評価対象は生成された MD であり原文ではない**。「渡された要約を正しく整形できたか」は見ているが、「原文に対して忠実か」は構造的に検証できない。

composite 0.98 という高スコアは、この経路の健全性を意味しない。

### 5.3 過去の事象との整合

2026-07-26 の設計タスクで、L2 レビュアーが「カタログの DCM +17.4% は digest に存在しない」と指摘したが、実際には `2026-06-27.md` / `2026-06-28.md` に実在した（流通ニュース s062681）。

当時は「レビュアーの誤検知」として処理したが、**要約経路による情報欠落が背景にあった可能性**がある。本検証で確認した「根拠リンクの欠落」「表記の正規化」は、いずれも後からの照合を失敗させる方向に働く。

## 6. 対策

### 6.1 curl による原文取得は実際に機能する

本検証で A〜C の 3 記事すべてを curl で取得できた（HTTP 200、8,167 / 1,795 / 8,943 字）。Zenn は SSR のため、HTML から本文テキストを抽出できる。

`daily-digest-automation.yml` には既に curl fallback の記述がある（L174「万一 WebFetch が blocked の場合、Claude に Bash+curl fallback を明示指示」）。ただしこれは **Issue #690「WebFetch 無効化」への対策**であり、**要約経路を回避する目的では位置づけられていない**。

→ fallback ではなく**第一選択を curl に切り替える**ことを検討する価値がある。

### 6.2 段階的な対応案

| 段階 | 内容 | コスト |
|---|---|---|
| 1 | ダイジェストの巡回を curl 主体に変更し、WebFetch は補助に回す | 中（workflow の prompt 改修） |
| 2 | 収集した本文を中間ファイルに保存し、要約の根拠を後から検証可能にする | 中（保存先とサイズ管理の設計が必要） |
| 3 | L2 に「原文との照合」軸を追加する | 大（原文保存が前提。段階 2 に依存） |

**段階 1 を推奨**。curl は追加依存がなく、workflow に既に記述がある。

### 6.3 適用範囲の注意

本検証は「**要約経路が存在し、情報が落ちる**」ことを示したが、「**ダイジェストの品質が実用に耐えない**」ことは示していない。

記事 B では見出し 3 件すべてが原文に実在し、要点も正確だった。短い記事では要約でも十分な情報量が保たれる。過剰反応してすべてを curl 化すると、HTML パースの保守コストが発生する。

**判断材料**: 落ちるのは「一次情報へのリンク」「具体的な数値の文脈」「原文の表記」であり、**後から検証・追跡する用途で効いてくる**。日次の読み物としては要約でも成立するが、提案資料の根拠にする用途では原文が要る。
