## 2. 精読した記事と、自組織での実測

### 2.1 CLAUDE.md は「短く保つ」が公式の立場

**出典**: [CLAUDE.md は21セクションか、8行か — 公式ドキュメントで決着をつけた](https://qiita.com/jqit_suwa/items/cea574550613de33a114)（jqit_suwa / 株式会社JQIT）

#### 記事の要点

「20 項目以上のテンプレートを用意すべき」（立場 A）と「8 行で十分」（立場 B）が対立していたが、**公式は明確に立場 B** だった。理由は 2 つ。

| 理由 | 内容 |
|---|---|
| **毎リクエストのコンテキストに載る** | セッション開始時に 1 回読まれて終わりではない。API はステートレスなので毎回送り直される。**100 回やり取りすれば 100 回分**のトークンコスト |
| **指示が増えると 1 つあたりの重みが下がる** | 指示 5 個ならそれぞれに注意が払われるが、50 個あると相対的な重みが下がる。「日本語で」が「デプロイは CI/CD で自動化」と同じ重みで並ぶ |

さらに**現行モデルでは書くと逆効果になる指示**がある。

- **「検証しろ」は削除が正解** — Opus 5 は言われなくても自己検証する。指示が残ると二重に検証してトークンを消費する。Anthropic の移行ガイドが「書き換えるのではなく削除」と明示
- **`CRITICAL:` / `MUST` は過剰反応（overtrigger）を招く** — Opus 4.5 以降は指示に忠実になったため、強い言葉が過剰に効く。公式が明言

#### 自組織での実測

| 指標 | 実測値 |
|---|---|
| `CLAUDE.md` | 203 行 / **9,403 文字** / セクション 9 / 注意事項（⚠️❌）**28 件** |
| `.claude/rules/` | 9 ファイル / 992 行 |
| **CLAUDE.md + rules 合計** | **37,309 文字** |
| CLAUDE.md 内の `@参照` | 13 箇所 |

強い言葉の出現数:

| 語 | CLAUDE.md | rules |
|---|---|---|
| 必須 | 8 | 19 |
| 禁止 | 9 | 5 |
| 必ず | 3 | 6 |
| ⚠️ | 22 | — |
| ❌ | 6 | — |
| **計** | **48** | **30** |

**合計 78 箇所**。記事が警告する `CRITICAL` / `MUST` の日本語版に相当する。

#### 評価

**「検証しろ」型の指示は本リポジトリには無い**（`検証` の出現は curl ルールと不確実性ルールの文脈のみ）。この点は問題ない。

一方、**強い言葉 78 箇所は多い**。ただし本リポジトリの ⚠️ は「注意事項リストの見出し記号」であり、記事が指す `CRITICAL:` プレフィックス（個々の指示を強調する接頭辞）とは性質が異なる。**同列に扱うべきかは未検証**。

`@参照` された rules が常時ロードされるか遅延ロードかは、**Claude Code の内部実装が公開されていないため確定できない**。もし常時ロードなら 37,309 文字が毎リクエストに載ることになり、記事の警告が強く当てはまる。

### 2.2 Skill は「弁別性」で死ぬ（トークンではない）

**出典**: [スキルは増やしすぎると使われなくなるのか？実測したら原因はトークンではなかった](https://zenn.dev/canly/articles/43bef1eacdae44)（KeitoInoue / 株式会社カンリー）

#### 記事の要点

スキルが 50 個になったとき、一度も使われないスキルが出はじめた。当初は「トークンを食うから間引くべき」と考えたが、**実測で否定された**。

| 実測 | 値 |
|---|---|
| 50 スキル分のメタデータ | 5.2k tokens |
| コンテキスト全体に対する比率 | **0.5%**（上限は 1%） |

**真の問題は「薄いスキルの弁別性不足」**だった。

> トリガー例が乏しく、description が when_to_use より長いスキル——つまり「何をするか」は書いてあるが「いつ使うか」が薄いスキルは、**静かに呼ばれなくなります**。エラーは出ません。ただ選ばれないだけです。

さらに**意味空間が重なる隣接スキル間で「票の取り合い」が起きる**ことを実測で確認している（誤ルーティングは「起こりうる」ではなく「起きた」）。

構造の整理も有用:

| 層 | 内容 | 発火判定への影響 |
|---|---|---|
| 常時ロード | frontmatter（name / description / when_to_use） | **これだけが効く** |
| オンデマンド | 本体（指示書 + references） | **一切効かない**。使うまでコストゼロ |

#### 記事が提示する作成ゲート 4 問

1. **反復性** — その作業はもう繰り返し起きたか？（**先回りの投機的作成が未使用スキルの最大要因**）
2. **アップリフト** — 素の AI に頼むより明確に良くなるか？
3. **区別可能性** — 隣のスキルの発火と重ならないか？
4. **オーナーと寿命** — 誰が保守し、いつ見直すか？

#### 自組織での実測

| 指標 | 実測値 |
|---|---|
| Skill 数 | 16 種 |
| **frontmatter 合計** | **3,680 文字**（記事の 50 スキル = 5.2k tokens より小さい） |
| SKILL.md 本体 合計 | 110,276 文字（**オンデマンドなので発火判定には無関係**） |
| `when_to_use` を持つ Skill | **0 / 16** |
| frontmatter 内トリガー語（「」で囲まれた語） | 81 語 |
| **複数 Skill で重複するトリガー語** | **0 語** |

意味が近いペアの重なりも確認した。

| ペア | 共通トリガー語 |
|---|---|
| `company-diagram` × `company-diagram-v2` | **0** |
| `company-report` × `company-cycle` | **0** |
| `company-daily-digest` × `company-digest-html` | **0** |
| `company-dashboard` × `company-handover` | **0** |

#### 評価

**票の取り合いは起きていない。** 81 語すべてがユニークで、意味が近いペアでも重複ゼロ。記事が実測で確認した誤ルーティングのリスクは、本リポジトリでは現状顕在化していない。

`when_to_use` フィールドは 0/16 だが、**description 内に「〜と言われたときに使用する」形式でトリガー語を書く方式**を採っており、弁別性は別の手段で確保されている。

トークン面も 3,680 文字と小さく、記事の結論（トークンを理由にした間引きは成立しない）が本リポジトリでも当てはまる。

### 2.3 「緑になっていること」が一番危ない

**出典**: [DESIGN.md を置くと、どこまで「いい感じ」になるのか — 74件を測って確かめた](https://zenn.dev/ait/articles/google-design-md-measured)（aito）

#### 記事の要点

Google Labs の DESIGN.md（デザイン意図を 1 ファイルに書いて AI に読ませる形式）を 74 件測定した記録。効くところと効かないところを分けている。

最も重要な指摘:

> DESIGN.md を置いても、**実装がそれに従っているかは誰も確認していません**。lint は通ります。CI も緑になります。でもそれは「DESIGN.md というファイルの書式が正しい」という意味であって、画面が意図どおりかとは無関係です。

節タイトルが「**一番危ないのは緑になっていること**」。

#### 本組織での該当

**この警告は本組織で既に実証されている。**

| 事象 | 内容 |
|---|---|
| L2 pass 後の設計不整合 | `retail-stats-tracker` は L2 composite **0.88 pass** だったが、実装フェーズで設計不整合が **3 件**報告された（#724 / #728 / #729） |
| 「動いた」と「使える」の乖離 | M3 の関連タスクはすべて `completed` だが、NFR-05 は 67.09% で未達、`no_metric_match_in_multi_value` が 29 件残存 |

L0/L1/L2 は「成果物の書式・構造・内容が基準を満たすか」を測るが、**実装がそれに従うか、実用に耐えるかは測っていない**。DESIGN.md と同じ構造の限界を持つ。

## 3. 採用候補

### 候補 Q: CLAUDE.md / rules の削減を検討 — 優先度 **中**

現状 37,309 文字。記事の立場（短く保つ）と乖離している可能性がある。

**ただし即座の削減は推奨しない。** 理由:

1. `@参照` された rules が常時ロードか遅延ロードかが**未確定**。遅延なら CLAUDE.md 本体 9,403 文字のみが毎回載ることになり、問題の規模が変わる
2. 注意事項 28 件は**実際に踏んだ事故の記録**であり、削ると同じ事故が再発しうる
3. 記事自身が別記事（コメント分量）で示したとおり、**削減ルールは「有用だから消せない」で止まる**

**先にやるべきは測定**。`@参照` の挙動を公式ドキュメントで確認し、実際のトークン消費を測ってから判断する。

### 候補 R: Skill 作成ゲート 4 問の導入 — 優先度 **中**

現状 16 種で弁別性は良好だが、**増やすときの歯止めがない**。記事の 4 問（反復性 / アップリフト / 区別可能性 / オーナーと寿命）を `skill-development.md` に追加する価値がある。

とくに「**先回りの投機的作成が未使用スキルの最大要因**」は、本リポジトリでも将来起きうる。

### 候補 S: 「緑 ≠ 実用可」を明文化 — 優先度 **高**

L2 pass が実用可を意味しないことは、既に 2 度実証されている（設計不整合 3 件 / 「動いたが未検証」が completed）。

これは既存の**候補 B（`verification-pending` の追加）と同じ問題**を別角度から指しており、統合して扱うべき。

### 候補 T: `when_to_use` フィールドの採用 — 優先度 **低**

記事は when_to_use を前提に議論しているが、本リポジトリは description 内トリガー語方式で弁別性を確保できている（重複 0）。**変える利益が確認できない**ため見送る。
