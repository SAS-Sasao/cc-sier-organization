## 1. 記事の要旨

数十〜数百件のタスクを含む開発では「この不具合を直して」式の指示が通用しない。著者が挙げる症状は具体的である。

- どのタスクを作業中か分からなくなる
- 依頼していない範囲まで変更される
- **実装済みと検証済みが混同される**
- 「完了しました」と報告されたが実環境では動かない
- 新しく見つかった問題が作業中のタスクへ混ぜ込まれる

著者の立脚点は、**これらが AI のコーディング能力では解決しない**という認識にある。必要なのは「AI が迷わず作業でき、**人間があとから検証できる形**にタスクを設計すること」。

### 中核の 6 原則

1. `task-list.md` を進捗管理の**唯一の正本**にする
2. 原則として**進行中タスクを 1 件に限定**する
3. 複数 AI を使うなら**役割とコンテキストの境界**を決める
4. 目的・変更範囲・禁止事項・完了条件・停止条件を明文化する
5. 実装・テスト・文書更新・Git 操作を**一つの作業単位**にする
6. **AI の自己申告ではなく、差分・テスト結果・実環境の証拠で完了を判定**する

## 2. 主要な論点

### 2.1 チャットは正本に向かない

新セッションで決定が引き継がれない、方針変更が正式仕様か分からない、完了の根拠が追跡できない。そこで会話の外に「現在の正しい状態」を残す。

`docs/task-list.md` に ID / タスク名 / 状態 / 進捗 / 依存 / **完了条件** / **証拠** を表形式で保持する。

運用ルールが 2 点ある。

- **タスク ID を再利用しない** — 過去のコミット・PR・会話に書かれた ID が別の意味になるため。取りやめは行削除でなく「中止」に状態変更し理由を残す
- **新しい問題は新しいタスクとして登録** — 現タスクの完了条件に必須か / 別か / 無関係かで切り分ける。これをやらないと 1 件が際限なく膨らむ

### 2.2 1 タスクに含める 6 項目

| 項目 | 要点 |
|---|---|
| 目的 | 「何を」でなく「**なぜ**」。エラーを隠すのでなく利用者が期待する状態を基準にできる |
| 変更範囲 | 「ついでのリファクタリング」を防ぐ |
| 禁止事項 | 「テストを通すために期待値を実装へ合わせない」「**不明点を推測で埋めない**」 |
| 完了条件 | 第三者が Yes/No で判定できる形に。「適切に動作すること」は基準にならない |
| テスト方法 | どの層で何を確認するか。**行っていないテストも区別して報告させる** |
| 停止条件 | AI が勝手に判断してはいけない境界 |

著者は停止条件を「AI の能力を制限するものではなく、**人間が判断すべき箇所をあらかじめ切り分けるもの**」と位置づけている。

### 2.3 状態を 7 段階に分ける（本記事で最も実務的な提案）

未着手 / 調査中 / 実装中 / ローカル検証済み / **実環境検証待ち** / 完了 / 保留。

この区別がないと AI はコードを書いた時点で完了と報告し、人間は実環境で使える状態だと誤認する。実環境でしか確認できない項目が残るなら、無理に 100% にせず「実装完了・実環境検証待ち」とする。

### 2.4 完了報告は「作業内容」でなく「証拠」

求めるのは開始時 / 終了時の HEAD、テスト件数と結果、**未実施の検証項目**、コミット SHA など。

著者の表現を借りれば、すべて成功したように見せることではなく、**未確認事項を未確認のまま正確に報告すること**が要点である。

### 2.5 失敗例 7 件（実体験ベース）

とくに失敗例 1 が具体的で、示唆が大きい。

ChatGPT を GitHub 連携し実装を Claude Code に依頼したところ、両者が同じリポジトリと設計書を読み直すラリーが発生。確認精度は読み込み量に比例せず、**トークンだけが異常に消費された**。

著者の分析が鋭い。問題は複数 AI を使ったことでも広い範囲を任せたことでもなく、**ハーネス側で責務・受け渡し情報・再読み込み範囲・完了判定者を設計しないまま、両方に全体を理解させようとしたこと**にある。

対処として ChatGPT を要件整理とレビュー、Claude Code を実装とテストに限定し、受け渡しを「対象タスク / 変更対象 / 完了条件 / 差分 / テスト結果 / 未確認事項」だけに絞った。

残る 6 件: 一度に複数タスクを依頼 / 「残りをいい感じに進めて」/ AI の完了報告だけで 100% にする / テストを通すために仕様を変える / ドキュメント更新だけが進む / **同じ失敗をプロンプトで毎回注意する**。

最後の対策が「繰り返すルールは `AGENTS.md` / `CLAUDE.md` へ移す。機械的に検出できるものは CI や lint へ移す」。

## 3. 本組織の運用との対比

記事の主張と cc-sier の現行運用を突き合わせた。**多くは既に実装されている**が、1 点だけ明確な欠落がある。

| # | 記事の主張 | cc-sier の現状 | 判定 |
|---|---|---|---|
| 1 | `task-list.md` を唯一の正本にする | WBS markdown を SSoT とする三層モデル（`todo-management.md`）。Issues / Projects v2 は派生ビュー | **実装済み・より厳密** |
| 2 | 進行中タスクを 1 件に限定 | 明文化なし。ただし実運用では 1 件ずつ進んでいる（`status: in-progress` は現在 4 件、うち大半は放置された古いもの） | **部分的** |
| 3 | 複数 AI の役割とコンテキスト境界 | 19 種の Subagent に責務を定義。maker-checker 分離（`retail-stats-qa` は Bash あり Write なし）。L2 は fresh general-purpose | **実装済み・より厳密** |
| 4 | 目的・変更範囲・禁止事項・完了条件・停止条件の明文化 | `CLAUDE.md` に禁止事項 12 件、`rules/` に 7 ファイル。停止条件は「破壊的操作は事前承認必須」等 | **実装済み** |
| 5 | 実装・テスト・文書更新・Git を一つの単位に | Skill の 9 フェーズ統合実行フローがこれに相当（生成 → L0 → L1 → L2 → PR → task-log 完了） | **実装済み** |
| 6 | 自己申告でなく証拠で完了判定 | 3 層レビュー（L0 機械 / L1 構造 / L2 独立 LLM）+ task-log に `l2_composite` 等を記録 | **実装済み・より厳密** |
| — | **状態を 7 段階に分ける** | **`in-progress` / `completed` / `blocked` の 3 値のみ** | **❌ 欠落** |

### 3.1 唯一の明確な欠落: 「実環境検証待ち」に相当する状態がない

現行の task-log は `status` が 3 値で、実測では以下の分布になっている。

```
completed    199 件
in-progress    4 件
blocked        0 件
```

`blocked` は定義されているが**一度も使われていない**。そして「コードは動いたが実環境での確認が残っている」を表す状態が存在しない。

**これは実際に問題になりうる状況が既に発生している。**

`retail-stats-tracker` の M3 は実装が完了し、実データ（observations 71 件）が生成・配信された。task-log 上は関連タスクがすべて `completed` である。しかし:

- NFR-05 は 51/80 = 63.75% で目標 80% に未達
- `no_metric_match_in_multi_value` が 29 件残っている
- 提案資料の根拠として使える品質かは未検証

つまり「**動いた**」と「**使える**」の間にある状態が、記録上どこにも現れない。記事が指摘する「AI はコードを書いた時点で完了と報告し、人間は実環境で使える状態だと誤認する」構図に、そのまま当てはまる。

### 3.2 進行中タスク 1 件制限は明文化されていない

実運用では 1 件ずつ進んでいるが、ルールとして書かれていない。`status: in-progress` が 4 件あるのは、完了時に更新し忘れた古いログが残っているためで、同時並行していたわけではない。

ただし cc-sier は **Agent Teams による並列実行**を前提とする設計であり、記事の「1 件に限定」をそのまま適用すべきではない。記事自身も「独立性の高い調査やテストに限定して並列化してよい」「ブランチや worktree を分離する」と条件付きで認めている。

cc-sier の並列は「1 タスク内で複数 Subagent が異なる成果物を分担する」形であり、記事が警告する「同じリポジトリで複数タスクが同時に同じファイルへ変更を加える」形とは異なる。**現状の運用で問題は生じていない。**

## 4. 取り入れる価値があるもの

### 4.1 task-log の `status` に検証段階を追加する（推奨）

3 値を次のように拡張することを提案する。

| 状態 | 意味 |
|---|---|
| `in-progress` | 作業中（現行のまま） |
| **`verification-pending`** | **成果物は生成されたが、実用可否の検証が残っている**（新設） |
| `completed` | 完了条件と必要な検証をすべて満たした |
| `blocked` | 外部回答・権限・仕様決定を待っている（現行のまま。未使用） |

記事は 7 段階だが、cc-sier には既に L0/L1/L2 の 3 層レビューがあり、「ローカル検証済み」に相当する情報は `l2_composite` で表現されている。**不足しているのは「レビューは通ったが実用検証が残る」段階のみ**なので、1 値の追加で足りる。

適用例: `retail-stats-tracker` の M3 関連タスクは `verification-pending` が適切だった。NFR-05 未達と `no_metric_match_in_multi_value` 29 件が未処理のまま `completed` になっている。

### 4.2 「未確認事項を未確認のまま報告する」の明文化（推奨）

cc-sier の 3 層レビューは成果物の品質を測るが、「**何を検証していないか**」を報告させる仕組みはない。

L2 の採点は 6 軸すべてにスコアが付くため、「この軸は検証できなかった」という状態を表現できない。実際、`analyses/webfetch-summarization.md` の検証では「未検証事項」を独立した章として設けたが、これは秘書の判断であってルール化されていない。

→ task-log のテンプレートに「未検証事項」欄を設けることを検討する価値がある。

### 4.3 タスク ID の再利用禁止（既に満たしている）

cc-sier の task-id は `YYYYMMDD-HHMMSS-{slug}` 形式でタイムスタンプを含むため、構造的に再利用が起きない。**明文化は不要。**

## 5. 取り入れるべきでないもの

### 5.1 進行中タスクの 1 件制限

前述のとおり、cc-sier の並列は「1 タスク内での Subagent 分担」であり、記事が警告する形とは異なる。一律に 1 件制限を導入すると Agent Teams の設計思想と衝突する。

ただし記事の警告自体は有効で、**同一ファイルへ複数 Subagent が同時に書き込む形は避ける**という原則は既に運用されている（設計 3 冊の並列生成では担当ファイルを分けた）。

### 5.2 `task-list.md` の新設

cc-sier は既に WBS markdown を SSoT とする三層モデルを持っており、記事の `task-list.md` より厳密である（Issues / Projects v2 との同期ルール、完了判定の 4 条件、停滞検知まで定義済み）。**屋上屋を架す必要はない。**

---

## 6. 総括

記事の 6 原則のうち **5 つは cc-sier で既に実装済み**であり、多くはより厳密な形になっている。これは cc-sier が「AI に任せる範囲を広げるほど、役割・情報の流れ・完了条件を判定可能な形へ変える」という記事の結論と同じ方向で設計されてきたことを示す。

**唯一かつ明確な欠落が「実装済みと完了の分離」**である。しかもこれは理論上の欠落ではなく、`retail-stats-tracker` で実際に「動いたが使えるか未検証」の状態が `completed` として記録される事態が発生している。

対処は `status` への 1 値追加（`verification-pending`）で足りる。既存の 3 層レビューが「ローカル検証済み」相当を担っているため、記事の 7 段階をそのまま導入する必要はない。
