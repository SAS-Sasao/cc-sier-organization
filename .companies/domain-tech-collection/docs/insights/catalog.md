## 0. このカタログの使い方

「いずれ採用するか考える」ための材料を 1 箇所に集約したもの。各知見について次を記録する。

- **何を主張しているか**（要点のみ。詳細は個別レポートへ）
- **本組織での採用状況**（採用済み / 未採用 / 不採用 + 理由）
- **適用先**（cc-sier 本体 / 派生アプリ / 両方）
- **採用する場合のコスト**と、判断に必要な追加情報

採用状況の凡例:

| 記号 | 意味 |
|---|---|
| ✅ | 採用済み（実装または明文化されている） |
| 🔶 | 部分採用（一部のみ / 明文化されていない） |
| ⬜ | 未採用（検討対象） |
| ❌ | 不採用（理由あり） |

## 1. Skills は「コード」ではなく「手順書」である

**出典**: [Claude CodeのSkillsは「手順書」だったので、/article コマンドを作ってみた](https://zenn.dev/osakayakyu/articles/e6aa9835c04d73)（KoH / 2026-08-02、curl で原文取得 6,783 字）

### 主張

Claude Code の Skill は、スクリプトや拡張機能ではなく **`SKILL.md` に自然言語で書いた作業手順書**である。「この順番で」「これは出さない」「ここで確認する」を書くだけで動く。

著者は `/article`（セッションの学びを Zenn 記事の下書きにする）を実例として提示している。

### 中核の設計原則

> 自動化の目的は、確認をなくすことではなく、**確認する前の面倒な作業を減らすこと**

この原則から、著者は「AI に任せる範囲」と「人間が見る範囲」を明示的に分離している。

| AI に任せる | 人間が見る |
|---|---|
| セッションを振り返る / 学びを選ぶ / Markdown に整える / 機密情報を落とす / **下書きとして**保存する | 外に出してよい内容か / 社内情報が残っていないか / 技術的な正しさ / **公開してよいか** |

具体的な安全策として:

- **`published: false` を必ず入れる**。公開は別コマンドで明示的に実行する（「ここは絶対に分けた方がいい」）
- 業務情報はそのまま使わず、Todo アプリ等の一般的な題材に置き換える
- push 前の確認では、**文章の質より先に「外に出してよいか」を見る**

### 本組織との対比

| 論点 | cc-sier の現状 | 採用状況 |
|---|---|---|
| Skill は手順書である | 16 種の Skill がすべて `SKILL.md` の手順書形式。1,500〜2,000 語制約 + `references/` への外出しまで規定 | ✅ |
| 自動化範囲と人間の判断の分離 | 破壊的操作は事前承認必須。auto-merge は 3 層レビュー通過が条件 | ✅ |
| **公開判断を自動化しない** | **`/company-spawn` でリポジトリを作成する際、public/private をオーナーに確認している**（2026-08-02 の実績）。ただし**ルールとして明文化されていない** | 🔶 |
| 機密情報のマスキング | `.conversation-log/` は「顧客案件混入時はマスキング必須」と CLAUDE.md に記載 | 🔶 |
| 外部公開前のレビュー観点 | 明文化なし | ⬜ |

### 採用候補

**(A) 外部公開を伴う操作の確認ルールを明文化する** — ⬜ 未採用

現状は個別の判断で確認しているが、ルールがない。本組織で外部公開が発生するのは:

- `/company-spawn` でのリポジトリ作成（public/private）
- GitHub Pages への配信（`docs/` 配下）
- Issue / PR の本文（public リポジトリでは全世界に見える）

記事の「push 前の公開レビュー」に相当する観点リスト（社名 / 内部 URL / 顧客情報 / 本番環境情報 / エラー文の固有情報）を、`.claude/rules/` に持つ価値がある。

**コスト**: 小（ルールファイル 1 本）
**判断に必要な情報**: 本組織で公開事故のリスクがどれだけあるか。`.companies/` は現状すべて自組織の情報のみ

## 2. タスク管理 — 「実装済み」と「完了」を分ける

**出典**: [Claude Code／Codexに中〜大規模開発を任せるためのタスク管理](https://qiita.com/Y-Y-dev/items/d526fb7cdbe35a3f9384)（Y-Y-dev / 2026-08-01、curl で原文取得 12,458 字）
**詳細レポート**: `analyses/task-management.md`

### 主張の 6 原則と採用状況

| # | 主張 | cc-sier | 状況 |
|---|---|---|---|
| 1 | `task-list.md` を唯一の正本に | WBS を SSoT とする三層モデル（より厳密） | ✅ |
| 2 | 進行中タスクを 1 件に限定 | 明文化なし。ただし Agent Teams の設計と衝突 | ❌ |
| 3 | 複数 AI の役割とコンテキスト境界 | 19 Subagent + maker-checker 分離 | ✅ |
| 4 | 目的・範囲・禁止・完了・停止条件の明文化 | CLAUDE.md 禁止事項 12 件 + rules/ 8 ファイル | ✅ |
| 5 | 実装・テスト・文書・Git を一単位に | Skill の 9 フェーズ統合実行フロー | ✅ |
| 6 | 証拠で完了判定 | 3 層レビュー + task-log 記録 | ✅ |
| — | **状態を 7 段階に分ける** | **3 値のみ** | ⬜ |

### 採用候補

**(B) task-log の `status` に `verification-pending` を追加** — ⬜ 未採用・**優先度高**

実測: `completed` 199 件 / `in-progress` 4 件 / `blocked` **0 件**（定義されているが未使用）。

「コードは動いたが実環境での確認が残っている」を表す状態がない。**これは理論上の欠落ではない** — `retail-stats-tracker` の M3 は実装完了・実データ配信済みで関連タスクはすべて `completed` だが、NFR-05 は 63.75% で未達、`no_metric_match_in_multi_value` が 29 件残存している。

**コスト**: 小〜中。ただし後方互換性の確認が要る
**判断に必要な情報**: `rebuild-case-bank.sh` / `generate-dashboard.sh` が `status` 値をどう参照しているか（未確認）

**(C) 「未検証事項」欄を task-log に設ける** — ⬜ 未採用

3 層レビューは成果物の品質を測るが、「**何を検証していないか**」を報告させる仕組みがない。L2 は 6 軸すべてにスコアが付くため「この軸は検証できなかった」を表現できない。

**コスト**: 小（テンプレート変更のみ）

## 4. レビューループの品質管理（設計済み・未実装）

**出典**: 2026-07-25 の日次ダイジェスト A1 章（keep-best / Review Definition / 承認キュー）
**詳細レポート**: `keep-best-review-retry-requirements.md`（401 行、L2 composite 0.88 pass）

### 採用候補

**(F) keep-best リトライ** — ⬜ 設計完了・未実装

現行は「L2 fail → 1 回修正 → 再採点 → fail なら中止」で、**修正で composite が下がっても劣化版が残る**。各試行のスナップショットを保持し、致命軸 fail でない中で composite 最良の版を採用する。

要件定義で確定済みの重要事項:
- **致命軸 fail の版は composite がどれだけ高くても採用禁止**
- 同点タイブレークは試行番号の小さい方（変更量が少ない方）
- **L2 のみリトライ上限を 1 → 2 回に拡張**、L0/L1 は 1 回維持

**コスト**: 中〜大（5 Skill への横断改修）
**判断に必要な情報**: スナップショット保持方式（`/tmp` コピー / git stash / commit）の選定は未決

**(G) Review Definition を PR head で固定** — ⬜ 設計完了・未実装

`review-prompt.md` を更新すると過去・進行中の PR と採点基準が食い違う。プロンプトに version フィールドを追加し、task-log に hash を記録してドリフトを検知する。

**(H) 承認キューの監視** — 🔶 設計のみ・実装見送り

実測 39 件/月で、参考記事の「月 300 件でパンク」の 1/8。**現時点では過剰設計**と判断し、可視化のみ実装、閾値監視は設計止まり。

## 5. ループエンジニアリング（実装済み）

**詳細レポート**: `retail-stats-tracker-loop-engineering-design.md`（1,393 行）/ `ai-virtual-office-loop-engineering-design.md`（423 行）

### 採用済みの原則

**(I) hooks の 2 系統を区別する** — ✅ 採用済み

| | 観測用 hooks | 検証用 hooks |
|---|---|---|
| 目的 | イベント収集 | 開発ループの検証信号（損失関数） |
| 失敗時 | 必ず握り潰す | ブロックしてフィードバック |

**(J) 損失関数を定義する** — ✅ retail-stats-tracker で採用

`L_silent` / `L_extract` / `L_repro` / `L_prov` の 4 種。最大の危険を「silent accumulation」（失敗が例外にならず不在として蓄積する）と特定。

**(K) maker-checker 分離** — ✅ 採用済み

`retail-stats-qa` は Bash を持ち Write/Edit を持たない。構造的に自己承認できない。

**(L) 評価データを先に凍結する（LayerX 規律）** — ✅ 採用済み

golden-60 を実装前に凍結。**「解けないことが正解」のケースを評価データに含める**のが要点。これが無いと「取れた数」だけが報酬になり、無理に数値をひねり出す方向へ最適化が進む。

実効性の証明: `retail-stats-tracker` の M3 で「率を億円として蓄積する」誤格納を golden-60 が検出した（例外にならないため他の手段では気づけなかった）。

**(M) Stop 配下の hook は全て読み取り専用にする** — ✅ 採用済み

hooks は**並列実行される**ため（公式仕様）、破壊的検査を Stop に置くと他の hook と競合する。ロックによる直列化は「ゲート skip の常態化」を招くため棄却し、破壊的検査を `--full` 経由に分離した。

## 5.5 コメントの分量は不確実さの指標である

**出典**: [Claude が書く長いコメントは、Claude 自身の役に立っていなかった](https://zenn.dev/uzu_tech/articles/86a2ef05a7d649)（wellPicker / 2026-08-05、curl で原文取得 6,212 字）
**詳細レポート**: `analyses/comment-density.md`（自組織での実測あり）

### 主張

著者が Claude 本人に「長いコメントは AI 自身の読解を助けているか」と尋ねた結果:

1. **助けにならない** — 実際に見ているのはコードそのもの。コンテキストを圧迫して不利になる
2. **理解のためではなく出力の癖** — 説明的な出力が好まれるよう訓練されている
3. **自信がない箇所ほど言葉で埋めて補強する** ← 著者が最大の収穫とした点

> **コメントの分量が、その箇所の不確実さの指標になっている。**

丁寧な説明を「よく理解して書かれた証」と読むのは**逆**である。

### ルールは半分しか効かなかった

「コードから復元できない情報だけを書く」ルールで比率は 21.1% → 8.8% に半減したが、**4 行以上の長いブロックは 52 → 50 個でほぼ不変**。理由は **無意味だから消せるのではなく、有用だから消せない**。

判断軸を「有用か」から「**そこがその情報の置き場所か**」に変えることで解決した（変更履歴は git log、タスク ID は issue）。

### 自組織での実測結果

| 対象 | 比率 | 4 行以上のブロック | 最大 |
|---|---|---|---|
| `.claude/hooks/*.sh` | **11.5%** | **15 個** | **29 行** |
| `.claude/hooks/*.py` | 6.4% | 2 個 | 7 行 |

**記事のルール適用後（8.8% / 最大 18 行）を上回っている。**

さらに「置き場所」基準を当てたところ、**同じ知見が CLAUDE.md と hooks コメントに重複**していた（`PROJECTS_PAT` の制約が計 11 箇所）。

### 採用候補

**(N) 「不確実性の明示」をルール化** — ✅ **採用済み**（2026-08-08）

CLAUDE.md の注意事項に追加。「不確実さを分量で埋めない。『未確認』と明示的に書く」。
既に 4 レポートで「未検証事項」章を設ける運用が定着していたが、**ルール化されておらず秘書の判断に依存**していたため明文化した。

**(O) hooks コメントと CLAUDE.md の重複解消** — ⬜ 未採用

`PROJECTS_PAT` の制約が 11 箇所に散在。置き場所は CLAUDE.md であり hooks 側は参照に留めるべき。
**コスト**: 中（16 ファイルの精査）
**判断に必要な情報**: hooks が `/company-spawn` で新リポにコピーされる場合、CLAUDE.md 参照が切れる点をどう扱うか

**(P) ルール追加後の効果測定を習慣化** — ⬜ 未採用

本組織はルールを追加した後、出力に効いたかを測っていない（今回が初回）。
記事の著者は「体感では効いた/効かないを取り違える」と明言している。

## 5.7 PKB の 3 段導線（Capture → Daily → Distill）

**出典**: [0.5くらいから始めるPersonal Knowledge Base 構築実践](https://zenn.dev/mkj/articles/claudian-orchestra-build_20260720)（Taisei Ozaki / 松尾研究所 / 2026-07-30、curl で原文取得 15,020 字）
**詳細レポート**: `analyses/pkb-three-stage-pipeline.md`（解説つき・実測あり）

### 主張

Obsidian の Vault を**人間と AI の共有メモリ**に据える構想。骨格は 3 段。

```
外部ソース ──▶ Inbox/ ──▶ Daily/ ──▶ Wiki/ など Main DB
              Capture     Daily      Distill
             （自動寄り）（人間の監査盤面）（承認必須）
```

**人間は Daily 1 枚を見るだけで全体を差配できる**のが設計の要点。取り込みは自動でよいが、永続化には人間の承認を挟む。

### 自組織との対比

3 段導線は**既に存在する**（Obsidian を使わない点だけが違う）。

| 段 | 本組織の該当 | 規模 |
|---|---|---|
| Capture | `daily-digest/` / `.conversation-log/` / `.session-summaries/` | 115 / 15 / 124 |
| Daily | `board.md` / `dashboard.html` / `reports/` | 32 レポート |

## 5.8 AI による PR 承認ゲートと「人間が見るべき変更」の定義

**出典**: [58% の Pull Request を AI が承認するようになった](https://zenn.dev/she_techblog/articles/937836550dfdf3)（qsona / SHE 株式会社 開発責任者 / 2026-08-07、curl で原文取得 6,664 字）
**詳細レポート**: `analyses/ai-pr-approval-gate.md`

### 主張

PR レビューがボトルネックという課題に対し、**AI がコードレビューと approve 判断まで行う**仕組みを実装。approve 率 1 割 → **58%**（2 週間の速報値）。

出発点は **直近 3 週間 75 件の全数分析**で、60% が無言 approve か LGTM のみ、実質的な指摘は約 1 割、しかもその大半が AI 由来だった。

設計の核は 3 つ。

1. **2 軸の分離** — 「AI の意見」(approve/pending/need fix) と「人間レビューの要否」(required/optional) を独立させる。両方揃ったときだけ approve。1 軸だと「AI は OK だが人間も見てほしい」が潰れる
2. **決定的ゲートに LLM を使わない** — 監査で「なぜ人間レビューに回ったか」を再現できる必要があるため、ファイルパスのマッチで判定する
3. **`pending`** — diff の外の事実に正しさが依存する場合、承認も却下もせず質問して待つ

**最重要の教訓**: 以前は「ロジックの変更があれば人間レビュー」だったが、ほとんどの PR が引っかかった。**あいまいにしておくと AI は安全側に倒しがち**。条件を具体的に決めて、当てはまらなければ OK にする形式にした。さらに「**安全側に倒さない判断は責任者が明示的に下さないと起きない**」と運用面も指摘している。

### 自組織との対比（直近 60 PR の全数分析）

**記事は「人間レビューを減らす」話だが、本組織には逆向きに効く。**

| 指標 | SHE 社 | **本組織** |
|---|---|---|
| 母数 | 75 件 | 60 件 |
| レビューが付いた PR | （人間レビュー対象が母数） | **0 件（0%）** |
| approve 率 | 1 割 → 58% | **実質 100%** |

**止まる場所が一つもない。** さらに深刻な数字が出た。

| 実測 | 値 |
|---|---|
| 統制系（hooks/rules/CLAUDE.md/skills）を含む PR | **10 / 60 = 16.7%** |
| うち 3 層レビューまたは task-log を持つもの | **0 件** |
| L2 を持つ Skill | **6 / 17（35.3%）** |
| nightly の CLAUDE.md/rules 自動更新 | 12 回・**+49 / -5 行（追記が削除の約 10 倍）** |
| `l2_composite` の最小値 | **0.88**（fail が 1 件も残っていない。retry は 4 件発生） |

**成果物には 3 層の審査を敷き、審査の仕組みそのものを変える PR は素通ししている。** #723（品質ゲートの修正）と #714（Case Bank の修正）が実例。

記事の 8 項目のうち **6 項目が本組織に実在する**（統制系 / 不可逆操作 / 個人情報フロー / 外部契約 / 新規パターン / 高リスク値計算）。

### 採用候補

**(X) 「人間が見るべき変更」の定義を作る** — ⬜ 優先度 **高**

統制系 16.7% がレビューなしでマージという**実測**が根拠。まず**決定的ゲート（パスマッチのみ、LLM 不使用）**だけでも意味がある。`.claude/hooks/` `.claude/rules/` `CLAUDE.md` `.github/workflows/` を触る PR は無条件で人間レビュー必須にする。コスト小〜中。ゲートの設置場所（hook / Actions / Skill 内）は**未検討**。

**(Y) 判定を 2 軸に分ける** — ⬜ 優先度 中

現状 `l2_composite ≥ 0.85` の 1 軸。「L2 は通ったが人間も見るべき」を表現できない（#724/#728/#729 が実例）。**候補 B・S はこの 2 軸化の一部として実装できる**。

**(Z) `pending`（承認も却下もしない状態）** — ⬜ 優先度 中

「その文書の外の事実」に依存する判断を保留する状態。現状 pass/fail の 2 値なので未確認事項が丸められる。**候補 B / S / Y と同じ問題**なので統合して扱う。記事の対話ループ（作者に質問）は本組織では作者も AI なので、**保留状態を持つところまで**が現実的。

**(AA) nightly の CLAUDE.md 自動更新に人間の承認を入れる** — ⬜ 優先度 **高**

**追記 +49 / 削除 -5** で 12 回とも無レビュー。**AI が自分を縛るルールを一方向に増やしている**。候補 Q（CLAUDE.md 削減）が進まない原因がこの非対称性で説明できる。まず auto-merge を外して approve 必須にする（コスト小）。

**(AB) L2 の初回スコアを保存する** — ⬜ 優先度 中

記事の「偽陽性/偽陰性を見ていくべき」に対応。現状 retry 後の最終値しか残らず、**L2 の判定精度を後から検証できない**。`l2_composite_initial` を 1 フィールド足すだけ（コスト小）。ただし**過去分には遡れない**。

**(AC) AI による PR auto-approve の導入** — ❌ **不採用**

記事の主題そのものだが、**本組織には導入する対象がない**。approve 率は既に実質 100% で、記事が解決した課題が存在しない。同じ記事から採るべきは逆向きの示唆（X / Y / Z / AA）。

## 5.9 Claude Code と Codex の設定は、放置すると分岐する

### 主張

**worktree 記事**: 決定論的な処理を LLM の判断から外すだけでは足りない。**呼び出し方しだいで挙動が変わる仕組みに載せていれば同じこと**。`isolation: worktree` は「名前を付けずに起動した場合のみ有効」で、名前付き起動では無視される。見分ける物差しは **「単体で叩いて確かめられるか」**。この不安定さは「AI の気まぐれ」に見えるため、**実際には配線の問題なのにプロンプトを直そうとしてしまう**。

**ハーネス記事**: 20 章ぶんの仕組みを足しても**エージェントループ本体は最後まで変わらない**。Skill の 2 段階ロード、Memory の目次だけをシステムプロンプトに置く設計（キャッシュを壊さない）、Agent Teams の実体がファイル追記のメールボックスであること、が cc-sier の各機能の理解に直結する。

### 自組織との対比

| 項目 | 実測 |
|---|---|
| `isolation: worktree` の使用 | `.claude/agents/` `.claude/skills/` `plugins/` に記述**なし** → 該当なし（予防知識として保持） |
| L0 検証の入口 | Skill ごとに異なる（`review-drawio.js` / `validate_drawio.py` / grep）→ 原則③に反する |
| MCP と CLI の使い分け | `.mcp.json` に 4 サーバー。CLI 化の検討記録は**なし** |

### 採用候補

**(AF) Skill の L0 検証を 1 本に寄せる** — ⬜ 優先度 **中**

原則③の適用。ただし**現行 9 フェーズで検証の取り違えが実際に起きているかは未測定**。まず task-log の `l0_retries` を集計し、実績がなければ着手しない。

**(AK) 純粋リファクタリング判定ゲートからの部分転用** — ⬜ 優先度 **低**

出典: [「純粋リファクタリング」を AI に証明させて自動マージする](https://engineering.nature.global/entry/2026/07/prove-pure-refactoring-with-ai-and-auto-merge)（Nature、3 ヶ月半で 247 件自動マージ・1 件あたり約 $1.35）。**ゲート自体は不採用**（cc-sier はコードの自動テスト資産がなく「挙動の等価性」が成立しない）。転用できるのは 3 点 —— 出力を **JSON スキーマで縛る**、**「他多数」「以下同様」の省略を禁じて全件列挙させる**、`empirical-prompt-tuning` で review-prompt 自体を育てる。**候補 F・Y と同じ層の話**。

## 5.11 承認プロンプトでは「スコープ違反」が見逃される

**出典**: [40 万件の AI 承認を分析したら、見逃し率が 3 倍違った](https://qiita.com/jqit_suwa/items/ac7d1201bd14e9a4e1ac)（jqit_suwa / 株式会社JQIT、2026-08-06、curl 4,422 字）／ [コーディングエージェントを安全に使うための実務ガイド v0.2](https://zenn.dev/kanaria007/articles/ee3dfd438af4df)（かなりあ、2026-08-07、curl 9,713 字）
**詳細**: [`analyses/2026-08-w2-claude-code-codex-agent.md`](../../../../docs/insights/analyses/2026-08-w2-claude-code-codex-agent.md) §4.4 / §4.5

### 主張

409,000 件の承認判断で平均正答率 66.3%。**見逃し率は脅威の種類で 3 倍違う**（明白な破壊的操作 11.7% ↔ スコープ違反 35.0%）。承認プロンプトに出るのはコマンドそのものだが、危険かを決めるのは**そのコマンドが何に対して実行されるか**。Anthropic のテレメトリではユーザーは約 93% の許可プロンプトを承認している。対策は「注意して読む」ではなく、**危ない種類を承認画面まで持ち込まないこと**。

安全ガイド側の対応する主張が §9「プロンプトだけで安全を守ろうとしない」。**プロンプトは望ましい振る舞いを伝える層であって、望ましくない変更を通さないのは CI / 権限 / repository policy の役割**。さらに §10「AI には『問題ありませんか』より『証拠を出してください』」、§12 の 4 値（CONFIRMED / PARTIAL / UNCONFIRMED / CONTRADICTED）、§13「**AI に『人間が確認した』と書かせない**」。

> 記事のデータには著者自身が 3 つの限界を明記している（査読なし / ゲームなので脅威の割合が現実より高い / 被験者の自己選択）。

### 自組織との対比

`.claude/settings.local.json` は **`allow` リストのみで `deny` ブロックもディレクトリ制限もない**。`@.claude/rules/multi-org.md` の「組織 A の作業で組織 B に書き込まない」は**プロンプトでしか守られていない**——これは §9 が名指しする状態そのもの。

一方で本組織は単一リポジトリ・単一開発者・本番認証情報を実行環境に置いていないため、記事が想定する被害シナリオの一部は成立しない。

### 採用候補

**(AH) `deny` とディレクトリ制限の追加** — ⬜ 優先度 **中**

組織横断の誤書き込みを構造的に止める。コスト小。

**(AL) L2 レビューを「判定」から「証拠の構造化」へ寄せる** — ⬜ 優先度 **中**

現行 L2 は `verdict: pass|fail` を返す**判定者**。4 値化と未確認事項欄の追加が筋だが、**これは auto-merge の無人前提に触れる**ため方針判断であって「記事が正しいから直す」類ではない。まず **findings に未確認事項の欄を足す部分適用**から。**候補 B・S・Y・Z と同じ問題群**。

## 5.12 サブエージェントは「まとめて並列」が速く安い／キャッシュと棚卸し

## 5.14 「守ってほしい」を「守るしかない」に変える — ガイドとセンサー

**出典**: [Claude Codeに「違反できないコード」を書かせる：ガイドとセンサーの設計](https://qiita.com/shun123/items/7aa06b6982dfd1730af0)（shun noel / JISOU、2026-08-11、curl 34,401 字）／ [Claude Code に「同じ指摘を二度させない」仕組みを hook で作った](https://zenn.dev/nozomi720/articles/claude_code_hooks_feedback)（nonchan7720、2026-08-11、curl 9,506 字）
**詳細**: [`2026-08-w2-claude-code-codex-agent.md`](../../../../docs/insights/analyses/2026-08-w2-claude-code-codex-agent.md) §8.4.1 / §8.4.2

### 主張

**ガイド記事**: ハーネスを「ガイド（書ける範囲を狭める）」「計算的センサー（CPU、決定論）」「推論的センサー（LLM、意味を見るがぶれる）」に分ける。**cc-sier の L0 / L2 とほぼ同じ二分**だが、**先に計算的センサーを作り、その限界を自分の目で確かめてから推論的センサーを作る**順序を推す。持ち帰れるのは 3 点。

- **`deny` の迂回経路** — `node -e` / `sh -c` は引数の文字列を実行するため `rm` を禁止しても回避できる。`git -c キー=値` は設定ファイルを変更しないが `git config` と同じ効果を持つ。**片方だけ禁止しても意味がない**
- **`Write(path)` ルールは受理されるが参照されない**（ファイル権限の照合は `Edit(path)` と `Read(path)` のみ）
- **エラーメッセージは修正手順である** — 「禁止です」では自己修正できない。「どこに何を定義し、どう注入するか」まで書く。**メッセージの質がそのまま自己修正の成功率になる**

さらに「ファイルが 1 つも無い状態でも成功する検査が 5 つ中 3 つあった」という実測を示し、**「通った」は「検査された」を意味しない**と結論づける（候補 S と同じ主張のより原始的な形）。

**count 記事**: 1 指摘 = 1 ファイルに永続化し、`count`（指摘回数）から強制力を自動決定する。1〜2 回は warn、3〜4 回は ask、**5 回以上は deny**。設計判断が 3 つ効いている。

- **`count` は自動インクリメントしない。** hook の検知は「AI が破ろうとした」だけで「人間が再度指摘した」ではないため、**重みを上げる権限は人間側に残す**
- **本文に「言い訳」を書かせる** — 破りたくなる場面の理屈を先に潰す
- **hook 自身は絶対に事故らせない** — 例外を握り潰して `exit 0`。「検知できないことより止まらないことを優先」

限界: 47 ルール中 `enforce` を書けたのは 14 個。**順序のルールはファイル単体では違反判定できない**。

### 自組織との対比

| 項目 | 実測 |
|---|---|
| `settings.local.json` | **allow のみ、`deny` なし** |
| `~/.claude/feedback/` | **0 件**（count による段階的強制は未導入） |
| auto-memory の feedback 系 | 7 ファイル（**記録のみ。強制力に接続されていない**） |

### 採用候補

**(AP) `deny` の具体設計を導入する** — ⬜ 優先度 **高**

候補 AH の実装指針。特に迂回経路（`node -e` / `sh -c` / `git -c`）と `Write(path)` の仕様は自力では気づけない。コスト小。

**(AS) 指摘の `count` を強制力に接続する** — ⬜ 優先度 中

Case Bank / feedback memory は記録止まり。warn → ask → deny の段階化を入れる。**`count` を人間だけが上げる**設計は、候補 AA（AI が自分を縛るルールを一方向に増やす）への対処にもなる。**未検証**: 実装コストを見積もっていない。

## 5.15 承認の auto mode 既定化と fork 既定化 — 前提が変わった 2 件

**出典**: [Claude Code、承認ボタンを何度も押さなくていい「自動モード」がデフォルトに](https://pc.watch.impress.co.jp/docs/news/2131930.html)（PC Watch、2026-08-10、curl 9,798 字）／ [Claude Code v2.1.230〜v2.1.232 の主要アップデート](https://dev.classmethod.jp/articles/20260814-cc-updates-v2-1-232/)（DevelopersIO、2026-08-14、curl 13,882 字）
**詳細**: [`2026-08-w2-claude-code-codex-agent.md`](../../../../docs/insights/analyses/2026-08-w2-claude-code-codex-agent.md) §8.2.2 / §8.2.3

### 主張

**auto mode**（2026-08-14 から Pro / Max / Team の新規セッション既定）: 全ツール呼び出しを分類器がチェックし、危険な操作を検知・ブロック。分類器のトークンは無料。Anthropic の数値では、危険なコマンドの検知率が**人間 13.6% に対し auto mode 89%**。人間はセッション初期 17% → 承認 50 回以降 **約 5%** まで落ちるが、auto mode はセッション長に依存しない。

**§5.8 / 本編 §4.5 の「40 万件で見逃し率 3 倍」と同じ問題への提供側の回答**であり、「回数を重ねるほど注意が落ちる」という傾向は両者で一致している。

> **注意**: 数値はすべて Anthropic 自身の発表で、第三者による再現は未確認。

**fork 既定化**（v2.1.232）: `subagent_type: "fork"` のサブエージェントが**会話全体とプロンプトキャッシュを引き継ぐ**。従来は "no memory of prior runs" で、前提の再入力・キャッシュミス・文脈の取りこぼしが起きていた。teammate 以外のエージェント起動も既定でバックグラウンド実行に。従来動作は `CLAUDE_CODE_FORK_SUBAGENT=0`。

同回は権限バイパス 2 件（PowerShell / Git Bash シンボリックリンク）とネスト git リポジトリの信頼継承も修正。

### 自組織での実測

| 項目 | 実測値 | 意味 |
|---|---|---|
| Claude Code | **2.1.233** | fork 既定化（v2.1.232）**適用済み** |
| `defaultMode` | **未指定** | 2026-08-14 以降 **auto mode で動いている** |
| `CLAUDE_CODE_FORK_SUBAGENT` | 未設定 | fork 既定のまま |

### 採用候補

**(AQ) fork を前提にサブエージェントの投げ方を組み直す** — ⬜ 優先度 中

**既に適用済み**なので判断は「使うか」ではなく「前提を書き換えるか」。**候補 AG（独立タスクの並列起動を明文化）は fork 前提で書き直す必要がある**。本編 §2.1 の 44% 削減が fork 下でどう変わるかは**未測定**。

**(AR) auto mode 既定化を前提に権限設計を見直す** — ⬜ 優先度 中

**すでに auto mode で動いている。** 分類器 89% を信頼するのか、`deny` で構造的に潰すのか（候補 AP）の方針決めが要る。**未確認**: auto mode が実際に本セッションで有効かを確認しておらず、`defaultMode` 未指定からの推定にとどまる。

## 5.16 Agent Plugins 1.0.0 と claudex — 見送る 2 件

**出典**: [Agent Plugins 1.0.0 は何を標準化し、何を標準化しなかったのか](https://zenn.dev/inariku/articles/agent-plugins-1-0-deep-dive)（AWS Japan、2026-08-10、curl 17,364 字）／ [Claude Code経由でCodexを使う「claudex」の導入・検証レポート](https://zenn.dev/yam2357/articles/claudex-proxy-codex)（山田、2026-08-10、curl 13,640 字）

**限界**: 著者自身が「実験は各 1〜3 回で統計的有意性を主張する規模ではない」「判定者に執筆者と同系列の評価者バイアスがある」と明記している。
